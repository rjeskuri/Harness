# Work

Arguments: $ARGUMENTS

Ready tickets:
!`harness-board ready 2>/dev/null | head -20`

Every run of this skill is one turn, and a dispatched run (`claude --bg` by default, `claude -p` with `--api`) has no next turn: whatever is unfinished when the turn ends stays unfinished. Run every agent in the foreground, with `run_in_background: false` on each Agent call, and wait for its result before the next step; never launch an agent in the background. A call refused because the auto-mode classifier gave no verdict (`classifier:auto-mode:unavailable`) is an outage, not a denial, and ends no turn while steps remain: do the reads it was for with Read, Grep and Glob instead, retry the call once as it was, and when it is still refused go on with the steps that do not need it; once nothing else is left it is a tool failure no stage can fix (park, the paragraph after the steps). Every high or medium review finding on the files the ticket touched is fixed before `harness-pr ready`; a low finding goes into the PR notes for the owner, with no fix round; only a high or medium finding outside the ticket's files becomes a new ticket, and the PR body names it and says why. Every ticket the loop files (that one, a size-cap split, any other follow-up) is proposed: `harness-board task create ... --proposed --parent <epic>`, the epic being `parent` in `harness-board show N --json` (no `--parent` when there is none), and never with `--blocked-by N`, so it never blocks this ticket and the owner promotes it. With no ticket number the turn ends once `harness-work dispatch` has launched the runs, shown its `--dry-run` plan or found no ready tickets, and you have reported its output. With a ticket number the turn ends only when `harness-pr land` has merged the PR (step 9, at any risk), `harness-pr ready` has run on a `manual-land` ticket, whose PR only the owner's `/harness:land` lands (step 8; or step 9's land answered exit 9), `harness-board park` has parked the ticket and `harness-work dispatch --after N` has run (a final failure, the paragraph after the steps), `harness-board needs-input` has posted an agent's question (or start found the ticket still waiting for an answer), `harness-work start` has refused the ticket and you have reported why, or, on an ops ticket, the ops path has ended (its Results posted and the ticket in review, its preview waiting for the owner's OK, or the ticket retyped).

## No ticket number: dispatch
Run `harness-work dispatch $ARGUMENTS`. `--only N[,N...]` plans just the named tickets and `--after N` the ready tickets N unblocked, else the next ready one; a number after `--only`, `--after` or `--max` is that flag's value, not a ticket number. With `--dry-run` in the arguments, or more than ten ready tickets and none of `--max`, `--only` and `--after`, run it with `--dry-run`, show the plan and end the turn there: `/harness:work --max N` launches it. It starts a worktree per ready ticket (and per in-progress ticket whose last run ended early without a ready pull request: no PR, or only a draft; and per in-review ticket whose last run ended before the land, its ready pull request still open and the ticket not `manual-land`, which the new session resumes through step 1's in-review branch to step 9) and launches a session for each. The subscription is the default. Without `--api` or `--venue headless`, every run is a background session on the subscription. `--api` in the arguments reaches `harness-work dispatch` as its alias for `--venue headless`, so the runs are headless and billed to the API key. With `--api` or `--venue headless`, dispatch is refused while the API budget is exhausted. Report what was launched, or "No ready tickets.", and that notifications arrive when a PR is ready or a ticket is parked or needs input. Do not work tickets in this session when dispatching.

## One ticket: the loop
You orchestrate; agents do the work; the tools keep the record. Work only in the worktree path that `harness-work start` prints, never in the main checkout. After start, read `harness-board tier N --json`: on every test-author, breaker and coder Agent call (retries and fix rounds included) pass its `tier` as `model`, and pass its `effort` as `effort` when that is not null. The project's `HARNESS_CODE_TIER` and `HARNESS_CODE_EFFORT` decide that tier and effort when it sets them, the labels otherwise. On escalation pass the tier and effort `harness-work stage` names, counted from the tier and effort the stage ran at: `escalate opus` gives `model: opus` with no effort, `escalate opus xhigh` gives `model: opus` and `effort: xhigh`, and a stage already at Opus xhigh gets `park`, never a Fable run. The reviewer's model and effort come from `harness-board tier N --stage review --json` instead: pass its `tier` as `model`, and its `effort` when not null; the project's `HARNESS_REVIEW_TIER` decides that tier when set, the labels otherwise (Opus, at effort `xhigh` for a `risk:high` ticket; Fable when `HARNESS_REVIEW_TIER` is `fable`). Give each Agent call the `description` `#N <stage>`, with N the ticket number (`harness-work cost` reads it): `#N tests` for the test-author (in a revise pass or a fix round too), `#N breaker` for the breaker, `#N code` for the coder until the first review, `#N review` for the first review, and `#N fix` for every coder or reviewer run after the first review (its findings, CI failures, the owner's comments); a retry or an escalation keeps its stage's name. The agents commit on the ticket branch and never push; you push (`harness-pr open` on the first pass, `git push` in the worktree after that). Record each completed stage once with `harness-work stage N <stage> pass|fail --json` and the tier and effort it ran at. Follow its `action` (retry, escalate, park, or done) and `next`. An unusable reviewer response with no round to record uses `harness-work attempt N review fail` with the actual review tier and effort; retry according to its answer. On an unusable fix re-check record `harness-work attempt N fix fail` against the fix cap. A failed tool call or a moved head is distinct from a reviewer verdict. On resume read the latest round and cached attempts before recording or posting anything again.

1. **Start**: `harness-work start N --json`; when it refuses the ticket (an epic, a closed ticket, open blockers), report its message and stop. When it reports `ops: true`, follow **The ops path** below instead of these steps. Then read the ticket context it prints (request, outline, definition of done, tests, context, the epic's goal, blockers, recent comments). A dispatched prompt can carry a paragraph after the ticket number saying the previous run ended early with draft PR #P open and the worktree may hold uncommitted work: after start, read `git status` in the worktree, `harness-pr comments <P>` and the latest harness review (from `gh api --paginate repos/<owner>/<repo>/pulls/<P>/reviews`, the review with the newest `submitted_at` whose body carries the `<!-- harness-review -->` marker; its body holds the count and the findings not on a changed line, and the findings on changed lines are its inline comments at `gh api repos/<owner>/<repo>/pulls/<P>/reviews/<id>/comments`, with `<id>` the numeric `id`, not the `gh pr view` node id), then pick up at the step they point to, not at step 2 by default: committed or uncommitted source work goes to the step it belongs to, the high and medium harness review findings go to the coder as in step 6; a `harness-pr open` on that PR without `--review` or `--notes` keeps its Review summary and Notes section, so this session needs neither file to run it. A branch brought home from a cloud session (`harness-work cloud N`; no harness hook runs there) has its tests and source committed together and no red record (`harness-red status --worktree <path>` answers `No red run recorded`), so tests_first denies every source edit and `harness-red check` refuses: run `harness-red reprove --worktree <path>` before any local source edit or fix, and before merging main into the branch, never mid-merge (the merge stages main's own test changes, and reprove would count them as the branch's against the old merge base): a merge that already conflicted is aborted with `git merge --abort`, reprove runs, then the merge is redone and resolved. Red writes the record; when it refuses (the tests pass against main's code at the merge base, or prove nothing), the tests go back to the test-author as a green check does in step 2, except a refusal that names a dependency the temporary worktree could not import: point `HARNESS_TEST_CMD` at that environment by absolute path, as it says, and run reprove again. Branch on its `previous_status` (the status before start ran): `needs-input` with `answers` (all of the owner's replies since the newest needs-input question, oldest first): together they answer that question; continue with them (start moved the ticket to in-progress). `needs-input` with `waiting: true`: no answer yet and the ticket stays in needs-input; report that and stop. `in-review` (start leaves that label alone) with a PR: go to step 10. Otherwise, when start reports `resume: true` (an unparked `ready` ticket, or any ticket whose branch already carries commits beyond main or has an open PR `pr`: #407), treat it like the draft-PR paragraph above and pick up at the step the branch and PR state point to, reading `git status`, `harness-red status --worktree <path>`, the PR's comments (`harness-pr comments <pr>`) and its latest harness review: a branch with source changes never goes back to step 2's test-author or its default-base `harness-red check`. Read `flags` from `harness-board show N --json`: when it holds `no-tests` (docs or configuration only), say so and skip step 2 (the test-author and the red check) and step 3 (the breaker).
2. **Tests** (`harness:test-author`, stage `tests`). A `no-tests` ticket skips this step: go to step 4, where the coder works from the definition of done; the verify command must still pass and the review still runs. Otherwise: the context, the worktree, the test command (`HARNESS_TEST_CMD` from `.claude/settings.json`, or the detected default), and the ask for broad behavior tests first, each new or changed module under 180 s alone. The author runs `harness-red check --worktree <path>` and returns its evidence. After success confirm it with `harness-red check --reuse --worktree <path>`; this reruns only when the proof inputs changed or no reusable record exists. Green or no tests fails the stage. On the successful tests stage pass `--breaker-required` only for the high-risk changes described in step 3.
3. **Break** (`harness:test-breaker`, stage `breaker`): this step runs only where an adversary matters: a `risk:high` ticket whose outline or tests change a hook's decision path (`plugins/harness/hooks/*` in the Harness repo, a project's own hooks elsewhere) or a tool that destroys or rewrites data (backup, land, revert, worktree remove). Every other ticket, a `risk:high` one touching neither included, goes from step 2 to step 4; say which it was. Otherwise: `harness-red scratch create --worktree <path>`; give it the scratch path, the test files, the definition of done and the test command. One round, never a second. `cheat passed` counts only for a constant or a cheat that special-cases the fixture inputs: record `harness-work stage N breaker fail`, which answers `done`; any other cheat counts as `cheat failed`: record `harness-work stage N breaker pass`. Either way the breaker's `Requirement:` lines go to the coder (step 4) and, as check items, to the reviewer (step 5); its `Not worth pinning:` list goes nowhere. Then go on to step 4: the breaker sends no ticket back to the test-author and never parks it. Remove the scratch with `harness-red scratch remove --worktree <path>` after the round.
4. **Code** (`harness:coder`, stage `code`): the context, worktree, test files, red run, test command and the own-tests command, `harness-red run --worktree <path>`, which runs only the ticket's own test files (the full suite runs in CI, step 7), and the breaker's `Requirement:` lines from step 3, if any, which it meets like the definition of done. It commits on the ticket branch when green and does not push. "A test looks wrong": back to the author with the coder's reasoning, one round, then red again. "Outgrown the size cap": file each part of the split it proposes as a proposed task (`harness-board task create --title T --body-file F --size S --risk R --proposed --parent <epic>`, the body in the task template's headings: Request, Outline, Definition of done, Tests that must pass, Context), then park with `--follow-up` naming them (`harness-board park N --reason "code: outgrew the size cap" --follow-up A,B`, the paragraph after the steps).
5. **Draft and review.** Once the coder has committed and the ticket tests pass, run `harness-pr open N --worktree <path> --json` immediately. This pushes the branch and creates or reuses a draft PR. CI can now run during the foreground review. Capture the clean worktree's full HEAD SHA. Give the fresh reviewer that exact head, ticket context, red proof, own-tests output, and breaker requirements. Use the model and effort from `harness-board tier N --stage review --json` or the stage escalation. If a resumed draft has no marked review, start its first review here. Run Claude once on the first head. For each changed head after a recorded round go straight to the GPT re-check in step 6. On a legacy PR with no local round, establish the first paired round once.
6. **Findings and fixes.** Save the reviewer's raw findings array and verdict to a scratch file. Pass actionable findings to `harness-pr findings N --worktree <path> --head <reviewed-sha> --gpt-check --review <file> --model <model> --json`; give it `--rulings <file>` for agent rulings. Run the findings command as a background Bash task and await its completion notification in this turn; a large review may exceed the foreground Bash timeout. The command calls GPT-6.2 Sol independently on the same patch and publishes the combined result once. For an excluded patch, report the coverage gap and park for owner review. An explicitly authorized local reviewer may examine the excluded changes and submit a pinned local review with --head, --review and the actual reviewer name. If GPT fails, keep the Claude file for a retry on that SHA, count the failed attempt against the current stage cap and park on exhaustion. Report speculative outside gaps as notes rather than findings; only actionable outside blockers warrant tickets. This command owns posting the marked review, splitting the findings, recording the round and creating proposed follow-ups. If the head moved, review the new head before submitting. If publication failed, inspect the actual marked review and local round before retrying. Use the returned `files.review` and `files.notes` with `harness-pr open N --worktree <path> --review <review-file> --notes <notes-file>` to refresh the PR body. Carry forward any legacy notes and accumulated Not covered lines. Record its `record.stage` and `record.result` once with `harness-work stage` and follow `next`. For an existing pre-upgrade PR with a prior marked review and no local rounds, this re-check is a fix stage: use fix fail if the new round has blockers, fix pass otherwise.
   - On fix, send `files.blocking` to the coder. A test-file fix first goes to the test-author for the revise proof from step 10. The coder commits the fix, runs the ticket tests, and the orchestrator pushes. After a local-only round continue locally with owner authorization while protected changes remain, otherwise obtain fresh Claude findings for a paired review. After a paired round, on the new head run the same findings command with --gpt-check and --head, omitting --review and --model. Sol checks the changes since the previous reviewed head and verifies the prior blockers against current source. It checks the full patch after a history rewrite. Low findings stay in the PR notes. Apply the stage's fix cap; park on exhaustion.
7. **CI** (stage `ci`): `harness-pr checks <P> --wait --timeout 420`, on exit 8 the checks are pending, so wait again (up to two additional waits, then park with the pending run link). Record `harness-work stage N ci pass|fail` only for a completed check result. CI runs the whole suite in a clean checkout; it is the full-suite gate, so the loop runs no local full verify. Failures: the coder (`#N fix`) fixes and commits them and runs `harness-red run --worktree <path>`; push with `git push` in the worktree and check again; at most two rounds, fewer when `harness-work stage` answers `park` sooner (park: the paragraph after the steps).
8. **Ready**: the head review, then `harness-pr ready <P>`.
    - **Head review**: `harness-pr land` refuses a head its latest harness review does not cover (`review the head again`; `--accept-findings` does not override it), and only clean merges of main may follow the reviewed commit, so the loop's land and the user's `/harness:land` both need it. Take that review's `commit_id` (the review found as in step 1), then in the worktree `git fetch origin` and `git rev-list --first-parent --parents <commit_id>..HEAD`: one line per commit after the review, newest first, each the commit and then its parents. No line: no review. Otherwise judge every line as `harness-pr land` does (`autoland.at_head`), whoever made the commit and whatever its message says, since `git log` shows a hand-resolved merge and a clean one alike: a line is a clean merge of main only when it has exactly three hashes `<c> <p1> <p2>`, `git merge-base --is-ancestor <p2> origin/main` exits 0, and `git merge-tree --write-tree <p1> <p2>` exits 0 (1 is a conflict, resolved by hand) with a first line equal to `git rev-parse <c>^{tree}`; and the last line's `<p1>` must be `<commit_id>`. Every line a clean merge of main: no review. Anything else (a CI fix from step 7, a revise fix from step 10, a fix from step 9, a merge that conflicted or whose tree differs, a failing call): read findings --latest. If it returns no local round, run steps 5 and 6 with a fresh paired review on the pushed head and record the legacy fix stage. If the local round has no reviewers field, keep the re-review local while protected changes remain. Once cleared, obtain fresh Claude findings and run a paired check. Otherwise run the GPT-only re-check in step 6. If a fix changed the head, wait for its CI again.
    - **Ready**: `harness-pr ready <P>`. It refuses while the latest harness review has high or medium findings and no commit after it, and names them: those go back to the coder as in step 6. Low findings do not stop it: they stay in the PR notes for the owner. It sets `status:in-review` and notifies the user. Then step 9, unless the ticket is `manual-land` (`labels` in `harness-board show N --json` hold it, or ready printed `manual-land: waiting for /harness:land <P>`): only the owner lands that PR, with `/harness:land <P>`, so skip step 9, end the turn and report that PR #P waits for the owner. That is no park: no `harness-board park`, no `harness-work dispatch --after N`.
9. **Land**, at any risk (a `risk:high` ticket has had its Opus xhigh review in step 5): `harness-pr land <P> --catch-up --loop`, with no question to the owner first.
    - **The land**: `harness-pr land <P> --catch-up --loop` as a plain command, with nothing around it: no pipe, redirect, `;`, `2>&1`, `echo` or `tail` (a `cd <main checkout> &&` in front is the one addition allowed), since a call with a part no allow rule covers goes to the auto-mode classifier, which has denied it as `[Merge Without Review]`; give the Bash call `timeout: 600000` and read the tool's own output. Leave `--rounds` and `--timeout` at their defaults (420 s of waiting a call, which leaves the merge and the canary room under the Bash tool's 600 s), and never add `--accept-findings` or `--discard`; keep `--loop`, which records `Landed by: loop` in the ticket's Cost block (a land without it counts as a person's). When the branch is behind main, `--catch-up` merges origin/main into it in the worktree if that merge is clean, pushes it and waits for the checks at the new head, so the loop makes no merge of main of its own; then the land merges the PR, removes the worktree and branch (it runs from inside that worktree too), fast-forwards main, posts the Resolution, closes the ticket, checks the epic and runs the canary. Once it has merged (exit 0, an exit 1 naming the revert after a failed canary, or a stop at a dirty worktree), run nothing after it, a dispatch included (dispatching what it unblocked is the land's job), and report from its output; never add `--discard`.
    - **Exit 8** (the checks still pending at its deadline): run the same command again, unchanged; it merges nothing new while the branch is current and lands once the checks are green.
    - **Exit 9** (`PR #P is manual-land: the owner lands it with /harness:land P`; nothing merged): end the turn as step 8 does for a `manual-land` ticket, reporting that the PR waits for the owner; no park, no `harness-work dispatch --after N`, and never another land call.
    - **A refusal** (exit 1, nothing merged; read its reason). A conflict with main, which names the conflicted files: on a branch with no red record that is not `no-tests` (`harness-red status --worktree <path>` answers `No red run recorded`, as on one brought home from a cloud session), first `harness-red reprove --worktree <path>`, as in step 1, its refusal handled as there; then the coder (`#N fix`) runs `git fetch origin`, merges origin/main in the worktree, resolves the conflicts and commits (when it cannot, as with a conflict in a test file, which it may not edit: park); then `harness-red run --worktree <path>`, `git push` in the worktree, `harness-pr checks <P> --wait --timeout 420` (red: CI rounds as in step 7), step 8's head review, and land again. Red checks, which it names (a catch-up merge it pushed stays): `harness-work stage N ci fail`, a CI fix round as in step 7, step 8's head review, and land again. `review the head again`: step 8's head review, then land again. Any other refusal (still behind main after its catch-up rounds, open findings, a worktree that is dirty or missing, a failed read): park.
    - **Caps**: three re-runs on exit 8 in a row (four calls, about 28 minutes of waiting), two conflict resolutions, the CI rounds of step 7 and the fix rounds of step 6 as `harness-work stage` counts them, and five land calls in all, the re-runs on exit 8 not counted. A cap reached: park, the land's last output as the evidence.
10. **Revise** (already in review): `harness-pr comments <P> --unresolved`; the owner's comments are the coder's task (`#N fix`; it commits); with none, go to step 8. Comments that need new tests go to the test-author (`#N tests`) first, who leaves them uncommitted and proves them red with `harness-red check --worktree <path> --base HEAD` (the branch already carries source changes, so the default base refuses, and `--base HEAD` sees only uncommitted changes); when it answers green (tests of behaviour the branch already has, which pass at HEAD), or `harness-red status --worktree <path>` says `current: no` once such tests are committed, have the author prove them with `harness-red reprove --worktree <path>`, which runs the branch's test files against main's code at the merge base; after an ordinary successful check, confirm it with `harness-red check --base HEAD --reuse --worktree <path>`. For reprove, inspect the successful record and current status. Then the coder commits them with its fix. The coder runs `harness-red run --worktree <path>` after its fixes. Push with `git push` in the worktree (the PR body needs no refresh; a `harness-pr open N` here without `--review` or `--notes` would keep its Review summary and Notes section); `harness-pr checks <P> --wait --timeout 420`; answer each thread with what changed (`gh pr comment <P>` with a short list); then step 8: the head review of the coder's commits, and `harness-pr ready <P>`, which sets `status:in-review` again and notifies the user (gh accepts a PR that is already ready). Then step 9, at any risk: the PR lands without waiting for the owner again, his addressed comments being his review (the head review still covers the head for `harness-pr land`); a `manual-land` ticket ends the turn at ready instead, as in step 8.

**Park** on a final failure: `harness-work stage` answered `park`, step 9 reached a cap or a refusal it does not handle (exit 9 is handled: it is never parked), a size-cap split was filed (step 4), or a tool fails in a way no stage can fix (gh or git down, a refusal outside the loop's reach, a classifier that still gives no verdict). Write the tail of the failing output (the agent's last report, the checks' or the land's output) to a file in the scratchpad, run `harness-board park N --reason "<stage>: <what still fails>" --evidence-file <that file>` (`--follow-up A,B` for a split; without it the park files one proposed follow-up itself), then `harness-work dispatch --after N` (it launches the next ready ticket, if any), report both outputs, and end the turn; the PR and the worktree stay as they are for a retry. **Needs input** is only for an agent's question: when an agent reports a question the ticket, the epic and the code cannot answer, about product behavior or direction, or about something hard to undo or touching security, credentials or personal data, `harness-board needs-input N --question "<the question>" --evidence-file <tail of the agent's report>`, and end the turn. An agent's `Ruling:` line is not a question: it goes into the notes file and the stage continues. Never edit tests yourself, and merge only through step 9's `harness-pr land <P> --catch-up --loop`: never `gh pr merge` or any other merge of the PR.

## The ops path
An `ops` ticket updates records (Salesforce, Jotform, a project script) and changes no code: start made no branch or worktree and gave you `before_dir`. No test-author, red check, breaker, code review or PR; you work in the main checkout and write only into `before_dir`. A `needs-input` start follows step 1's branching first (waiting: stop; answers: they are the owner's OK or correction to the preview).
1. Read Change, Source of truth, Apply, Verify and Rollback. When the update needs a repository edit (code, a script, a mapping file), it becomes a normal ticket, before any write: (a) rewrite the body into the task template in a scratchpad file, `## Request`, `## Outline`, `## Definition of done`, `## Tests that must pass`, `## Context` (a normal run shows only those headings), with the repository edit as Outline steps and its tests, and Change, Source of truth, Apply, Verify and Rollback carried under Outline (the record update the code then runs) and Context (the rest, nothing dropped), then `gh issue edit N --body-file <file>`; (b) `harness-board retype N --type task --reason "<why>"`; (c) `harness-board needs-input N --question "#N needs a code change (<why>) and is now a task; confirm or correct the rewritten spec"`, and end the turn: his answer starts the normal run, never an orphaned in-progress ticket.
2. **Before-values, before any write**: query the records the Source of truth selects and save each one's id and the current value of every field the Change touches to `<before_dir>/before.json` (a resumed run saves `before-2.json` and so on, never overwriting).
3. **Preview**: the count and a before → after table (a sample of 20 when longer), in a scratchpad file. An update that deletes records or touches more than 25 records waits for the owner: `harness-board needs-input N --question "Apply this update? <count, fields, deletes>" --evidence-file <preview>`, and end the turn; the next run applies it once `answers` holds his OK. Any other update: post the preview with `harness-board comment N --body-file <preview>` and go on. (Auto mode still asks before any record delete in Salesforce or Jotform.)
4. **Apply** with the connector, API or script the Apply section names; a record that fails is noted and the rest go on.
5. **Read back** as Verify says.
6. **Results check**: one general-purpose Agent (`description: #N review`, `model: opus`, never Fable) given the Change section, the before-values and the read-back; it answers whether every record now matches the Change and lists each mismatch.
7. **Results**: `harness-board comment N --body-file <results.md>`, starting `**Results**`: the counts (selected, changed, unchanged, failed, skipped), each record changed with before → after (a sample past 50), the read-back, what failed or was skipped and why, the results check's verdict, and the before-values file path for a rollback. Then `harness-board status N in-review`, notify the owner (`osascript -e 'display notification "#N results ready" with title "Harness"'`), and end the turn: the owner checks and closes it.

## Report
Ticket and branch, PR URL and state (landed, with the merge commit `harness-pr land` printed and any canary or dirty-worktree lines; ready on a `manual-land` ticket, waiting for the owner's `/harness:land P`; parked, with the stage, the reason, the follow-up and what `harness-work dispatch --after N` launched; or the needs-input question), each stage with tier and attempts, the high and medium review findings fixed, the low ones left in the notes, the out-of-scope ones with their proposed tickets, and CI state. An ops ticket: the counts, the results check's verdict, the before-values path and where it ended. Short.

## Closing checklist
Before your last message, every item for your path holds: the first always; with no ticket number, the second; with a ticket number, one of the six end states after it, and with Landed or Waiting for the owner the findings item too. Otherwise the turn is not over: go back to the stage that has not finished.
