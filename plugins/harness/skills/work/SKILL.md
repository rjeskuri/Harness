# Work

Arguments: $ARGUMENTS

Ready tickets:
!`harness-board ready 2>/dev/null | head -20`

Every run of this skill is one turn, and a dispatched run (`claude --bg` by default, `claude -p` with `--api`) has no next turn: whatever is unfinished when the turn ends stays unfinished. Run every agent in the foreground, with `run_in_background: false` on each Agent call, and wait for its result before the next step; never launch an agent in the background. A call refused because the auto-mode classifier gave no verdict (`classifier:auto-mode:unavailable`) is an outage, not a denial, and ends no turn while steps remain: do the reads it was for with Read, Grep and Glob instead, retry the call once as it was, and when it is still refused go on with the steps that do not need it; once nothing else is left it is a tool failure no stage can fix (park, the paragraph after the steps). Every high or medium review finding on the files the ticket touched is fixed before `harness-pr ready`; a low finding goes into the PR notes for the owner, with no fix round; only a high or medium finding outside the ticket's files becomes a new ticket, and the PR body names it and says why. Every ticket the loop files (that one, a size-cap split, any other follow-up) is proposed: `harness-board task create ... --proposed --parent <epic>`, the epic being `parent` in `harness-board show N --json` (no `--parent` when there is none), and never with `--blocked-by N`, so it never blocks this ticket and the owner promotes it. With no ticket number the turn ends once `harness-work dispatch` has launched the runs, shown its `--dry-run` plan or found no ready tickets, and you have reported its output. With a ticket number the turn ends only when `harness-pr land` has merged the PR (step 10, at any risk), `harness-board park` has parked the ticket and `harness-work dispatch --after N` has run (a final failure, the paragraph after the steps), `harness-board needs-input` has posted an agent's question (or start found the ticket still waiting for an answer), or `harness-work start` has refused the ticket and you have reported why.

## No ticket number: dispatch
Run `harness-work dispatch $ARGUMENTS`. `--only N[,N...]` plans just the named tickets and `--after N` the ready tickets N unblocked, else the next ready one; a number after `--only`, `--after` or `--max` is that flag's value, not a ticket number. With `--dry-run` in the arguments, or more than ten ready tickets and none of `--max`, `--only` and `--after`, run it with `--dry-run`, show the plan and end the turn there: `/harness:work --max N` launches it. It starts a worktree per ready ticket (and per in-progress ticket whose last run ended early without a ready pull request: no PR, or only a draft) and launches a session for each. The subscription is the default. Without `--api` or `--venue headless`, every run is a background session on the subscription. `--api` in the arguments reaches `harness-work dispatch` as its alias for `--venue headless`, so the runs are headless and billed to the API key. With `--api` or `--venue headless`, dispatch is refused while the API budget is exhausted. Report what was launched, or "No ready tickets.", and that notifications arrive when a PR is ready or a ticket is parked or needs input. Do not work tickets in this session when dispatching.

## One ticket: the loop
You orchestrate; agents do the work; the tools keep the record. Work only in the worktree path that `harness-work start` prints, never in the main checkout. After start, read `harness-board tier N --json`: on every test-author, breaker and coder Agent call (retries and fix rounds included) pass its `tier` as `model`, and pass its `effort` as `effort` when that is not null. The project's `HARNESS_CODE_TIER` and `HARNESS_CODE_EFFORT` decide that tier and effort when it sets them, the labels otherwise. On escalation pass the tier and effort `harness-work attempt` names, counted from the tier and effort the stage ran at: `escalate opus` gives `model: opus` with no effort, `escalate opus xhigh` gives `model: opus` and `effort: xhigh`, and a stage already at Opus xhigh gets `park`, never a Fable run. The reviewer's model and effort come from `harness-board tier N --stage review --json` instead: pass its `tier` as `model`, and its `effort` when not null; the project's `HARNESS_REVIEW_TIER` decides that tier when set, the labels otherwise (Opus, at effort `xhigh` for a `risk:high` ticket; Fable when `HARNESS_REVIEW_TIER` is `fable`). `harness-pr ultra` prints that it ran nothing when the project sets `HARNESS_ULTRAREVIEW=off`; report that line. Give each Agent call the `description` `#N <stage>`, with N the ticket number (`harness-work cost` reads it): `#N tests` for the test-author (in a revise pass or a fix round too), `#N breaker` for the breaker, `#N code` for the coder until the first review, `#N review` for the first review, and `#N fix` for every coder or reviewer run after the first review (its findings, CI failures, ultrareview findings, the owner's comments); a retry or an escalation keeps its stage's name. The agents commit on the ticket branch and never push; you push (`harness-pr open` on the first pass, `git push` in the worktree after that). After every stage run `harness-work attempt N <stage> pass|fail` and do what it says: `retry` (same tier), `escalate <tier> [<effort>]`, `park` (park the ticket: the paragraph after the steps), or `done` (go on).

1. **Start**: `harness-work start N --json`; when it refuses the ticket (an epic, a closed ticket, open blockers), report its message and stop. Then read the ticket context it prints (request, outline, definition of done, tests, context, the epic's goal, blockers, recent comments). A dispatched prompt can carry a paragraph after the ticket number saying the previous run ended early with draft PR #P open and the worktree may hold uncommitted work: after start, read `git status` in the worktree, `harness-pr comments <P>` and the latest harness review (from `gh api --paginate repos/<owner>/<repo>/pulls/<P>/reviews`, the review with the newest `submitted_at` whose body carries the `<!-- harness-review -->` marker; its body holds the count and the findings not on a changed line, and the findings on changed lines are its inline comments at `gh api repos/<owner>/<repo>/pulls/<P>/reviews/<id>/comments`, with `<id>` the numeric `id`, not the `gh pr view` node id), then pick up at the step they point to, not at step 2 by default: committed or uncommitted source work goes to the step it belongs to, the high and medium harness review findings go to the coder as in step 6; a `harness-pr open` on that PR without `--review` or `--notes` keeps its Review summary and Notes section, so this session needs neither file to run it. A branch brought home from a cloud session (`harness-work cloud N`; no harness hook runs there) has its tests and source committed together and no red record (`harness-red status --worktree <path>` answers `No red run recorded`), so tests_first denies every source edit and `harness-red check` refuses: run `harness-red reprove --worktree <path>` before any local source edit or fix, and before merging main into the branch, never mid-merge (the merge stages main's own test changes, and reprove would count them as the branch's against the old merge base): a merge that already conflicted is aborted with `git merge --abort`, reprove runs, then the merge is redone and resolved. Red writes the record; when it refuses (the tests pass against main's code at the merge base, or prove nothing), the tests go back to the test-author as a green check does in step 2, except a refusal that names a dependency the temporary worktree could not import: point `HARNESS_TEST_CMD` at that environment by absolute path, as it says, and run reprove again. Branch on its `previous_status` (the status before start ran): `needs-input` with `answers` (all of the owner's replies since the newest needs-input question, oldest first): together they answer that question; continue with them (start moved the ticket to in-progress). `needs-input` with `waiting: true`: no answer yet and the ticket stays in needs-input; report that and stop. `in-review` (start leaves that label alone) with a PR: go to step 11. Read `flags` from `harness-board show N --json`: when it holds `no-tests` (docs or configuration only), say so and skip step 2 (the test-author and the red check) and step 3 (the breaker).
2. **Tests** (`harness:test-author`, stage `tests`). A `no-tests` ticket skips this step: go to step 4, where the coder works from the definition of done; the verify command must still pass and the review still runs. Otherwise: the context, the worktree, the test command (`HARNESS_TEST_CMD` from `.claude/settings.json`, or the detected default), and the ask for broad behavior tests first, each new or changed module under 180 s alone. Then `harness-red check --worktree <path>`. Red: continue. Green or no tests: the stage failed; send the author the tool's output.
3. **Break** (`harness:test-breaker`, stage `breaker`): this step runs only where an adversary matters: a `risk:high` ticket whose outline or tests change a hook's decision path (`plugins/harness/hooks/*` in the Harness repo, a project's own hooks elsewhere) or a tool that destroys or rewrites data (backup, land, revert, worktree remove). Every other ticket, a `risk:high` one touching neither included, goes from step 2 to step 4; say which it was. Otherwise: `harness-red scratch create --worktree <path>`; give it the scratch path, the test files, the definition of done and the test command. One round, never a second. `cheat passed` counts only for a constant or a cheat that special-cases the fixture inputs: record `harness-work attempt N breaker fail`, which answers `done`; any other cheat counts as `cheat failed`: record `harness-work attempt N breaker pass`. Either way the breaker's `Requirement:` lines go to the coder (step 4) and, as check items, to the reviewer (step 5); its `Not worth pinning:` list goes nowhere. Then go on to step 4: the breaker sends no ticket back to the test-author and never parks it. Remove the scratch with `harness-red scratch remove --worktree <path>` after the round.
4. **Code** (`harness:coder`, stage `code`): the context, worktree, test files, red run, test command and the own-tests command, `harness-red run --worktree <path>`, which runs only the ticket's own test files (the full suite runs in CI, step 7), and the breaker's `Requirement:` lines from step 3, if any, which it meets like the definition of done. It commits on the ticket branch when green and does not push. "A test looks wrong": back to the author with the coder's reasoning, one round, then red again. "Outgrown the size cap": file each part of the split it proposes as a proposed task (`harness-board task create --title T --body-file F --size S --risk R --proposed --parent <epic>`, the body in the task template's headings: Request, Outline, Definition of done, Tests that must pass, Context), then park with `--follow-up` naming them (`harness-board park N --reason "code: outgrew the size cap" --follow-up A,B`, the paragraph after the steps).
5. **Review** (`harness:reviewer`, stage `review`; `model` and `effort` from `harness-board tier N --stage review --json`: its `tier` as `model`, and its `effort` when not null; by the labels that is Opus, with `effort: xhigh` for a `risk:high` ticket, and `model: opus` with `effort: xhigh` once `harness-work attempt` says `escalate opus xhigh`): worktree, ticket context, the red run and the latest own-tests output (`harness-red run`), and the breaker's `Requirement:` lines from step 3, if any, as check items. Save its JSON array to a file in the scratchpad. Split it by severity and by the files the ticket touched (`git diff --name-only main...HEAD` in the worktree): the high and medium findings on those files go to `<findings.json>`, the fix file; each low finding, on or off those files, goes to the notes file under `### Low findings` and is still posted with the review (step 6); each high or medium finding outside those files becomes a proposed ticket (`harness-board task create --proposed --parent <epic>`, never `--blocked-by N`) only when it is a gap that a command the loop or the user actually runs would hit, noted with its reason for the PR body (step 6 puts it in the notes file under `### Out of scope`); any other gap is a `Not covered: <gap>` line in the notes file, under `### Out of scope`, with no ticket. The stage passes when the reviewer returned its findings array, whatever its length (an empty one included), and fails when it returned none usable. Record it as `harness-work attempt N review pass|fail --tier <tier> --effort <effort>`, with the tier and effort the review ran at (the `tier` and `effort` from `harness-board tier N --stage review --json`, or the ones the last `escalate` named; leave out `--effort` when the effort is null): the stage escalates from what it ran at, so an Opus review goes to `escalate opus xhigh` and an Opus xhigh review to `park`.
6. **PR and findings**: `harness-pr open N --worktree <path> --review <review.json> --json` (it pushes the branch; add `--notes <file>` for a second pass, low findings, out-of-scope findings or rulings: its markdown becomes a `## Notes` section that the Resolution repeats, so write each low finding under a `### Low findings` heading in that file, each high or medium out-of-scope finding with its new ticket and why under a `### Out of scope` heading, each `Ruling:` line the agents reported under a `### Rulings` heading, and no `## ` heading, which `open` refuses; `--notes` is needed whenever there are low findings or rulings), then `harness-pr review <P> --model <the reviewer's model> --findings <review.json>`, where `<review.json>` holds the high and medium findings on the ticket's files and every low finding, so the low ones are still posted with the review (an empty array posts "no findings"). A fix round runs only for high or medium findings on the ticket's files. One on a test file, which the coder may not edit, goes first to the test-author (`#N tests`), who changes the tests and leaves them uncommitted, its changes proven red as in step 11; then the coder (`#N fix`) fixes every other high and medium finding in `<findings.json>` and commits the test-author's changes with its own, in commits after that review (new tests a fix needs are proven red first, as in step 11; a fix round's test changes that pass at HEAD leave `harness-red status` at `current: no`, and `harness-red reprove --worktree <path>` re-proves them against main's code before the coder's next source edit), and runs its own tests with `harness-red run --worktree <path>`; push with `git push` in the worktree; the reviewer (`#N fix`) re-checks the branch, and its new findings are split as in step 5 and posted with `harness-pr review` the same way. Add the re-check's new low findings, the ones not already in the notes file, under its `### Low findings` heading, and run `harness-pr open` again with the updated `--notes`: on an open PR, `open` keeps the body's Review summary when `--review` is absent and its Notes section when `--notes` is absent, so pass a flag only to replace its section. After each fix round record `harness-work attempt N fix pass|fail --tier <the coder's tier>`: `pass` when the re-check found no high or medium finding on the ticket's files, `fail` when it found one. Do what it answers: `retry` means a second fix round on the new high and medium findings, and `park` means high or medium findings are still open after two rounds (park: the paragraph after the steps). At most two fix rounds, and `harness-work attempt` records them. A low finding gets no fix round: it stays in the notes file under `### Low findings`.
7. **CI** (stage `ci`): `harness-pr checks <P> --wait`, then `harness-work attempt N ci pass|fail`. CI runs the whole suite in a clean checkout; it is the full-suite gate, so the loop runs no local full verify. Failures: the coder (`#N fix`) fixes and commits them and runs `harness-red run --worktree <path>`; push with `git push` in the worktree and check again; at most two rounds, fewer when `harness-work attempt` answers `park` sooner (park: the paragraph after the steps).
8. **Ultrareview**, only when the ticket is `risk:high`: `harness-pr ultra <P> --post` (when the project's `HARNESS_ULTRAREVIEW` is `off` it prints one line and runs nothing; do not add `--force`). Its findings on the ticket's files go to the coder (`#N fix`) once, whatever their severity (one on a test file to the test-author first, as in step 6), and the rest become proposed tickets as in step 5; push its commits with `git push` in the worktree.
9. **Ready**: the head review, then `harness-pr ready <P>`.
    - **Head review**: `harness-pr land` refuses a head its latest harness review does not cover (`review the head again`; `--accept-findings` does not override it), and only clean merges of main may follow the reviewed commit, so the loop's land and the user's `/harness:land` both need it. Take that review's `commit_id` (the review found as in step 1), then in the worktree `git fetch origin` and `git rev-list --first-parent --parents <commit_id>..HEAD`: one line per commit after the review, newest first, each the commit and then its parents. No line: no review. Otherwise judge every line as `harness-pr land` does (`autoland.at_head`), whoever made the commit and whatever its message says, since `git log` shows a hand-resolved merge and a clean one alike: a line is a clean merge of main only when it has exactly three hashes `<c> <p1> <p2>`, `git merge-base --is-ancestor <p2> origin/main` exits 0, and `git merge-tree --write-tree <p1> <p2>` exits 0 (1 is a conflict, resolved by hand) with a first line equal to `git rev-parse <c>^{tree}`; and the last line's `<p1>` must be `<commit_id>`. Every line a clean merge of main: no review. Anything else (a CI fix from step 7, an ultrareview fix from step 8, a revise fix from step 11, a fix from step 10, a merge that conflicted or whose tree differs, a failing call): with the head pushed, the reviewer (`#N fix`, `model` and `effort` as in step 5) reviews the branch; split its findings as in step 5 and post them as in step 6, `harness-pr review <P> --model <the reviewer's model> --findings <review.json>` (an empty array posts "no findings", which covers the head too), and when it found new low or out-of-scope findings add them to the notes file and run `harness-pr open` again with `--notes`. It is the re-check of the fixes since that review: record `harness-work attempt N fix pass|fail --tier <the coder's tier>`, `pass` when it found no high or medium finding on the ticket's files, and do what it answers: on `retry` those findings go to a fix round as in step 6, whose re-check is posted the same way, and on `park` the ticket is parked. After a fix round, `harness-pr checks <P> --wait`; failures go to the coder as in step 7, and its commits get the head review again.
    - **Ready**: `harness-pr ready <P>`. It refuses while the latest harness review has high or medium findings and no commit after it, and names them: those go back to the coder as in step 6. Low findings do not stop it: they stay in the PR notes for the owner. It sets `status:in-review` and notifies the user. Then step 10.
10. **Land**, at any risk (a `risk:high` ticket has had its Opus xhigh review in step 5 and its ultrareview in step 8): `harness-pr land <P> --catch-up`, with no question to the owner first.
    - **The land**: `harness-pr land <P> --catch-up` as a plain command, with nothing around it: no pipe, redirect, `;`, `2>&1`, `echo` or `tail` (a `cd <main checkout> &&` in front is the one addition allowed), since a call with a part no allow rule covers goes to the auto-mode classifier, which has denied it as `[Merge Without Review]`; give the Bash call `timeout: 600000` and read the tool's own output. Leave `--rounds` and `--timeout` at their defaults (420 s of waiting a call, which leaves the merge and the canary room under the Bash tool's 600 s), and never add `--accept-findings` or `--discard`. When the branch is behind main, `--catch-up` merges origin/main into it in the worktree if that merge is clean, pushes it and waits for the checks at the new head, so the loop makes no merge of main of its own; then the land merges the PR, removes the worktree and branch (it runs from inside that worktree too), fast-forwards main, posts the Resolution, closes the ticket, checks the epic and runs the canary. Once it has merged (exit 0, an exit 1 naming the revert after a failed canary, or a stop at a dirty worktree), run nothing after it, a dispatch included (dispatching what it unblocked is the land's job), and report from its output; never add `--discard`.
    - **Exit 8** (the checks still pending at its deadline): run the same command again, unchanged; it merges nothing new while the branch is current and lands once the checks are green.
    - **A refusal** (exit 1, nothing merged; read its reason). A conflict with main, which names the conflicted files: on a branch with no red record that is not `no-tests` (`harness-red status --worktree <path>` answers `No red run recorded`, as on one brought home from a cloud session), first `harness-red reprove --worktree <path>`, as in step 1, its refusal handled as there; then the coder (`#N fix`) runs `git fetch origin`, merges origin/main in the worktree, resolves the conflicts and commits (when it cannot, as with a conflict in a test file, which it may not edit: park); then `harness-red run --worktree <path>`, `git push` in the worktree, `harness-pr checks <P> --wait` (red: CI rounds as in step 7), step 9's head review, and land again. Red checks, which it names (a catch-up merge it pushed stays): `harness-work attempt N ci fail`, a CI fix round as in step 7, step 9's head review, and land again. `review the head again`: step 9's head review, then land again. Any other refusal (still behind main after its catch-up rounds, open findings, a worktree that is dirty or missing, a failed read): park.
    - **Caps**: three re-runs on exit 8 in a row (four calls, about 28 minutes of waiting), two conflict resolutions, the CI rounds of step 7 and the fix rounds of step 6 as `harness-work attempt` counts them, and five land calls in all, the re-runs on exit 8 not counted. A cap reached: park, the land's last output as the evidence.
11. **Revise** (already in review): `harness-pr comments <P> --unresolved`; the owner's comments are the coder's task (`#N fix`; it commits); with none, go to step 9. Comments that need new tests go to the test-author (`#N tests`) first, who leaves them uncommitted; prove them red with `harness-red check --worktree <path> --base HEAD` (the branch already carries source changes, so the default base refuses, and `--base HEAD` sees only uncommitted changes); when it answers green (tests of behaviour the branch already has, which pass at HEAD), or `harness-red status --worktree <path>` says `current: no` once such tests are committed, prove them with `harness-red reprove --worktree <path>`, which runs the branch's test files against main's code at the merge base; then the coder commits them with its fix. The coder runs `harness-red run --worktree <path>` after its fixes. Push with `git push` in the worktree (the PR body needs no refresh; a `harness-pr open N` here without `--review` or `--notes` would keep its Review summary and Notes section); `harness-pr checks <P> --wait`; answer each thread with what changed (`gh pr comment <P>` with a short list); then step 9: the head review of the coder's commits, and `harness-pr ready <P>`, which sets `status:in-review` again and notifies the user (gh accepts a PR that is already ready). Then step 10, at any risk: the PR lands without waiting for the owner again, his addressed comments being his review (the head review still covers the head for `harness-pr land`).

**Park** on a final failure: `harness-work attempt` answered `park`, step 10 reached a cap or a refusal it does not handle, a size-cap split was filed (step 4), or a tool fails in a way no stage can fix (gh or git down, a refusal outside the loop's reach, a classifier that still gives no verdict). Write the tail of the failing output (the agent's last report, the checks' or the land's output) to a file in the scratchpad, run `harness-board park N --reason "<stage>: <what still fails>" --evidence-file <that file>` (`--follow-up A,B` for a split; without it the park files one proposed follow-up itself), then `harness-work dispatch --after N` (it launches the next ready ticket, if any), report both outputs, and end the turn; the PR and the worktree stay as they are for a retry. **Needs input** is only for an agent's question: when an agent reports a question the ticket, the epic and the code cannot answer, about product behavior or direction, or about something hard to undo or touching security, credentials or personal data, `harness-board needs-input N --question "<the question>" --evidence-file <tail of the agent's report>`, and end the turn. An agent's `Ruling:` line is not a question: it goes into the notes file and the stage continues. Never edit tests yourself, and merge only through step 10's `harness-pr land <P> --catch-up`: never `gh pr merge` or any other merge of the PR.

## Report
Ticket and branch, PR URL and state (landed, with the merge commit `harness-pr land` printed and any canary or dirty-worktree lines; parked, with the stage, the reason, the follow-up and what `harness-work dispatch --after N` launched; or the needs-input question), each stage with tier and attempts, the high and medium review findings fixed, the low ones left in the notes, the out-of-scope ones with their proposed tickets, and CI state. Short.

## Closing checklist
Before your last message, every item for your path holds: the first always; with no ticket number, the second; with a ticket number, one of the four end states after it, and with Landed the findings item too. Otherwise the turn is not over: go back to the stage that has not finished.

- Every agent ran in the foreground and you waited for its result; none was launched in the background.
- No ticket number: `harness-work dispatch` launched the runs, showed its `--dry-run` plan or said "No ready tickets.", and you reported its output.
- Landed: step 9's head review and `harness-pr ready <P>` have run, every commit step 10 added other than a clean merge of main had the head review, and a plain `harness-pr land <P> --catch-up` (no `--accept-findings`, no `--discard`), run again on exit 8 within step 10's caps, merged the PR, whatever its risk; your report names the merge commit, and the lines of a canary revert or of a land that stopped at a dirty worktree.
- Parked: `harness-board park N` has run with the stage, what still fails and its evidence (a final `park` from `harness-work attempt`, a step 10 cap or refusal it does not handle, a size-cap split with its proposed tasks as `--follow-up`, or a tool failure no stage can fix), then `harness-work dispatch --after N`, and you reported both outputs.
- Needs input: `harness-board needs-input N` has posted an agent's question with its evidence, or start found the ticket still waiting for an answer.
- Start refused: `harness-work start` refused the ticket (an epic, a closed ticket, open blockers) and you reported its message.
- Findings: every high and medium review finding on the ticket's files was fixed in a commit after the review that posted it; each low finding is in the PR notes under `### Low findings`, with no fix round; each high or medium finding outside them is a proposed ticket that the PR body names with the reason, when a command the loop or the user runs would hit it, and a `Not covered:` line in the notes otherwise.
