# Work

Arguments: $ARGUMENTS

Ready tickets:
!`harness-board ready 2>/dev/null | head -20`

Every run of this skill is one turn, and a dispatched run (`claude -p`) has no next turn: whatever is unfinished when the turn ends stays unfinished. Run every agent in the foreground, with `run_in_background: false` on each Agent call, and wait for its result before the next step; never launch an agent in the background. Every review finding on the files the ticket touched is fixed before `harness-pr ready`, whatever its severity; only a finding outside the ticket's files becomes a new ticket, and the PR body names it and says why. With no ticket number the turn ends once `harness-work dispatch` has launched the runs, shown its `--dry-run` plan or found no ready tickets, and you have reported its output. With a ticket number the turn ends only when `harness-pr ready` has run, `harness-board needs-input` has posted the question (or start found the ticket still waiting for an answer), `harness-work start` has refused the ticket and you have reported why, or `harness-work attempt` has recorded the final failure and its question is posted.

## No ticket number: dispatch
Run `harness-work dispatch $ARGUMENTS`. With `--dry-run` in the arguments, or more than three ready tickets and no `--max`, run it with `--dry-run`, show the plan and end the turn there: `/harness:work --max N` launches it. It starts a worktree per ready ticket (and per in-progress ticket whose last run ended early without a ready pull request: no PR, or only a draft) and launches a headless run billed to the API key, or a background session on the subscription when the API budget is exhausted. Report what was launched, or "No ready tickets.", and that notifications arrive when a PR is ready or a ticket needs input. Do not work tickets in this session when dispatching.

## One ticket: the loop
You orchestrate; agents do the work; the tools keep the record. Work only in the worktree path that `harness-work start` prints, never in the main checkout. Pass `model: <tier>` on every Agent call: the tier from `harness-board tier N`, or one tier up on escalation (sonnet, opus, fable). When escalating or reviewing on Fable, pass `model: fable` and `effort: xhigh` on the Agent call. The agents commit on the ticket branch and never push; you push (`harness-pr open` on the first pass, `git push` in the worktree after that). After every stage run `harness-work attempt N <stage> pass|fail` and do what it says: `retry` (same tier), `escalate <tier>`, or `needs-input` (go to the paragraph after the steps).

1. **Start**: `harness-work start N --json`; when it refuses the ticket (an epic, a closed ticket, open blockers), report its message and stop. Then read the ticket context it prints (request, outline, definition of done, tests, context, the epic's goal, blockers, recent comments). A dispatched prompt can carry a paragraph after the ticket number saying the previous run ended early with draft PR #P open and uncommitted work in the worktree: after start, read `git status` in the worktree, `harness-pr comments <P>` and the latest harness review (`gh pr view <P> --json reviews`, the newest body carrying the `<!-- harness-review -->` marker), then pick up at the step they point to, not at step 2 by default: committed or uncommitted source work goes to the step it belongs to, harness review findings go to the coder as in step 6. Branch on its `previous_status` (the status before start ran): `needs-input` with `answers` (all of the owner's replies since the newest needs-input question, oldest first): together they answer that question; continue with them (start moved the ticket to in-progress). `needs-input` with `waiting: true`: no answer yet and the ticket stays in needs-input; report that and stop. `in-review` (start leaves that label alone) with a PR: go to step 10. Read `flags` from `harness-board show N --json`: when it holds `no-tests` (docs or configuration only), say so and skip step 2 (the test-author and the red check) and step 3 (the breaker).
2. **Tests** (`harness:test-author`, stage `tests`). A `no-tests` ticket skips this step: go to step 4, where the coder works from the definition of done; the verify command must still pass and the review still runs. Otherwise: the context, the worktree, the test command (`HARNESS_TEST_CMD` from `.claude/settings.json`, or the detected default), and the ask for broad behavior tests first. Then `harness-red check --worktree <path>`. Red: continue. Green or no tests: the stage failed; send the author the tool's output.
3. **Break** (`harness:test-breaker`, stage `breaker`): `harness-red scratch create --worktree <path>`; give it the scratch path, the test files, the definition of done and the test command. `cheat passed`: back to the author with the breaker's suggestions (step 2 again, including `harness-red check`), at most two rounds, then continue and note it for the PR. `harness-red scratch remove --worktree <path>` either way.
4. **Code** (`harness:coder`, stage `code`): the context, worktree, test files, red run, test command and `CLAUDE_VERIFY_CMD`. It commits on the ticket branch when green and does not push. "A test looks wrong": back to the author with the coder's reasoning, one round, then red again. "Outgrown the size cap": `harness-board needs-input` with the split it proposes, and stop.
5. **Review** (`harness:reviewer`, stage `review`): worktree, ticket context, red and verify output. Save its JSON array to a file in the scratchpad. Split it by the files the ticket touched (`git diff --name-only main...HEAD` in the worktree): the findings on them go to `<findings.json>`, whatever their severity; each finding outside them becomes a new ticket (`harness-board task create`, under the ticket's epic), noted with its reason for the PR body (step 6 puts it in the notes file).
6. **PR and findings**: `harness-pr open N --worktree <path> --verify-log <file> --review <findings.json> --json` (it pushes the branch; add `--notes <file>` for a second pass or out-of-scope findings: its markdown becomes a `## Notes` section that the Resolution repeats, so write each out-of-scope finding, its new ticket and why under a `### Out of scope` heading in that file, and no `## ` heading, which `open` refuses), then `harness-pr review <P> --findings <findings.json>` (an empty array posts "no findings"). With findings, the coder fixes every one of them in commits after that review (new tests a fix needs are proven red first, as in step 10); push with `git push` in the worktree; the reviewer re-checks the branch, and its new findings are split and posted with `harness-pr review` the same way. At most two fix rounds; findings still open after them fail the stage.
7. **CI** (stage `ci`): `harness-pr checks <P> --wait`. Failures: the coder fixes and commits them; push with `git push` in the worktree and check again; at most two rounds.
8. **Ultrareview**, only when the ticket is `risk:high`: `harness-pr ultra <P> --post`. Its findings on the ticket's files go to the coder once, whatever their severity, and the rest become new tickets as in step 5; push its commits with `git push` in the worktree.
9. **Ready**: `harness-pr ready <P>`. It refuses while the latest harness review has findings and no commit after it, and names them: those go back to the coder as in step 6. It sets `status:in-review` and notifies the user. Stop.
10. **Revise** (already in review): `harness-pr comments <P> --unresolved`; the owner's comments are the coder's task (it commits). Comments that need new tests go to the test-author first, who leaves them uncommitted; prove them red with `harness-red check --worktree <path> --base HEAD` (the branch already carries source changes, so the default base refuses, and `--base HEAD` sees only uncommitted changes); then the coder commits them with its fix. Push with `git push` in the worktree; `harness-pr checks <P> --wait`; answer each thread with what changed (`gh pr comment <P>` with a short list); then `harness-pr ready <P>`, which sets `status:in-review` again and notifies the user (gh accepts a PR that is already ready).

When a stage reaches `needs-input`, an agent reports a question the ticket, the epic and the code cannot answer, or a tool fails in a way no stage can fix (gh or git down, a refusal outside the loop's reach): `harness-board needs-input N --question "<the question or blocker>" --evidence-file <tail of the failing output>`, and stop. Never loosen a test, never edit tests yourself, never push to main, never merge: landing is the user's `/harness:land`.

## Report
Ticket and branch, PR URL and state, each stage with tier and attempts, review findings fixed and the out-of-scope ones with their new tickets, CI state, and anything the user must decide. Short.

## Closing checklist
Before your last message, every item for your path holds: the first always; with no ticket number, the second; with a ticket number, one of the four end states after it, and with Ready the findings item too. Otherwise the turn is not over: go back to the stage that has not finished.

- Every agent ran in the foreground and you waited for its result; none was launched in the background.
- No ticket number: `harness-work dispatch` launched the runs, showed its `--dry-run` plan or said "No ready tickets.", and you reported its output.
- Ready: `harness-pr ready <P>` has run and the ticket is `status:in-review`.
- Needs input: `harness-board needs-input N` has posted the question with its evidence (an agent's question, a size-cap split, or a tool failure the loop cannot recover from), or start found the ticket still waiting for an answer.
- Final failure: `harness-work attempt` answered `needs-input` after the stage's last failure, and that question is posted.
- Start refused: `harness-work start` refused the ticket (an epic, a closed ticket, open blockers) and you reported its message.
- Findings: every review finding on the ticket's files was fixed in a commit after the review that posted it, whatever its severity, and each finding outside them is a new ticket that the PR body names with the reason.
