# Work

Arguments: $ARGUMENTS

Ready tickets:
!`harness-board ready 2>/dev/null | head -20`

Every run of this skill is one turn, and a dispatched run (`claude --bg` by default, `claude -p` with `--api`) has no next turn: whatever is unfinished when the turn ends stays unfinished. Run every agent in the foreground, with `run_in_background: false` on each Agent call, and wait for its result before the next step; never launch an agent in the background. Every high or medium review finding on the files the ticket touched is fixed before `harness-pr ready`; a low finding goes into the PR notes for the owner, with no fix round; only a high or medium finding outside the ticket's files becomes a new ticket, and the PR body names it and says why. With no ticket number the turn ends once `harness-work dispatch` has launched the runs, shown its `--dry-run` plan or found no ready tickets, and you have reported its output. With a ticket number the turn ends only when `harness-pr land` has merged the PR (a `risk:low` ticket, step 10), `harness-pr ready` has run and step 10 left the PR at ready (a ticket that is not `risk:low`, or a merge of main or a land that failed, reported), `harness-board needs-input` has posted the question (or start found the ticket still waiting for an answer), `harness-work start` has refused the ticket and you have reported why, or `harness-work attempt` has recorded the final failure and its question is posted.

## No ticket number: dispatch
Run `harness-work dispatch $ARGUMENTS`. With `--dry-run` in the arguments, or more than ten ready tickets and no `--max`, run it with `--dry-run`, show the plan and end the turn there: `/harness:work --max N` launches it. It starts a worktree per ready ticket (and per in-progress ticket whose last run ended early without a ready pull request: no PR, or only a draft) and launches a session for each. The subscription is the default. Without `--api` or `--venue headless`, every run is a background session on the subscription. `--api` in the arguments reaches `harness-work dispatch` as its alias for `--venue headless`, so the runs are headless and billed to the API key. With `--api` or `--venue headless`, dispatch is refused while the API budget is exhausted. Report what was launched, or "No ready tickets.", and that notifications arrive when a PR is ready or a ticket needs input. Do not work tickets in this session when dispatching.

## One ticket: the loop
You orchestrate; agents do the work; the tools keep the record. Work only in the worktree path that `harness-work start` prints, never in the main checkout. After start, read `harness-board tier N --json`: on every test-author, breaker and coder Agent call (retries and fix rounds included) pass its `tier` as `model`, and pass its `effort` as `effort` when that is not null. The project's `HARNESS_CODE_TIER` and `HARNESS_CODE_EFFORT` decide that tier and effort when it sets them, the labels otherwise. On escalation pass the tier and effort `harness-work attempt` names, counted from the tier and effort the stage ran at: `escalate opus` gives `model: opus` with no effort, `escalate opus xhigh` gives `model: opus` and `effort: xhigh`, and a stage already at Opus xhigh gets `needs-input`, never a Fable run. The reviewer's model and effort come from `harness-board tier N --stage review --json` instead: pass its `tier` as `model`, and its `effort` when not null; the project's `HARNESS_REVIEW_TIER` decides that tier when set, the labels otherwise (Opus, at effort `xhigh` for a `risk:high` ticket; Fable when `HARNESS_REVIEW_TIER` is `fable`). `harness-pr ultra` prints that it ran nothing when the project sets `HARNESS_ULTRAREVIEW=off`; report that line. Give each Agent call the `description` `#N <stage>`, with N the ticket number (`harness-work cost` reads it): `#N tests` for the test-author (in a revise pass too), `#N breaker` for the breaker, `#N code` for the coder until the first review, `#N review` for the first review, and `#N fix` for every coder or reviewer run after the first review (its findings, CI failures, ultrareview findings, the owner's comments); a retry or an escalation keeps its stage's name. The agents commit on the ticket branch and never push; you push (`harness-pr open` on the first pass, `git push` in the worktree after that). After every stage run `harness-work attempt N <stage> pass|fail` and do what it says: `retry` (same tier), `escalate <tier> [<effort>]`, or `needs-input` (go to the paragraph after the steps).

1. **Start**: `harness-work start N --json`; when it refuses the ticket (an epic, a closed ticket, open blockers), report its message and stop. Then read the ticket context it prints (request, outline, definition of done, tests, context, the epic's goal, blockers, recent comments). A dispatched prompt can carry a paragraph after the ticket number saying the previous run ended early with draft PR #P open and the worktree may hold uncommitted work: after start, read `git status` in the worktree, `harness-pr comments <P>` and the latest harness review (from `gh api --paginate repos/<owner>/<repo>/pulls/<P>/reviews`, the review with the newest `submitted_at` whose body carries the `<!-- harness-review -->` marker; its body holds the count and the findings not on a changed line, and the findings on changed lines are its inline comments at `gh api repos/<owner>/<repo>/pulls/<P>/reviews/<id>/comments`, with `<id>` the numeric `id`, not the `gh pr view` node id), then pick up at the step they point to, not at step 2 by default: committed or uncommitted source work goes to the step it belongs to, the high and medium harness review findings go to the coder as in step 6; a `harness-pr open` on that PR without `--review` or `--notes` keeps its Review summary and Notes section, so this session needs neither file to run it. A branch brought home from a cloud session (`harness-work cloud N`; no harness hook runs there) has its tests and source committed together and no red record (`harness-red status --worktree <path>` answers `No red run recorded`), so tests_first denies every source edit and `harness-red check` refuses: run `harness-red reprove --worktree <path>` before any local source edit or fix, and before merging main into the branch, never mid-merge (the merge stages main's own test changes, and reprove would count them as the branch's against the old merge base): a merge that already conflicted is aborted with `git merge --abort`, reprove runs, then the merge is redone and resolved. Red writes the record; when it refuses (the tests pass against main's code at the merge base, or prove nothing), the tests go back to the test-author as a green check does in step 2, except a refusal that names a dependency the temporary worktree could not import: point `HARNESS_TEST_CMD` at that environment by absolute path, as it says, and run reprove again. Branch on its `previous_status` (the status before start ran): `needs-input` with `answers` (all of the owner's replies since the newest needs-input question, oldest first): together they answer that question; continue with them (start moved the ticket to in-progress). `needs-input` with `waiting: true`: no answer yet and the ticket stays in needs-input; report that and stop. `in-review` (start leaves that label alone) with a PR: go to step 11. Read `flags` from `harness-board show N --json`: when it holds `no-tests` (docs or configuration only), say so and skip step 2 (the test-author and the red check) and step 3 (the breaker).
2. **Tests** (`harness:test-author`, stage `tests`). A `no-tests` ticket skips this step: go to step 4, where the coder works from the definition of done; the verify command must still pass and the review still runs. Otherwise: the context, the worktree, the test command (`HARNESS_TEST_CMD` from `.claude/settings.json`, or the detected default), and the ask for broad behavior tests first. Then `harness-red check --worktree <path>`. Red: continue. Green or no tests: the stage failed; send the author the tool's output.
3. **Break** (`harness:test-breaker`, stage `breaker`): this step runs only where an adversary matters: a `risk:high` ticket whose outline or tests change a hook's decision path (`plugins/harness/hooks/*` in the Harness repo, a project's own hooks elsewhere) or a tool that destroys or rewrites data (backup, land, revert, worktree remove). Every other ticket, a `risk:high` one touching neither included, goes from step 2 to step 4; say which it was. Otherwise: `harness-red scratch create --worktree <path>`; give it the scratch path, the test files, the definition of done and the test command. One round, never a second. `cheat passed` counts only for a constant or a cheat that special-cases the fixture inputs: record `harness-work attempt N breaker fail`, which answers `done`; any other cheat counts as `cheat failed`: record `harness-work attempt N breaker pass`. Either way the breaker's `Requirement:` lines go to the coder (step 4) and, as check items, to the reviewer (step 5); its `Not worth pinning:` list goes nowhere. Then go on to step 4: the breaker sends no ticket back to the test-author and never stops on needs-input. Remove the scratch with `harness-red scratch remove --worktree <path>` after the round.
4. **Code** (`harness:coder`, stage `code`): the context, worktree, test files, red run, test command and the own-tests command, `harness-red run --worktree <path>`, which runs only the ticket's own test files (the full suite runs in CI, step 7), and the breaker's `Requirement:` lines from step 3, if any, which it meets like the definition of done. It commits on the ticket branch when green and does not push. "A test looks wrong": back to the author with the coder's reasoning, one round, then red again. "Outgrown the size cap": `harness-board needs-input` with the split it proposes, and stop.
5. **Review** (`harness:reviewer`, stage `review`; `model` and `effort` from `harness-board tier N --stage review --json`: its `tier` as `model`, and its `effort` when not null; by the labels that is Opus, with `effort: xhigh` for a `risk:high` ticket, and `model: opus` with `effort: xhigh` once `harness-work attempt` says `escalate opus xhigh`): worktree, ticket context, the red run and the latest own-tests output (`harness-red run`), and the breaker's `Requirement:` lines from step 3, if any, as check items. Save its JSON array to a file in the scratchpad. Split it by severity and by the files the ticket touched (`git diff --name-only main...HEAD` in the worktree): the high and medium findings on those files go to `<findings.json>`, the fix file; each low finding, on or off those files, goes to the notes file under `### Low findings` and is still posted with the review (step 6); each high or medium finding outside those files becomes a new ticket (`harness-board task create`, under the ticket's epic), noted with its reason for the PR body (step 6 puts it in the notes file under `### Out of scope`). The stage passes when the reviewer returned its findings array, whatever its length (an empty one included), and fails when it returned none usable. Record it as `harness-work attempt N review pass|fail --tier <tier> --effort <effort>`, with the tier and effort the review ran at (the `tier` and `effort` from `harness-board tier N --stage review --json`, or the ones the last `escalate` named; leave out `--effort` when the effort is null): the stage escalates from what it ran at, so an Opus review goes to `escalate opus xhigh` and an Opus xhigh review to `needs-input`.
6. **PR and findings**: `harness-pr open N --worktree <path> --review <review.json> --json` (it pushes the branch; add `--notes <file>` for a second pass, low findings, out-of-scope findings or rulings: its markdown becomes a `## Notes` section that the Resolution repeats, so write each low finding under a `### Low findings` heading in that file, each high or medium out-of-scope finding with its new ticket and why under a `### Out of scope` heading, each `Ruling:` line the agents reported under a `### Rulings` heading, and no `## ` heading, which `open` refuses; `--notes` is needed whenever there are low findings or rulings), then `harness-pr review <P> --model <the reviewer's model> --findings <review.json>`, where `<review.json>` holds the high and medium findings on the ticket's files and every low finding, so the low ones are still posted with the review (an empty array posts "no findings"). A fix round runs only for high or medium findings on the ticket's files: the coder (`#N fix`) fixes every high and medium finding in `<findings.json>` in commits after that review (new tests a fix needs are proven red first, as in step 11; a fix round's test changes that pass at HEAD leave `harness-red status` at `current: no`, and `harness-red reprove --worktree <path>` re-proves them against main's code before the coder's next source edit), and runs its own tests with `harness-red run --worktree <path>`; push with `git push` in the worktree; the reviewer (`#N fix`) re-checks the branch, and its new findings are split as in step 5 and posted with `harness-pr review` the same way. Add the re-check's new low findings, the ones not already in the notes file, under its `### Low findings` heading, and run `harness-pr open` again with the updated `--notes`: on an open PR, `open` keeps the body's Review summary when `--review` is absent and its Notes section when `--notes` is absent, so pass a flag only to replace its section. After each fix round record `harness-work attempt N fix pass|fail --tier <the coder's tier>`: `pass` when the re-check found no high or medium finding on the ticket's files, `fail` when it found one. Do what it answers: `retry` means a second fix round on the new high and medium findings, and `needs-input` means high or medium findings are still open after two rounds (go to the paragraph after the steps). At most two fix rounds, and `harness-work attempt` records them. A low finding gets no fix round: it stays in the notes file under `### Low findings`.
7. **CI** (stage `ci`): `harness-pr checks <P> --wait`. CI runs the whole suite in a clean checkout; it is the full-suite gate, so the loop runs no local full verify. Failures: the coder (`#N fix`) fixes and commits them and runs `harness-red run --worktree <path>`; push with `git push` in the worktree and check again; at most two rounds.
8. **Ultrareview**, only when the ticket is `risk:high`: `harness-pr ultra <P> --post` (when the project's `HARNESS_ULTRAREVIEW` is `off` it prints one line and runs nothing; do not add `--force`). Its findings on the ticket's files go to the coder (`#N fix`) once, whatever their severity, and the rest become new tickets as in step 5; push its commits with `git push` in the worktree.
9. **Ready**: the head review, then `harness-pr ready <P>`.
    - **Head review**: `harness-pr land` refuses a head its latest harness review does not cover (`review the head again`; `--accept-findings` does not override it), and only clean merges of main may follow the reviewed commit, so the loop's land and the user's `/harness:land` both need it. Take that review's `commit_id` (the review found as in step 1), then in the worktree `git fetch origin` and `git rev-list --first-parent --parents <commit_id>..HEAD`: one line per commit after the review, newest first, each the commit and then its parents. No line: no review. Otherwise judge every line as `harness-pr land` does (`autoland.at_head`), whoever made the commit and whatever its message says, since `git log` shows a hand-resolved merge and a clean one alike: a line is a clean merge of main only when it has exactly three hashes `<c> <p1> <p2>`, `git merge-base --is-ancestor <p2> origin/main` exits 0, and `git merge-tree --write-tree <p1> <p2>` exits 0 (1 is a conflict, resolved by hand) with a first line equal to `git rev-parse <c>^{tree}`; and the last line's `<p1>` must be `<commit_id>`. Every line a clean merge of main: no review. Anything else (a CI fix from step 7, an ultrareview fix from step 8, a revise fix from step 11, a fix from step 10, a merge that conflicted or whose tree differs, a failing call): with the head pushed, the reviewer (`#N fix`, `model` and `effort` as in step 5) reviews the branch; split its findings as in step 5 and post them as in step 6, `harness-pr review <P> --model <the reviewer's model> --findings <review.json>` (an empty array posts "no findings", which covers the head too), and when it found new low or out-of-scope findings add them to the notes file and run `harness-pr open` again with `--notes`. It is the re-check of the fixes since that review: record `harness-work attempt N fix pass|fail --tier <the coder's tier>`, `pass` when it found no high or medium finding on the ticket's files, and do what it answers: on `retry` those findings go to a fix round as in step 6, whose re-check is posted the same way. After a fix round, `harness-pr checks <P> --wait`; failures go to the coder as in step 7, and its commits get the head review again.
    - **Ready**: `harness-pr ready <P>`. It refuses while the latest harness review has high or medium findings and no commit after it, and names them: those go back to the coder as in step 6. Low findings do not stop it: they stay in the PR notes for the owner. It sets `status:in-review` and notifies the user. Then step 10.
10. **Land**: read `risk` from `harness-board show N --json`. Anything but `low` (`high`, or null for no risk label): stop at ready; the user lands it with `/harness:land`. `low`: bring the branch current with main, then land it.
    - **Current with main**: in the worktree, `git fetch origin`, then `git rev-list --count HEAD..origin/main`. `0`: go to the land. Otherwise, a branch with no red record that is not `no-tests` (`harness-red status --worktree <path>` answers `No red run recorded`, as on one brought home from a cloud session) first runs `harness-red reprove --worktree <path>` before the merge, as in step 1, its refusal handled as there. Then `git merge --no-edit origin/main` in the worktree; when it stops on a conflict, `git merge --abort` there, and the coder (`#N fix`) merges origin/main, resolves the conflicts and commits (when it cannot, as with a conflict in a test file, which it may not edit, report its reason and stop at ready). Then `harness-red run --worktree <path>`, push with `git push` in the worktree, and `harness-pr checks <P> --wait`; own tests or checks red: the coder (`#N fix`) fixes them as in step 7, at most two rounds. Then step 9's head review before the land: it skips a merge `git merge-tree` shows clean and reviews anything else this committed (the coder's resolution or a fix).
    - **The land**: `harness-pr land <P>` as a plain command, with nothing around it: no pipe, redirect, `;`, `2>&1`, `echo` or `tail` (a `cd <main checkout> &&` in front is the one addition allowed), since a call with a part no allow rule covers goes to the auto-mode classifier, which has denied it as `[Merge Without Review]`; read the tool's own output. Never add `--accept-findings` or `--discard`. It merges, then removes the worktree and branch (it runs from inside that worktree too), fast-forwards main, posts the Resolution, closes the ticket and checks the epic; once it has merged, run nothing after it and report from its output.
    - **A refusal** because the PR conflicts with main or is behind it: bring the branch current once more as above, then `harness-pr land <P>` once more. A refusal saying `review the head again`: the head review of step 9, then `harness-pr land <P>` once more. Any other refusal, or a second refusal: report it and stop at ready (the ticket stays `status:in-review`). A land that merged but stopped at a dirty worktree: report its lines and stop; never add `--discard`.
11. **Revise** (already in review): `harness-pr comments <P> --unresolved`; the owner's comments are the coder's task (`#N fix`; it commits); with none, go to step 9. Comments that need new tests go to the test-author (`#N tests`) first, who leaves them uncommitted; prove them red with `harness-red check --worktree <path> --base HEAD` (the branch already carries source changes, so the default base refuses, and `--base HEAD` sees only uncommitted changes); when it answers green (tests of behaviour the branch already has, which pass at HEAD), or `harness-red status --worktree <path>` says `current: no` once such tests are committed, prove them with `harness-red reprove --worktree <path>`, which runs the branch's test files against main's code at the merge base; then the coder commits them with its fix. The coder runs `harness-red run --worktree <path>` after its fixes. Push with `git push` in the worktree (the PR body needs no refresh; a `harness-pr open N` here without `--review` or `--notes` would keep its Review summary and Notes section); `harness-pr checks <P> --wait`; answer each thread with what changed (`gh pr comment <P>` with a short list); then step 9: the head review of the coder's commits, and `harness-pr ready <P>`, which sets `status:in-review` again and notifies the user (gh accepts a PR that is already ready). Then step 10: a `risk:low` PR lands without waiting for the owner again, his addressed comments being his review (the head review still covers the head for `harness-pr land`); any other stays at ready.

When a stage reaches `needs-input`, an agent reports a question the ticket, the epic and the code cannot answer that is about product behavior, is hard to undo, or touches security, credentials or personal data, or a tool fails in a way no stage can fix (gh or git down, a refusal outside the loop's reach): `harness-board needs-input N --question "<the question or blocker>" --evidence-file <tail of the failing output>`, and stop. An agent's `Ruling:` line is not a question: it goes into the notes file and the stage continues. Never edit tests yourself, and merge only through step 10's `harness-pr land <P>`: never `gh pr merge` or any other merge of the PR; a PR step 10 does not land waits at ready for the user's `/harness:land`.

## Report
Ticket and branch, PR URL and state (landed, with the merge commit `harness-pr land` printed; or at ready, and why: not `risk:low`, a merge of main that failed, or the land's refusal), each stage with tier and attempts, the high and medium review findings fixed, the low ones left in the notes, the out-of-scope ones with their new tickets, CI state, and anything the user must decide. Short.

## Closing checklist
Before your last message, every item for your path holds: the first always; with no ticket number, the second; with a ticket number, one of the five end states after it, and with Landed or Ready the findings item too. Otherwise the turn is not over: go back to the stage that has not finished.

- Every agent ran in the foreground and you waited for its result; none was launched in the background.
- No ticket number: `harness-work dispatch` launched the runs, showed its `--dry-run` plan or said "No ready tickets.", and you reported its output.
- Landed: the ticket is `risk:low`, step 9's head review and `harness-pr ready <P>` have run, the branch was current with origin/main and green, any commit step 10 made but a clean merge had the head review, and a plain `harness-pr land <P>` (no `--accept-findings`, no `--discard`) merged the PR; your report names the merge commit, and the lines of a land that stopped at a dirty worktree.
- Ready: step 9's head review and `harness-pr ready <P>` have run and the ticket is `status:in-review`, and step 10 left it there: the ticket is not `risk:low`, or the branch could not be made current or the land was refused, and you reported why.
- Needs input: `harness-board needs-input N` has posted the question with its evidence (an agent's question, a size-cap split, or a tool failure the loop cannot recover from), or start found the ticket still waiting for an answer.
- Final failure: `harness-work attempt` answered `needs-input` after the stage's last failure, and that question is posted.
- Start refused: `harness-work start` refused the ticket (an epic, a closed ticket, open blockers) and you reported its message.
- Findings: every high and medium review finding on the ticket's files was fixed in a commit after the review that posted it; each low finding is in the PR notes under `### Low findings`, with no fix round; each high or medium finding outside them is a new ticket that the PR body names with the reason.
