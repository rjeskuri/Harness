# Research notes: how a background session reports the subscription usage limit

Gathered 2026-11-19 for #164 (outline step 3), with Claude Code 2.1.328 installed. Sources, all local and read-only: the transcripts under `~/.claude/projects/` of the 2026-10-23 and 2026-10-24 limit hits (written by 2.1.309 and 2.1.310), the job files under `~/.claude/jobs/`, the run records under `~/.claude/harness/runs/`, `claude agents --json [--all]`, and the 2.1.328 binary (`~/.local/share/claude/versions/2.1.328`, read with grep and python). No session was started and nothing was sent.

  The separator is U+00B7 and the apostrophe is ASCII.
- **Every hit on this Mac** (19 main transcripts, all `five_hour`): 2026-10-23T05:45-05:47Z, 4 jotform-glow-sync bg runs (2.1.309), "You've hit your session limit · resets 3:20pm (Asia/Tokyo)", `resetsAt` 1792736400 = 06:20Z; 2026-10-24T10:03-10:36Z, 14 bg runs in Harness and jotform-glow-sync and one interactive session (2.1.310), "... resets 8:40pm (Asia/Tokyo)", `resetsAt` 1792842000 = 11:40Z. Text and epoch agree. No weekly or per-model refusal was recorded, and no "Claude AI usage limit reached|<epoch>" (absent from every transcript and not a template in 2.1.328).
- **Fable variant (a different kind).** 7 subagent entries, 2026-10-24T09:36-09:49Z: "You've reached your Fable limit. Run /usage-credits to continue or switch models with /model.", `apiError` `model_requires_usage_credits`, `error` `rate_limit`, 429, no `apiErrorParams`, no reset.
- **The binary documents the fields** (2.1.328 message schema): `api_error` is "for consumers that key on the cause instead of the message text (the text stays the fallback and may change)"; "usage_limit_reached: ... a plan limit (session, weekly or per-model) or a spend cap on usage credits; api_error_params.rate_limit_info says which and when it resets"; "It is that refusal's record and is never updated, so compare resetsAt with the clock before calling the limit current."
- **The text (2.1.328):** `` `You've hit your ${name}${" \xB7 resets " + time}${" \xB7 progress saved" behind a flag}` ``. Names: `five_hour` "5-hour limit", `seven_day` "weekly limit", `seven_day_opus` "Opus limit", `seven_day_sonnet` "Sonnet limit", `seven_day_overage_included` "Fable limit", `overage` "usage credit limit"; fallbacks "You've hit your usage limit", "You've hit your limit". Versions 2.1.325 to 2.1.328 all say "5-hour limit" where 2.1.310 wrote "session limit": key on the fields, not the words.
- **Reset-time format** (2.1.328 formatter): within 24 h, en-US hour and minutes (minutes dropped on the hour), "pm" lower case, then the IANA zone: "8:40pm (Asia/Tokyo)", "8pm (Asia/Tokyo)". Further out it adds month and day, and the year when it differs: "Oct 29, 8pm (Asia/Tokyo)", "Dec 28, 2027, 10:20pm (Asia/Tokyo)" (these two from the formatter run in node, not seen in a transcript). The zone is the configured one, otherwise the system zone (Asia/Tokyo here).
- **Place in the file.** The refusal was never the last line: 1 to 8 lines followed it before the reset (`system` turn_duration, `queue-operation`, an unanswered `user` task-notification, `last-prompt`, `custom-title`, `agent-name`, `mode`, `permission-mode`, `atis-latch`, `cost-state`, `file-history-snapshot`), and no further request was made. About six minutes earlier a meta user line `"usageLimitNote":"wrap_up"` ("[Usage limit reached; a short grace allowance remains, ...]") arrives; on resume a meta line `"usageLimitNote":"release"` ("[Earlier usage-limit notes no longer apply. Continue working normally. Don't mention this to the user.]").
- **Nothing resumed on its own.** All 18 bg sessions were resumed by a cross-session message ("Retry now: Ryan says the usage limit has reset. ...") 7 minutes to 16.5 hours after the reset.
- **The words appear elsewhere.** "hit your session limit" is in 38 transcripts, 33 with a real entry (19 main, 14 subagent copies with `isSidechain` true under `<sessionId>/subagents/`). Main transcripts also quote it in subagent notices: "Agent terminated early due to an API error: You've hit your session limit · resets 8:40pm (Asia/Tokyo) (error type rate_limit, HTTP 429, ...)". Parse the JSON; do not grep lines.
- **bg_id to transcript.** `bg_id` is the first 8 characters of the session id (the `id` in `claude agents --json`, `daemonShort` in the job). `~/.claude/jobs/<bg_id>/state.json` holds `sessionId`, `cwd` and `linkScanPath`, the transcript. For all 306 jobs the path is `~/.claude/projects/<cwd with every non-alphanumeric character replaced by "-">/<sessionId>.jsonl`. 66 `linkScanPath` values point at pre-move paths (jotform-glow-sync moved to ~/Projects), so fall back to `~/.claude/projects/*/<bg_id>*.jsonl`. Example: run `953ec26da542-222-20261024092105`, `bg_id` 106605e7, to the t-222 transcript above.
- **Job timeline.** `~/.claude/jobs/<bg_id>/timeline.jsonl` got `{"at":"2026-10-24T10:11:06.501Z","state":"blocked","detail":"You've hit your session limit · resets 8:40pm (Asia/Tokyo)",...}` in all 18 limited jobs. "blocked" also marks questions to Ryan ("go", "vpn is off").
- **`claude agents --json`.** Per entry: `pid` (live only), `id` (background only), `cwd`, `kind`, `startedAt` (ms), `sessionId`, `name`, `status` (busy, idle, waiting; live only), `waitingFor` (with waiting), `state` (background: working, blocked, done, stopped, failed). No error, reset or transcript path. The 2.1.328 source maps an API error with `error` rate_limit to state "blocked", needs "rate limited — wait and retry", and `needs` is not printed. So the list says blocked, never why.

## Detection rule for the run sweep (as implemented in #164)

`harness-work`'s sweep (`runs --sweep`, and the sweep every `dispatch` runs first) checks every bg run record not yet ended, since a limited session stays `blocked`, a live state:

- **The transcript.** `~/.claude/jobs/<bg_id>/state.json`'s `linkScanPath` when that file exists and names a file that exists, else the newest `~/.claude/projects/*/<bg_id>*.jsonl`. A subagent's copy sits deeper (`<sessionId>/subagents/`) and is never matched.
- **Limited.** Read the last 256 KiB, parse the lines from the end as JSON (a line that does not parse is skipped), and take the last entry with `type` "assistant" and `isSidechain` false. The session is limited when that entry has `isApiErrorMessage` true and `apiError` "usage_limit_reached", and no later `type` "user" entry has `usageLimitNote` "release". The text is never matched: no text fallback.
- **Reset, in UTC.** `apiErrorParams.rate_limit_info.resetsAt`, else `quotaLimits.resetsAt` (Unix seconds); without either, the entry's `timestamp` plus 5 hours. The reset text ("resets 8:40pm (Asia/Tokyo)") is not parsed: the epoch was present in every real refusal, and parsing the words is fragile across versions.
- **Mark.** Only when the reset is still ahead of the clock (the refusal's record is never updated, so an old one is not current): the `subscription` budget becomes exhausted until the reset, unless it is already exhausted until later. The run record keeps the refusal as `usage_limit` (`{"at": <its timestamp>, "until": <the reset>}`), so the same refusal marks the budget once and `budget reset subscription` holds; a new refusal (another timestamp) marks it again.
- **The hold.** While `subscription` is exhausted, bg dispatch (single repository, `--only`, `--after`, `--all-projects`, `--dry-run` too) starts and launches nothing, prints one line naming the budget and the reset time, and exits 1. Headless dispatch, billed to the API key, is not held.

- Whether 2.1.328's `autoContinueAtUsageLimit` ("When a claude.ai usage limit stops your session, wait for the limit to reset and continue the task automatically."; on when absent, behind server flags and an interactive-launch check) applies to `--bg` sessions. If it does, a `release` line and a new assistant turn follow the refusal, which the rule above already treats as resumed.
- The directory-name rule for paths long enough to be shortened.
