# Research notes: what a PreToolUse hook's allow and ask decide

Gathered 2026-11-05 for ticket #323 (epic #322) on Claude Code **2.1.318** (`claude --version`: `2.1.318 (Claude Code)`). The ticket expected 2.1.316. The CHANGELOG entries for 2.1.317 and 2.1.318 contain nothing about hook decisions, permission rules or the rm check, so the results should hold for 2.1.316 too; that was not tested. Quotes are the docs' words. Outcomes come from controlled runs in a throwaway fixture. Nothing under `~/.claude` was edited by hand (side effects are listed under Method).

## Answers

| # | Hook answer vs blocker | Command | `-p` | `--bg` | Interactive (pty) |
| :- | :- | :- | :- | :- | :- |
| a | allow vs auto-mode classifier | `rm -rf "$PROBE_TARGET"` | **ran** (a1); baseline denied (a0d) | **ran**, decided by the hook (bg-h1, `git clean -fd`) | **ran** (i-a1) |
| b | allow vs built-in rm check | `rm -rf victim/*/` | **denied** (b1 auto, b2 default) | **blocked** on a prompt with a 2-minute timer, then denied (bg-b1) | **prompted**, 2-minute timer (i-b1) |
| c | allow vs `permissions.ask` `Bash(rm *)` | `rm -rf victim` | **denied** (c1 default, c3 auto) | not run | **prompted**: "Ask rule Bash(rm *) overrides auto mode" (i-c1) |
| d | ask vs allow rule `Bash(echo:*)` | `echo probe-d` | **denied**; the reason is the tool result (d1 default, d2 auto) | **blocked**, `waitingFor: "permission prompt"`, no timer (bg-d1 default, bg-d2 auto) | **prompted**, with the reason in the dialog (i-d1 default) |
| e | deny + allow, two hooks | `rm -rf victim` | **denied**, in both orders (e1, e2) | not run | **denied** (i-e1) |
| f | allow in plan mode | `rm -rf victim` | hook ignored, **the classifier decided** (f1: ran, `reasonType: classifier`) | not run | not run |
| g | `additionalContext` / allow reason | `echo probe-g` | context **reaches the model**, the allow reason does not (g1, g2); context did not change a classifier denial (g3, g4) | not run | not run |

In short: a hook's `allow` skips the auto-mode classifier and the default-mode prompt, in every way a session can run. It does not get past an ask rule, the built-in rm check or plan mode. A deny from any hook beats an allow from another. A hook's `ask` overrides an allow rule. With no one to answer (`-p`), an ask becomes a denial. In a background session it holds the session at the prompt, with no time limit, until someone answers.

## Sources (fetched 2026-11-05)

- https://code.claude.com/docs/en/hooks.md, PreToolUse decision control: "`"allow"` skips the permission prompt, except for [actions no mode auto-approves] and [reads from network paths] ... For plan mode, see [Hook approvals in plan mode]. `"deny"` prevents the tool call. `"ask"` prompts the user to confirm. `"defer"` ends the turn so the tool can be resumed later, and requires [non-interactive mode] with the `-p` flag. [Deny and ask rules] are still evaluated regardless of what the hook returns". "When multiple PreToolUse hooks return different decisions, precedence is `deny` > `defer` > `ask` > `allow`." `permissionDecisionReason`: "For `"ask"`, shown to the user in the permission prompt. When Claude Code denies the call in a `-p` run where no one can answer that prompt, Claude reads the reason in the tool result instead. For `"deny"`, shown to Claude. For `"allow"` and `"defer"`, written to the debug log only". `additionalContext`: "String added to Claude's context alongside the tool result."
- hooks.md, "PreToolUse `ask` decisions in auto mode": "a PreToolUse hook's `"ask"` normally sends the tool call to the permission prompt, and the classifier doesn't decide it."
- hooks.md, "Annotate a result for the auto mode classifier": the supported way to tell the classifier something is PostToolUse `classifierContext` ("The classifier never receives tool results themselves"); from a settings or plugin hook "the classifier treats the note as unverified, application-provided context."
- https://code.claude.com/docs/en/permissions.md, "Precedence among rules, hooks, and mods": "Claude Code evaluates deny and ask rules regardless of what a PreToolUse hook returns: a matching deny rule blocks the call, and a matching ask rule still prompts even when the hook returned `"allow"` or `"ask"`." "Hook approvals in plan mode": "apart from `ExitPlanMode`, your `PreToolUse` hook's `"allow"` has no effect on a file edit or another call that isn't read-only."
- https://code.claude.com/docs/en/permission-modes.md, "Actions no mode auto-approves": "Recognized `rm` and `rmdir` critical-path removals, which no allow rule or `PreToolUse` hook `"allow"` approves, and Bash commands flagged `Dangerous rm operation not ruled out`". Other critical-path targets include "Some targets that end in `/*` or `/*/` | `rm -rf logs/*/*`, `rm -rf logs/*/`". In `auto` mode a critical-path removal "Asks you to approve it in the terminal, with a time limit. Elsewhere, denies it". The decision order's step 3: "Everything else goes to the classifier, apart from critical-path removals under their default handling."
- https://code.claude.com/docs/en/auto-mode-config.md: no statement about PreToolUse hooks beyond `PermissionDenied`. The docs never say in so many words that a hook allow skips the classifier; the runs below show it does.
- CHANGELOG (https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md, newest 2.1.318): 2.1.299 "Fixed plan mode running a write (an MCP tool's, a file's, a shell command's) that a `PreToolUse` hook or a mod's `tool.check` hook allowed"; 2.1.314 "Changed auto mode in Cowork cloud sessions: a hook's allow of an MCP tool call now counts as no answer" (Cowork cloud only, MCP only); older: "Fixed `permissions.deny` rules not overriding a PreToolUse hook's `permissionDecision: "ask"`" and "Fixed PreToolUse hooks returning `"allow"` bypassing `deny` permission rules".

## Method

- **Fixture**: `mktemp -d` under `$TMPDIR` (`/private/var/folders/.../T/hookprobe.RGT2`), outside every registered project and `~/.claude`: a git repo on `trunk` with one commit, plus a linked worktree `wt` on branch `probe`, so background sessions would not make a worktree of their own. `wt/victim/` was untracked: three files and two subdirectories `a/` and `b/`, rebuilt before every run. The ticket asked for branch `t/1-probe`. That name was not used, because tests_first.py acts on every `t/<N>-<slug>` branch and would have judged `rm` of an untracked path as a source edit needing a red run. branch_guard.py acts only on main and master, so any other branch keeps both out.
- **Probe hook**: `probe.py <tag>` (python3, matcher `Bash`). It appended its stdin to `hooklog.jsonl` and answered whatever `decision.<tag>` named (allow, ask, deny or none) as `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": ..., "permissionDecisionReason": "PROBE-REASON-<tag>-<run>"}}`. When `ctx.<tag>` existed it also returned `additionalContext` `PROBE-CONTEXT-<tag>-<run>`. It was loaded only with `claude --settings <file>`, a hooks block plus, for c and d, `permissions.ask ["Bash(rm *)"]` or `permissions.allow ["Bash(echo:*)"]`. For e it registered two probes (A and B) on one matcher. The settings file was a JSON file in the fixture, not an inline string. It works the same way and is easier to quote.
- **Runs**: `claude -p --session-id <uuid> --permission-mode <auto|default|plan> --settings <file> --max-turns 3..4 --output-format json --append-system-prompt "<run the one Bash command as given>" "Scratch fixture test ... Run this in Bash: <command>"`. Background runs used the same flags with `claude --bg -n probe-<run>`, read with `claude agents --json --all` and `claude logs`. Interactive runs drove `claude` through a python3 `pty` (120x40) and read the screen. The model sometimes ran an inspection command first. The probe answered that call too, and only the target command's record counts below.
- **Outcome**: whether `victim/` (or `victim/a/`) was gone after the run, and the transcript entry of the Bash `tool_result` in `~/.claude/projects/<slug>/<session>.jsonl` (`permissionDecision` `decision`, `source`, `reasonType`, `reasonCode`, `classifierCategory`, plus `toolDenialKind`), as in `auto-mode-classifier.md`. Hook-decided calls show `source: hook, reasonType: hook`. Classifier calls show `source: config, reasonType: classifier`. The rm check shows `reasonType: safetyCheck, circuitBreaker: dangerousRemoval`. An ask rule shows `reasonCode: rule:flagSettings`. A hook ask that nobody answered shows `reasonCode: hook:PreToolUse` with `toolDenialKind: user-rejected`.
- **Harness hooks active**: the plugin's readonly_bash.py, branch_guard.py and tests_first.py (PreToolUse Bash; the screen shows "running PreToolUse hooks… 0/4" with the probe), after_edit.py, session_brief.py, verify_on_stop.py and notify.py. None of the PreToolUse ones printed anything in any run (no `hook_success` with stdout in any transcript but the probe's), so none of them decided a call. bg-d2 ran with `enabledPlugins: {"harness@ryan": false}` so that its prompt sent no notification.
- **Conditions**: every run was started from inside a Claude Code background session, so `CLAUDE_CODE_CHILD_SESSION=1` was inherited. Interactive runs set `CLAUDE_CODE_FORCE_SESSION_PERSISTENCE=1` to get a transcript. The model was the default (Opus 5.5, high effort). Environment variables did not reach `--bg` sessions (`$PROBE_TARGET` was empty there), so the classifier-denied command could not be repeated in a background session.
- **Side effects outside the fixture**: the interactive trust prompt was accepted once (the background launch refused with `Workspace not trusted` until then). That makes Claude Code write a trust entry for `.../hookprobe.RGT2/repo` into `~/.claude.json` (not under `~/.claude/`). The path no longer exists, and Ryan can remove the entry if he wants. Claude Code itself wrote the probe transcripts under `~/.claude/projects/-private-var-folders-...-hookprobe-RGT2-wt/` and the interactive prompts to `~/.claude/history.jsonl`. `~/.claude/settings.json` is unchanged (mtime 2026-11-04). The fixture and its five background sessions were removed; afterwards `claude agents --json --all` lists no `probe-*` session.

## Evidence per answer

**a. allow vs the classifier.** Baseline a0d (`-p`, auto, no hook decision): `rm -rf "$PROBE_TARGET"` (`PROBE_TARGET=victim` in the environment) was `reject / config / classifier`, `classifierCategory: unverifiable_deletion_target`, `toolDenialKind: automode-blocked` ("Reason: [Unverifiable Deletion Target]"), and victim was kept. g3 and g4 repeated that denial. a1 (`-p`, auto, allow): the same command gave `accept / hook / hook`, and victim was gone. i-a1 (interactive, auto, allow) gave `accept / hook / hook`, gone. bg-h1 (`--bg`, auto, allow): `git clean -fd` gave `accept / hook / hook`, gone, session `done`. Without the hook, `git clean -fd` (h0) and `git reset --hard` (h2) were `accept / config / classifier` when the user's message asked for them. With allow, h1 and h3 were `accept / hook / hook`. In auto mode, a plain `rm -rf victim` (a literal path in the working directory) was `accept / config / mode` with no hook decision (a0): the classifier never saw it. In default mode the same command was refused in `-p` (a2: "rm in '<wt>/victim' needs approval ... Claude Code asks before a shell command creates, changes or removes files there"). With allow it ran (a3, `accept / hook / hook`).

**b. allow vs the built-in rm check.** b0 (`-p`, auto, none), b1 (`-p`, auto, allow) and b2 (`-p`, default, allow): `rm -rf victim/*/` was `reject / config / safetyCheck / dangerousRemoval` every time, and `victim/a` was kept. The probe's `hook_success` with the allow is in the b1 and b2 transcripts. bg-b1 (`--bg`, auto, allow): `state: blocked, waitingFor: "permission prompt"`, screen "Dangerous rm operation on statically-unresolvable target: <wt>/victim/* ⚠ Claude Code will automatically block this request in 1:59, to avoid holding up an unattended session". After two minutes it was `reject / safetyCheck`, and victim/a was kept. i-b1 (interactive, auto, allow) showed the same prompt and timer, and was refused with Esc.

**c. allow vs an ask rule.** c0 (`-p`, default, none), c1 (default, allow), c2 (auto, none) and c3 (auto, allow): every one was `reject / config / reasonCode rule:flagSettings`, "Claude requested permissions to use Bash, but you haven't granted it yet.", and victim was kept. i-c1 (interactive, auto, allow) showed the prompt "Ask rule Bash(rm *) overrides auto mode for this command. /permissions to let auto mode decide. Do you want to proceed?".

**d. ask vs an allow rule.** d0 (`-p`, default, no decision) was `accept / config / subcommandResults`, so the rule matches. d1 (`-p`, default, ask) and d2 (`-p`, auto, ask) were both `reject / config / reasonCode hook:PreToolUse`, `toolDenialKind: user-rejected`; the tool result the model read was the reason text `PROBE-REASON-A-d1-...`, and `permission_denials` in the JSON output lists the call. i-d1 (interactive, default) showed "Hook PreToolUse:Bash requires confirmation for this command: PROBE-REASON-A-i-d1-default-ask ... Do you want to proceed? 1. Yes 2. No". bg-d1 (`--bg`, default) was `state: blocked, status: waiting, waitingFor: "permission prompt"` with the same dialog and no timer. About four minutes later the prompt was answered Yes from outside this session, probably by Ryan through the harness notification: the record is `accept / user_temporary / grantScope once / reasonCode hook:PreToolUse`. bg-d2 (`--bg`, auto, plugin off) was `blocked / waiting / "permission prompt"` with no "automatically block" timer. It was stopped by hand.

**e. two hooks, deny and allow.** e1 (A deny, B allow) and e2 (A allow, B deny), both `-p` auto: `reject / hook / hook`, reason from the denying hook ("PreToolUse:Bash hook error: PROBE-REASON-B-e2-..."), and victim was kept. i-e1 (interactive, auto) gave the same; the hook log shows A answered deny and B allow for that call.

**f. allow in plan mode.** f1 (`-p`, plan, allow): `rm -rf victim` ran, but the record is `accept / config / classifier`, not `hook`. The hook's allow was ignored, and plan mode's classifier approved the call ("Reads, plus classifier-approved commands when auto mode is available", permission-modes.md). A plan-mode run with a command the classifier denies (f2) was not obtained: the model refused to call the tool in plan mode three times. That allow cannot override a plan-mode denial therefore rests on the docs plus f1's decision source.

**g. additionalContext and the allow reason.** g1 (`-p`, auto, allow + context) and g2 (`-p`, default, allow rule, context with no decision): the transcript has a `hook_additional_context` attachment and a system message "PreToolUse:Bash hook additional context: PROBE-CONTEXT-A-g1-...". The model quoted it when asked. The allow's `PROBE-REASON-...` appears only in the `hook_success` record (the hook's stdout), in no request sent to the model, and the model did not report it. g3 and g4 (`-p`, auto, no decision, context explaining that the target is a backed-up throwaway directory): the classifier still denied `rm -rf "$PROBE_TARGET"` [Unverifiable Deletion Target], both on the call that carried the context and on a later call after an earlier one had delivered it. PostToolUse `classifierContext`, the documented channel to the classifier, was not tested.

## What it means for the design (epic #322)

- **Task 5, backup_gate.py (rm in the project).** Its `allow` is the right lever. It makes a backed-up removal run with no prompt and no classifier in auto mode, and with no prompt in default mode, in `-p`, `--bg` and interactive sessions (a1, a3, i-a1, bg-h1). No `autoMode.allow` sentence is needed for it, so ruling 7's sentence does not apply: a hook's allow does override the classifier. Three limits hold whatever the hook says. (1) The built-in rm check (`victim/*/`, `logs/*/*`, a variable glob, `$(pwd)`-derived targets, any of permission-modes' "Other targets that count as critical paths") still denies in `-p` and prompts with a 2-minute timer in `--bg` and interactive sessions (b). So backup_gate should not snapshot for such a command, or must expect the prompt anyway. (2) Any `permissions.ask` rule that matches still prompts (c). (3) Plan mode ignores the allow (f). A deny from another hook (branch_guard, tests_first) beats backup_gate's allow whatever the order in hooks.json (e). The ordering is therefore safe, but the hooks run independently, so backup_gate cannot learn that a sibling denied the call. To satisfy "no snapshot is made for it" it has to repeat branch_guard's main-branch test, and tests_first's, before it snapshots. One more point, from reading tests_first.py rather than from a run: on a ticket branch it judges `rm` of a non-ignored untracked path as a source edit, so a coder without a red run is refused there before backup_gate matters.
- **Task 6, the git forms.** `git clean -fd` and `git reset --hard` reach the classifier in auto mode (h0, h2). There they passed when the user's message asked for them, but the classifier can refuse them when the request is less explicit. A hook allow takes them off the classifier entirely (h1, h3, bg-h1: `source: hook`). The rm check does not look at git commands, so the allow is enough for them unless an ask rule matches.
- **Task 8, land_ask.py (ask before landing a risk:high PR).** A hook `ask` does what the task needs. It overrides an allow rule such as `Bash(harness-pr:*)` (d) and keeps the classifier out of the call. In an interactive session it shows Ryan the `permissionDecisionReason` in the dialog. In a background session it holds the session at `blocked / waitingFor: "permission prompt"` with no timeout, in default and in auto mode, until Ryan answers (bg-d1, bg-d2). In `-p` it is a denial and the model reads the reason as the tool result (d1, d2), so the reason should say what to do next (for example "Ryan lands this one with /harness:land N"). Any deny elsewhere still wins over it (precedence `deny > defer > ask > allow`, as documented). Since `additionalContext` reaches the model but not the classifier (g), use it for guidance to the model only.
