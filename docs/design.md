# Harness design, v2

Ryan's personal Claude Code harness. One repository, one plugin, installed once at user scope, applied to every project. v2 written 2026-10-13 against Claude Code 2.1.296 (installed from the latest channel that day; the per-call Agent `effort` parameter arrived in 2.1.292), gh 2.99.0, git 2.39. v1 (2026-10-06) is in git history; what changed and why is in `docs/research/` and in the interview notes at the end of this file.

## Principles

1. **The board is the context.** Every unit of work is a GitHub issue: an epic with sub-issue tasks, each carrying the request, an outline, a definition of done and the tests that must pass. Agents read the ticket and its epic before working and write status back. The user's job is to answer questions on tickets and review pull requests.
2. **Tests before code, proven.** A test-author writes tests from the ticket; a tool proves they fail against the unchanged code; only on a `risk:high` ticket that changes a hook's decision path or a tool that destroys or rewrites data does an adversary try, for one round, to pass them with a trivial implementation, its gaps becoming requirements for the coder; only then does a coder touch source. A hook denies source edits until the proof exists.
3. **Never on main.** Each ticket gets its own branch and worktree. A hook denies edits, commits and pushes on main in every repository. GitHub Free does not protect branches on private repos, so the block is local, in two layers: git's own `pre-commit` and `pre-push` hooks (the scaffold installs them through `core.hooksPath`; `HARNESS_ALLOW_MAIN=1` skips them, as it does the branch guard, which `harness-pr revert` and the scaffold's first push of main set) refuse a commit on main or master, a push to either, a push that is not a fast-forward and a branch deletion, whatever the command was spelled as, and the branch guard hook refuses the same earlier, in the session, with the way forward, and keeps edits off the main checkout's working tree; landing goes through a pull request merged only by `harness-pr land`: the work loop runs `harness-pr land --catch-up` on every ticket, at any risk, once the branch is current with main and green and its high and medium findings are fixed, with no question to the user first, and parks a ticket it cannot land; the user lands a parked ticket's PR, when he chooses, with `/harness:land`. The one exception is `harness-pr revert`, which pushes a single revert commit from the main checkout.
4. **Route by labels, escalate by failure.** Opus 5.5 at high effort is the default everywhere. The planner labels each task with size and risk; the labels pick the tier and effort (Sonnet, Opus, or Opus at xhigh for size:L or risk:high; never Fable) unless the project's `HARNESS_CODE_TIER` or `HARNESS_REVIEW_TIER` sets it for that stage, and `HARNESS_CODE_EFFORT` sets the coding stages' effort. A second failure re-runs one step up (Sonnet to Opus, Opus to Opus at xhigh); a third, or a second already at Opus xhigh, stops and asks on the ticket. Fable runs only when a setting names it or Ryan launches it.
5. **Spend the subscription first.** Interactive sessions and dispatched ticket work run on the Max subscription by default. The API key is spent only on request: `harness-work dispatch --api` (an alias for `--venue headless`) runs headless and bills it. While the `api` budget is exhausted, `--api` and `--venue headless` are refused. An exhausted budget is remembered for a day; the `subscription` budget, marked when a background session hits the usage limit, until the reset that refusal names, and bg dispatch launches nothing until then (#164).
6. **Additive, never invasive.** Projects keep their own `CLAUDE.md`, hooks, rules and skills. The harness adds the board, the guards and the loop beside them, in every project including jotform-glow-sync.
7. **Deterministic where it must be, advisory where it can be.** Hooks and tools enforce; prompts advise.
8. **Fail open, except where a guard is sure.** A hook that hits its own error exits 0 and says so on stderr. The guards deny only when they have established the branch and the path.
9. **Standard library only.** `python3` 3.9 or newer, `git`, `gh`. Nothing to install.
10. **Hooks run outside the sandbox**, with the user's permissions and no prompt. The verify and test commands must be commands the user trusts.

Code shared between files lives in `plugins/harness/lib/harness_lib` (python3 standard library, `from __future__ import annotations`), loaded in place from the checkout with no install step. A file finds it relative to its own real path: a seven-line prologue at module top, after the standard-library imports, puts `os.path.realpath(__file__)`'s `../lib` first on `sys.path` (so a symlink still reaches the checkout, and neither a hooks/-local file nor a project file can shadow it; a file copied out of the checkout does not find it) and binds the names it uses in its own namespace (`from harness_lib.paths import canonical_path, ...`), never through `CLAUDE_PLUGIN_ROOT`.

Fail open: a hook that cannot load the lib (missing, a syntax error, an import that raises) writes `<hook>.py: cannot load harness_lib from <lib>: <error>` to stderr in one line and exits 0, so the call is allowed; notify.py also prints the bell (`{"terminalSequence": "\u0007"}`, as when `notify` answers False), because a Notification hook's stderr reaches no one; session_brief instead goes on without ticket state and puts one `Warning:` line naming harness_lib in the brief, because the guards are then off and a SessionStart hook's stderr reaches no one; in a project that declares its own SessionStart hook, where the brief is otherwise silent, that warning line is its whole output. The bin tools do not fail open: a bin tool that imports the lib (every one but harness-scaffold) prints `<tool>: cannot load harness_lib from <lib>: <error>` in one line and exits 1 before it parses an argument, because it must not guess a state key.

Every bin script is otherwise standalone (no imports between scripts): argparse, standard library, finds nothing through `CLAUDE_PLUGIN_ROOT` (that variable is not set for Bash). Scripts compose by calling each other on PATH and exchanging JSON (`--json`). A script that must call another finds it next to itself (`Path(__file__).resolve().parent`) when it is not on PATH. Each prints one line and exits 1 on a bad invocation or a failed precondition, never a traceback. `gh` is resolved as `os.environ.get("HARNESS_GH", "gh")` so tests can substitute a fake.

Install (once): `sh scripts/install.sh`. A marketplace added from a local path loads the plugin in place, so edits take effect at the next session start or `/reload-plugins`.

## Platform facts this design relies on

Verified 2026-10-13 from the Claude Code docs, the gh source at v2.99.0 and the GitHub docs; details in `docs/research/`.

- Plugin agents support `model` (alias, full id or `inherit`) and `effort`; they ignore `hooks` and `permissionMode`. The Agent tool takes `model` per call and, since 2.1.292, `effort`. An agent that omits `effort` runs at the session's level.
- `"model": "opus"` in settings resolves to Opus 5.5. `modelSettings` is keyed by canonical ids (`claude-opus-5-5`, `claude-fable-5-1`, `claude-sonnet-5-5`); a top-level `effortLevel` does not apply to Opus 5.5.
- PreToolUse receives `cwd`, `session_id`, `agent_type` (`harness:coder` for plugin agents), `tool_name`, `tool_input` (`file_path` absolute for Edit and Write, `notebook_path` for NotebookEdit, `command` for Bash). It denies with `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny", "permissionDecisionReason": "..."}}`; deny wins over every other hook. SessionStart carries no branch; its `cwd` is the worktree root when the session runs in one.
- `claude -w <name>` creates `.claude/worktrees/<name>` on branch `worktree-<name>` and cannot pick a branch name; `git worktree add` is the way to control the branch. `claude --bg -n <name> "<prompt>"` starts a background session in the cwd with the supervisor's stored login; trust is inherited from the main checkout; a session already in a linked worktree does not self-isolate. `claude rm` leaves a user-created worktree in place.
- Billing: `ANTHROPIC_API_KEY` and `apiKeyHelper` outrank the subscription login; in `-p` mode the key is used without a prompt. Background sessions cannot be billed separately. Cloud sessions and routines bill the subscription, need a TTY to start, and do not load plugins.
- Auto mode (verified 2026-10-24 on 2.1.310; `docs/research/auto-mode-classifier.md`): narrow Bash allow rules such as `Bash(harness-pr:*)` are resolved before the classifier, while a rule that ends in `:*` is read as a literal prefix, so `Bash(harness-*:*)` never matched a `harness-*` call; a compound call (pipe, redirect, `;` or `&&`) still reaches the classifier when one of its parts (`tail`, `head`, `python3`, `echo`, ...) matches no allow rule (116 of 116 on 2.1.310, 0 rule path), while one whose every part is covered (`cd`, `git`, `gh`, a `harness-<tool>`) usually takes the rule path (28 of 41 on 2.1.310; what sends the other 13 to the classifier is unknown). `autoMode` is read from `~/.claude/settings.json` only, not from the project file. The classifier denied `harness-pr land` twice (`Merge Without Review`, 2026-10-22 and 2026-10-23); 40 denials in all from 2026-09-01 to 2026-10-22.
- PreToolUse decisions (verified 2026-11-05 on 2.1.318; `docs/research/hook-permission-decisions.md`): a hook's `allow` runs a command the auto-mode classifier denies (auto mode, `-p` and interactive; in `--bg` a hook-decided `git clean -fd`), and one default mode would prompt for (`-p`), with the decision recorded as `source: hook` and no classifier call. It does not get past a `permissions.ask` rule (default and auto: denied in `-p`; in `--bg` the session stays `blocked`, `waitingFor: "permission prompt"`, with no timer; interactively it prompts), the built-in rm check (`rm -rf dir/*/` and the other critical-path forms: denied in `-p`, a prompt with a 2-minute auto-block timer in `--bg` and interactive auto mode) or plan mode (in `-p` the allow is ignored and the classifier decides; unverified in `--bg`, where the model wrote a plan instead of calling). A deny from any hook beats another hook's allow, in either order (auto mode, `-p`, `--bg` and interactive). A hook's `ask` overrides an allow rule: in `-p` (default, auto) it becomes a denial whose `permissionDecisionReason` the model reads as the tool result; in `--bg` it leaves the session `blocked`, `waitingFor: "permission prompt"`, with no timeout in default or auto mode; interactively (default) it prompts and shows the reason. `additionalContext` reaches the model (`-p`, `--bg`) and did not change a classifier verdict (`-p`). An allow's reason reaches neither. backup_gate.py and readonly_allow.py rely on the allow skipping the classifier.
- gh: `gh issue create --parent` links a sub-issue (not idempotent on retry); `gh api repos/O/R/issues/N/sub_issues` lists sub-issues with labels; `--blocked-by`, `--add-blocked-by` and `--json blockedBy` are native; a parent never auto-closes. `gh label create --force` updates. `gh pr checks --watch` exits 0, 1 (failure) or 8 (pending) and counts cancelled runs as not failed. The PR author can post a `COMMENT` review with inline comments through `POST /repos/O/R/pulls/N/reviews`; `APPROVE` is refused. `gh pr merge -R O/R --squash --delete-branch` deletes only the remote branch; local cleanup is ours. Branch protection and rulesets return 403 on this account's private repos. Issue types are organization-only; labels it is.
- The subscription usage limit (verified 2026-11-19 on 2.1.328 from the 2026-10-23 and 10-24 refusals; `docs/research/usage-limit.md`): a refused request becomes one synthetic assistant entry on the session's main transcript with `isApiErrorMessage` true, `apiError` "usage_limit_reached" and the reset as Unix seconds in `apiErrorParams.rate_limit_info.resetsAt` and `quotaLimits.resetsAt`; its text changes between versions and is quoted elsewhere (subagent notices), so the fields decide. `claude agents --json` shows such a bg session only as `blocked`, never why; `~/.claude/jobs/<bg_id>/state.json`'s `linkScanPath` names the transcript (stale after a project moves, so `~/.claude/projects/*/<bg_id>*.jsonl` is the fallback), and a resumed session gets a user entry with `usageLimitNote` "release".
- GitHub rate limits and gh's traffic (verified 2026-10-23, details and sources in `docs/research/github-rate-limits.md`): a user has 5,000 REST requests and 5,000 GraphQL points an hour, plus secondary limits (100 concurrent requests, 900 REST and 2,000 GraphQL points a minute, 80 content-creating requests a minute and 500 an hour). A GraphQL primary refusal is HTTP 200 and gh prints "API rate limit already exceeded for user ID <id>" (by the source with a `GraphQL: ` prefix, but the 2026-10-22 incident text had none, so the exact string is assembled, not verified; see the note) with exit 1; every refusal exits 1 and gh prints neither `retry-after` nor `x-ratelimit-reset` (only `GH_DEBUG=api` shows headers). `GET /rate_limit` is free on the primary limit but may count against the secondary one; a 304 is free on the primary limit and impossible over GraphQL. Most gh commands cost 1 to 4 requests (table in the note), `run watch` polls every 3 seconds with 3 requests plus one per in-progress job (about 7,200 an hour with 3 jobs), and gh keeps GraphQL feature-detection answers, refusals included, in `~/.cache/gh` for 24 hours.

Per project, in `.claude/settings.json` under `env` (read by hooks and tools the way `CLAUDE_VERIFY_CMD` is today: the process environment first, then `.claude/settings.local.json`, then `.claude/settings.json`, so a local file overrides the project file; read from the worktree's own `.claude/`, except the two classification keys tests_first and harness-red read from the main checkout's tracked settings, see Hooks):

A session started in one project can work a ticket of another (`harness-red check --worktree <Harness worktree>` from an OkinawaDream session); its process environment then carries the first project's settings env. The session's project is known from `HARNESS_SESSION_PROJECT`: Claude Code sets `CLAUDE_PROJECT_DIR` for hook processes only, never for the session's Bash calls, so session_brief (the SessionStart hook) exports `HARNESS_SESSION_PROJECT=<CLAUDE_PROJECT_DIR>` through `CLAUDE_ENV_FILE`, which each later Bash call sources first (verified facts in `docs/research/session-project-env.md`). So harness-red reads the worktree settings it uses (`HARNESS_TEST_CMD`, `HARNESS_TEST_TIMEOUT`, `HARNESS_TEST_MAP`) through settings.py's `project_setting`: when `other_project(main)` holds, that is, the session's project (`HARNESS_SESSION_PROJECT`, else `CLAUDE_PROJECT_DIR`, a blank one counting as unset) names a folder whose main checkout (`main_checkout`) is not this repository's (another repository, a folder outside any, or one git cannot read), the process environment is ignored for them and only the worktree's `.claude/settings.local.json` over `.claude/settings.json` counts, then the default (the detected test command, no verify command). Both unset, or the session's project naming this repository's main checkout in any spelling, a worktree of it or a folder inside one, keeps the order above. The classification keys keep tests_first's order, so the hook and the red run agree. harness-work's launches follow the same rule for the target repository (#299): `cloud` reads the prompt's verify command through `project_setting`, and when `other_project(<main>)` holds, the session `dispatch` launches gets `CLAUDE_VERIFY_CMD` and `HARNESS_TEST_CMD` from the main checkout's `.claude/settings.local.json` over `.claude/settings.json` only, each left out where they set none; otherwise the environment passes through.

A background session can also start inside another project's environment (#345): `claude --bg` run from one project's session starts the background daemon with that session's environment, every spare the daemon keeps inherits it, and a job of another project that claims such a spare gets that project's settings `env` laid over it, so a key only the first project's settings set (OkinawaDream's `HARNESS_TEST_CMD=npm test -- {files}` in a Harness job) survives, next to the first project's `HARNESS_SESSION_PROJECT` (verified facts in `docs/research/session-project-env.md`). session_brief's own export then names this project, so `other_project` is False in the session's Bash calls and `project_setting` would take the stray. So session_brief drops the strays at SessionStart: when its own `HARNESS_SESSION_PROJECT` names another project than `CLAUDE_PROJECT_DIR` (by `other_project`, as above), it appends `unset <KEY>` to `CLAUDE_ENV_FILE` for each harness key (`HARNESS_*` but `HARNESS_SESSION_PROJECT`, `CLAUDE_VERIFY_CMD`, `CLAUDE_VERIFY_TIMEOUT`) that no `env` object of `~/.claude/settings.json`, `<CLAUDE_PROJECT_DIR>/.claude/settings.json` or `settings.local.json` sets, and names each in the brief (Hooks). The drop happens once, where both facts are known: a hook process never sources `CLAUDE_ENV_FILE`, so it still sees the inherited `HARNESS_SESSION_PROJECT` beside `CLAUDE_PROJECT_DIR`, while a Bash call sees only this session's export. Teaching `project_setting` the same rule instead would need every tool to know which project the process came from, which its Bash environment no longer says, and to read the user's and the other project's settings files on every lookup. A key the user exports in the shell that started the daemon, and that no settings file sets, is dropped from another project's claimed session too, since the environment does not say where a value came from; set it in `~/.claude/settings.json` `env` to keep it everywhere. Hook processes keep reading the strays through `setting()` (tests_first, verify_on_stop and the rest), since they never source the file.

| `HARNESS_AUTODISPATCH` | `1` (a string or a number) opts the project into `harness-work dispatch --all-projects`, the hourly LaunchAgent's tick (#164). Read only from the `.claude/settings.json` committed at `origin/main` (`settings.committed_env`): never the environment, the working tree or `settings.local.json`; any other value is off | unset (off) |

The four routing keys (`HARNESS_CODE_TIER` to `HARNESS_WAVE_REVIEW`) are read by `harness_lib/routing.py` `load_routing(main)`: from the environment when it is not blank, else from `env` in the main checkout's tracked `.claude/settings.json` only (through `settings_env(main, ("settings.json",))` and `setting`); `settings.local.json` is never read. Values are stripped and matched case-insensitively. A value outside the allowed list is ignored, as if unset, and adds one problem line to the result (`HARNESS_CODE_TIER='gpt' is not one of sonnet, opus, fable; ignored`), so a bad value falls back to today's behavior and is reported rather than guessed at.

Machine-wide, under `env` in `~/.claude/settings.json`: `HARNESS_API_KEY_CMD` (default `security find-generic-password -s harness-anthropic -w`), `HARNESS_NOTIFY_APP`, `HARNESS_NOTIFY_SOUND`, `HARNESS_SECRET_SCAN`, `HARNESS_PROJECT` (`owner/number` of the GitHub Projects board harness-board mirrors the labels to; unset means no mirroring; see The board), `CLAUDE_VERIFY_TIMEOUT` as before.

Globs match against the repo-relative path with `/` separators; `**` matches any number of segments including none; a pattern without `/` matches the basename. One matcher function, specified here so every script agrees: split the pattern on `/`, walk segments, `**` consumes zero or more, other segments use `fnmatch`.

`repo-key` is the first 12 hex digits of the sha1 of the canonical path of the **main** working tree, found as the parent of `git rev-parse --git-common-dir` resolved to an absolute path. The canonical path is the real path with each component spelled as its parent directory lists it (`os.listdir`, matched case- and normalisation-insensitively and confirmed with `samefile`); from the first component that cannot be found, the rest stays as the real path spells it. A linked worktree and its main checkout therefore share one state directory, and so does every spelling of the path on a case-insensitive file system (macOS: `portfolio_projects/Harness` and `portfolio_projects/harness`). The helpers `canonical_path`, `same_entry`, `path_key`, `repo_key` and `adopt_old_state` are defined once, in `lib/harness_lib/paths.py`. The hooks session_brief and tests_first import all five and branch_guard imports `canonical_path` and `same_entry`, each binding the names in its own namespace; none keeps a copy, so without the lib a hook computes no key of its own (it fails open, above). The tools harness-board, harness-pr and harness-work import all five; harness-red imports `canonical_path`, `repo_key` and `adopt_old_state`; and harness-standup and harness-digest (which only key run files and never migrate a directory) import `canonical_path`, `same_entry`, `path_key` and `repo_key`. No tool keeps a copy (without the lib they print one line and exit 1, above). branch_guard uses no key helpers: it judges a main checkout reached through another spelling of its path (`/users/.../harness` for `/Users/.../Harness`) exactly as the on-disk spelling, comparing git's on-disk paths with the given path canonically rather than by `realpath`. `branch-slug` is the branch name with `/` replaced by `-`.

Migration from the spelling-based key: before the key was canonical it was the sha1 of the real path as spelled. When `repos/<repo-key>/` does not exist and `repos/<old>/` does, where `<old>` is the sha1 of the spelling of the main tree that git reported or that the tool's start path (cwd, `--repo`, `CLAUDE_PROJECT_DIR`, the hook's cwd or edited path) uses, the old directory is renamed to the canonical key, once. Only that repository's directory is moved; when both exist, both stay and the canonical one is used. harness-standup and harness-digest attribute a run file to a registered project by the canonical key or by the old key of the registered spelling, and harness-work counts a run as the repository's when its `repo` field is any spelling of the main tree.

Red record `red/<branch-slug>.json`:

```json
{"branch": "t/12-slug", "base_sha": "<merge base>", "test_files": ["tests/test_x.py", "tests/conftest.py", "tests/fixtures/a.json"],
 "run_files": ["tests/test_x.py"], "test_hash": "sha256 over path + newline + bytes of every test file, sorted",
 "cmd": "...", "exit": 1, "kind": "assertion|import|error|green", "tail": "last 40 lines", "at": "..."}
```

`test_files` is every changed path matching `HARNESS_TEST_PATTERNS` (fixtures and `conftest.py` included) and all of them are hashed; `run_files` is the subset passed to the test command, those whose basename matches `test_*.py`, `*_test.py`, `*.test.js`, `*_test.js`, `*.test.ts`, `*_test.ts`, `*.test.mjs`, `*.spec.js` or `*.spec.ts`. A change with no runnable file is refused.

A record is **current** (#231) when its test files hash to `test_hash` now, or when they are exactly the red-time files with main's changes since `base_sha` merged in: a merge of main (or a rebase) that brings in main's edits to the branch's test files keeps the proof, while a test change of the branch's own does not. harness_lib's `redproof.py` (`record_current(root, record, record_path, timeout)`) decides it for both harness-red `status` and tests_first, so the two agree on the rules; only their budgets differ: `status` gives it 30 s, tests_first what is left of its one deadline (tests_first, below), and it answers `current`, `stale` or `unknown` (`record_state`; the budget ran out first). `status` prints `unknown` as `current: no`; tests_first denies it with its own message. So on a slow git the hook can refuse an edit, asking for a retry, while `status` says `current: yes`; never the other way round. `check` keeps the red-time bytes of the test files in a side file, `red-files/<branch-slug>.json` beside `red/` (`{"test_hash", "files": {path: base64}}`, written just before the record); it counts only when it holds exactly the record's `test_files` and they hash to the record's `test_hash`, so an edited or stale side file proves nothing. A record without a valid side file (one written before it existed) has its red-time bytes recovered per candidate base by taking main's change back out of each file (`git merge-file -p --ours <now> <new base> <old base>`); the recovered set must hash to `test_hash` too, and goes through the same forward replay. When the hash differs, the new merge base is that of `refs/remotes/origin/main`, then `refs/heads/main` (the refs `check` defaults to, spelled in full so a tag or another ref named `main` cannot stand in; the record keeps no ref), each taken at the commit its newest reflog entry set and only when that entry is one the harness trusts (Trust boundary, below), with HEAD (`git merge-base <tip> HEAD`), with `MERGE_HEAD` added while a merge is in progress (`git merge-base <tip> HEAD MERGE_HEAD`, the base the merge commit will have, so a source conflict can be resolved mid-merge). A candidate counts only when it differs from `base_sha` and descends from it (`git merge-base --is-ancestor`): an older base (a stale local main, a record made with `--base` a stacked parent) would let the branch undo main's edits. Each test file must then be exactly its red-time bytes with main's change merged in (a file main left alone, or deleted, must be its red-time bytes): first `git merge-file -p --ours <red-time> <old base> <new base>` (Myers, no objects written); for the files where that differs, git's own merge (ort, histogram), as `git merge-tree --write-tree <synthetic> <new base>` (git 2.38+), where the synthetic commit is the old base's tree with the red-time blobs, its parent the old base, so the merge base is the old base. Its blobs, trees and commit go to a temporary object directory (`GIT_OBJECT_DIRECTORY`, reading the repository's through `GIT_ALTERNATE_OBJECT_DIRECTORIES`, with a temporary `GIT_INDEX_FILE` and a fixed identity and date), so the repository's object store and index are untouched; it costs eight git calls (rev-parse, hash-object, read-tree, update-index, write-tree, commit-tree, merge-tree, cat-file), about 0.3 s, only when merge-file has not matched every file; a conflicted ort merge counts for nothing (merge-file's `--ours` covers that case). Before it: one rev-parse for `MERGE_HEAD`, a merge-base and an is-ancestor per ref, one `cat-file --batch` per candidate and one merge-file per changed file (two without a side file: the recovery, then the replay). The inputs are fixed (bytes proven by `test_hash`, two commits of main), so a match pins every byte of the file now and nothing the branch does can satisfy it but the replay itself; a replay that differs from git's real merge can only give a false "not current", never a false "current". A known limit: the replay merges once, from `base_sha` to the newest merge base, while git merged each merge of main in turn, so after several merges a later edit of main's that lands next to an earlier merge's hunk can, rarely, merge differently; that reads as not current (a false deny, never a false allow); the recovery is below. The branch's own lines are thus compared by position against the new base, not by content: an edit, a move, a swap or a merge resolution that changes the branch's lines (main's side kept, a third value, the branch's line moved elsewhere) leaves the record stale. `--ours` settles a conflict the way git's `-X ours` would: a resolution that keeps the branch's own lines verbatim and drops main's conflicting edit of them keeps the record, as taking the branch's whole file (`git checkout --ours`) always did through the hash; any other resolution of a conflict does not. A `base_sha` that is not a commit id (40 hex digits, or 64 in a `--object-format=sha256` repository) or not a commit here (a hand-written `"0" * 40`) gets the whole-file comparison only. Any git failure counts as not current, a timeout as `unknown`.

Recovering from a false "not current" on a branch that has source, or from a fix round's test change (#275: coverage tests of behaviour the branch already has, which pass at HEAD): running `harness-red check` again does not help. It refuses with `Source already changed before the red run` and leaves the record as it was; `check --base HEAD` sees only uncommitted changes, so it needs a new, failing test change and records only those files, and with tests that pass at HEAD it writes a green record, which then refuses every source edit. The recovery is `harness-red reprove` (harness-red, below): it re-proves the branch's test files as they are now against main's code at the merge base, in a temporary worktree of its own, and writes the side file and the record as `check` does; a run that passes there, or proves nothing, is refused and writes nothing, so any earlier record stays as it was. It needs no earlier record (#309), and that is how a branch brought home from a cloud session gets its red record: no harness hook runs there, so its tests and source arrive together with no record, tests_first denies every source edit and `check` refuses; run `harness-red reprove --worktree <path>` before any local source edit or fix, and before merging main into the branch. Not mid-merge: HEAD has not moved, so the merge base is still the old branch point, while the test files main changed are staged and counted as the branch's, and they fail there for want of main's code, a red that proves nothing about the branch. A merge that already conflicted is aborted (`git merge --abort`), reprove runs, then the merge is redone and resolved; the record stays current through main's merged changes. Tests that pass at the merge base still get no record. It proves whatever the test files are now, whoever changed them (the role rules keep the coder and the test-breaker out of them), so after a false "not current" first read `git diff <base_sha> HEAD -- <test files>`. reprove is the right move only when that difference is main's merge or the branch's own reviewed test change (a fix round's tests, written by the test-author); any other change to the test files (one nobody reviewed, one that loosens or drops an assertion) goes back to the test-author, and a branch with no source yet proves its tests with `harness-red check`.

Trust boundary. The red proof stops an agent's shortcuts, not an agent set on getting round it. The state directory `~/.claude/harness/repos/<key>/` lies outside every repository, and its `red/`, `red-files/` and `tickets/` are what the gate reads. Since #267 tests_first denies the main session and every agent a direct write there (an Edit or Write, and a Bash write the walker sees: a redirection, `tee`, `cp`, `mv`, `sed -i` and the rest; Hooks, tests_first.py), so only harness-red, harness-board and harness-work write a red record, a side file or a ticket cache. A write the walker cannot see still gets there: an inline program (`python3 -c`, a heredoc) run by the main session or by an agent outside its ticket worktree, a tool it does not know as a writer (`tar -x`, `unzip`), or a directory's contents copied into a key directory (BSD `cp -R d/ <key>`); each takes intent, and each gives more than any forged ref. Within that boundary a merge of main adds no easier way round: a ref counts at the commit its newest reflog entry set, and only when that entry is a fetch or pull from `origin` (named or the default) whose refspecs name no destination or take `main` to one, a push or a clone, and, for `refs/heads/main` (the user's own checkout), a commit, merge, rebase, reset or branch creation. That stops `git update-ref <ref> <commit>` (no message), `git fetch . <commit>:<ref>`, a fetch of another remote or another branch into the ref, `git branch -f`, a tag named `main` or `origin/main`, and a write to the ref's file (no reflog entry). It does not stop `git update-ref -m "fetch: fast-forward"`, a hand-written reflog line, or `git remote set-url origin` to a repository of the agent's own followed by a fetch; branch_guard's rule (d) refuses those, and the other moves above, from a ticket branch or a linked worktree (#268), `git -C <main checkout>` run from one included; a command that starts in the main checkout on main keeps rule (b) alone. A ref with no reflog (`core.logAllRefUpdates=false`, or an entry gc expired) names no base: a false "not current" until the next fetch. Neither the hook nor `status` asks the remote.

## The board

GitHub Issues in each project's private repository. An **epic** is an issue labeled `epic`; its **tasks** are sub-issues. Dependencies use GitHub's native blocked-by. Status, type, size, risk and flags are labels. Done is closed.

**Projects board (optional, a mirrored view).** One GitHub Projects board, a user-owned project spanning the registered repositories, shows the same tickets as columns by Status, with the epics as swim lanes (grouped by Parent issue). The labels stay authoritative: no ticket state is ever taken from the board, and only `harness-board project check` and `project sync` read it, to compare it with the labels. The mirror sets the item's Status (Ready, In progress, In review, Blocked or Needs input) and, for `task create --priority`, Priority High; a closed issue becomes Done through the project's built-in workflow, not through the harness. A card dragged to another column is not a status change: the labels are not touched, and for an open issue the board is put back from the labels the next time that issue's status changes or `harness-board project sync` runs (decision D3 in `docs/proposals/kanban-board.md`). That holds for open issues only: a closed issue's card dragged out of Done stays where it is until auto-archive removes it. A drag between epic lanes may also change the issue's parent. A failed mirror call is one warning and never fails a command, so the board can drift until the next sync; `project check` and `project sync` report their own failures with exit 1. Since no ticket state comes from the board, drift is cosmetic. It is off unless `HARNESS_PROJECT` is set, from the environment (an empty value is off) or `env` in `~/.claude/settings.json`, and it needs the `project` scope of `gh auth`. Ryan chose a new board, separate from the existing "Claude Kanban" project #1 (2026-10-14). Epic body template (`templates/ticket_epic.md`): `## Goal`, `## Why`, `## Scope` and `## Out of scope`, `## Definition of done`, `## Verification` (the end-to-end commands), `## Decisions and open questions`. Tasks are the sub-issues; no task list in the body.

Ops body template (`templates/ticket_ops.md`, #72; for a record update with no code change, type `ops`): `## Request`, `## Change` (which records and fields, from what to what), `## Source of truth` (the query or id list), `## Apply` (the connector, API or project script), `## Verify` (the read-back), `## Rollback` (restoring the before-values), `## Context`.

The harness comments on a ticket as it moves: `Started on <branch> (...)`, `Pull request: <url>`, then on landing a `**Resolution**` comment followed by `Landed in <full squash sha>` (the line other tools look for; unchanged). Every one ends with `<!-- harness -->`. The Resolution is the account of what landed, copied from the merged PR, each part left out when the PR body lacks it:

```markdown
**Resolution**

<the PR body's whole ## Summary section>

Notes:
<the PR body's ## Notes section, when `harness-pr open --notes` added one (a later open without --notes keeps it)>

Files changed (<n>):
- `<path>`            (one per file, every file the PR changes)

Definition of done:
<the PR body's ## Definition of done section as landed, wrapped lines included>

Red run before implementation (<kind>, exit <code>)
Verify: <the last non-empty line of the verify fence>
PR: <url>
Squash commit: <full sha>

<this ticket's Cost block: the stdout of `harness-work cost N --pr P --markdown --landed-by loop|hand`, stripped>

<!-- harness -->
```

Everything above the Cost block is the PR's and the same on each ticket it closes; the Cost block is the ticket's own. Its `Landed by: loop` line marks a land the work loop ran (`harness-pr land --loop`), and `Landed by: hand` any other land (#426): the loop marks itself, so a missing flag counts as a person's land and the loop's completion rate is never overstated. It is left out, with no blank line, when the cost run prints nothing; when the run fails, times out or harness-work cannot be found, the land prints one `harness-pr: warning: no cost block for #N: <reason>` line and posts the Resolution without it.

The orchestrator passes `model` and `effort` on the Agent call from `harness-board tier N --json`: for the test-author, breaker and coder (retries and fix rounds included), its `tier` as `model` and its `effort` when that is not null. The project's `HARNESS_CODE_TIER` and `HARNESS_CODE_EFFORT` decide that tier and effort when it sets them, the labels otherwise (`opus` at `xhigh` for `size:L` or `risk:high`). An escalation runs at the tier and effort `harness-work attempt` names, counted from what the stage ran at: `escalate opus` from sonnet, `escalate opus xhigh` from opus, and `park` from opus xhigh or an explicitly set `fable`; no escalation goes to Fable. The reviewer's model and effort come from `harness-board tier N --stage review --json` the same way: `HARNESS_REVIEW_TIER` when the project sets it (a `fable` review carries `xhigh`), otherwise the labels: `opus`, with `xhigh` when the ticket is `risk:high`. The review stage is recorded with `harness-work attempt N review pass|fail --tier <tier> --effort <effort>`, the tier and effort it ran at (`--effort` left out when null), so a second failure of an Opus review escalates to opus xhigh and one of an Opus xhigh review gives park; without `--tier` the attempt uses the ticket's review route. The read-only guard (`readonly_bash.py`) now covers `planner`, `reviewer` and `researcher`.

Every high or medium review finding on the files the ticket touched is fixed before `harness-pr ready`; a low finding goes into the PR notes for the owner, with no fix round; only a high or medium finding outside the ticket's files that a command the loop or the user runs would hit becomes a new ticket, and the PR body names it and says why (any other gap is a `Not covered:` line in the notes). Every ticket the loop files (such a finding, a size-cap split, any other follow-up) is `harness-board task create ... --proposed` under the ticket's epic, never `--blocked-by` the current ticket; the owner promotes it. A high or medium finding on a test file, which the coder may not edit, goes to the test-author (`#N tests`) in the fix round, and its changes are proven red as a revise pass's are. `harness-pr land` refuses a head its latest harness review does not cover (only clean merges of main may follow the reviewed commit, and `--accept-findings` does not override it), for the loop and `/harness:land` alike. The skill judges the commits after the reviewed one as `autoland.at_head` does, whoever made them and whatever their messages say, since `git log` shows a hand-resolved merge of main and a clean one alike: `git rev-list --first-parent --parents <commit_id>..HEAD` after `git fetch origin`, and each commit on it must have two parents, the second an ancestor of `origin/main`, with `git merge-tree --write-tree <parent1> <parent2>` exiting 0 and printing the commit's own tree, the oldest one's first parent being the reviewed commit. So a head that carries any other commit since that review (a CI, revise or merge fix, or a merge that conflicted) gets a head review before `harness-pr ready`, and again before the land when making the branch current added a commit of the coder's: the reviewer (`#N fix`) reviews the pushed head, its findings split and posted with `harness-pr review` as the first review's are, recorded as those fixes' re-check (`harness-work attempt N fix`), its high and medium ones on the ticket's files going to a fix round; a land refused with `review the head again` gets the head review and one more land. The head is thus covered for any land. A `manual-land` PR (#451: the label on the PR or on its ticket, `labels` in `harness-board show N --json`) is the one exception: the loop stops after `harness-pr ready`, the ticket in review, and ends the turn reporting that the PR waits for the owner's `/harness:land P`, with no park and no `dispatch --after`; an exit 9 from `harness-pr land --loop` ends the turn the same way. Every other PR, at any risk, is then landed by the loop with `harness-pr land P --catch-up`, with no question to the owner first (a `risk:high` ticket has had the Opus xhigh review), run as a plain command (a pipe, redirect or `tail` around it sends the call to the auto-mode classifier, which has denied it as `[Merge Without Review]`, docs/research/auto-mode-classifier.md section 6) with the Bash timeout at 600000 ms and the default `--timeout`, whose 420 s of waiting leave the merge and the canary room under the tool's 600 s; `--catch-up` merges origin/main into a branch behind main when that merge is clean, so the loop makes no merge of main of its own. An exit 8 (checks still pending) is run again unchanged, at most three times in a row (about 28 minutes of waiting in all). A conflict refusal goes to the coder (`#N fix`, after `harness-red reprove` on a branch with no red record), which merges origin/main, resolves and commits, then own tests, push and `checks --wait`; red checks go to a CI fix round; `review the head again` goes to the head review; each ends in the head review and another land. Any other refusal, a coder that cannot resolve a conflict (one in a test file), or a cap (two conflict resolutions, the ci and fix rounds `harness-work attempt` allows, five land calls besides the exit-8 re-runs) parks the ticket. The land is the turn's last command, since it removes the worktree the session may run in, and the loop runs no dispatch after it (dispatching what it unblocked is the land's job, #390); the loop never merges otherwise (no `gh pr merge`). A call refused because the auto-mode classifier gave no verdict (`classifier:auto-mode:unavailable`) ends no turn while steps remain: the skill reads with Read, Grep and Glob instead, retries the call once as it was and goes on with the other steps; one still refused when nothing else is left is a tool failure, and parks. The skill is one turn, every agent in the foreground: it ends at a landed PR (any risk), a ready PR of a `manual-land` ticket, a parked ticket followed by `harness-work dispatch --after N`, a posted needs-input question (an agent's question only), or a `harness-work start` refusal; without a ticket number, once dispatch has launched the runs, shown its `--dry-run` plan or found no ready tickets.

A ticket whose `flags` (from `harness-board show N --json`) hold `no-tests` skips the test-author, `harness-red check` and the breaker: the coder implements against the definition of done, the verify command must still pass, and the review still runs. A `risk:high` ticket that changes neither a hook's decision path (`plugins/harness/hooks/*` here, a project's own hooks elsewhere) nor a tool that destroys or rewrites data (backup, land, revert, worktree remove) skips the breaker too, from the orchestrator's reading of its outline and tests, and goes from the red check to the coder.

An `ops` ticket (#72: records updated in Salesforce, Jotform or by a project script, no code change) takes the ops path instead: `harness-work start` makes no worktree and names `before_dir`; no test-author, red check, breaker, code review or pull request. The session reads Change, Source of truth, Apply, Verify and Rollback; saves the before-values of the selected records into `before_dir` before any write; previews before → after; applies with the named tool; reads back; runs a short Opus results check (never Fable) that the read-back matches the Change; posts a `**Results**` comment (counts, records changed before → after, the read-back, failures and skips, the check's verdict, the before-values path for a rollback); then `harness-board status N in-review` and a notification, and the owner closes it. Ruling (the ticket's open question): an update that deletes records or touches more than 25 records posts its preview as `harness-board needs-input` and waits for the owner's OK before applying; smaller updates apply directly (auto mode still asks before record deletes in Salesforce or Jotform). An ops ticket that needs a code change after all becomes a normal ticket before any write: the run rewrites the body into the task template (Request, Outline, Definition of done, Tests that must pass, Context; `context_markdown` shows the ops headings only for type `ops`), carrying Change, Source of truth, Apply, Verify and Rollback into Outline and Context, with `gh issue edit N --body-file F`; then `harness-board retype N --type task --reason ...`; then `harness-board needs-input N` asks the owner to confirm the rewritten spec, and the run stops. Ruling: needs-input, not ready or park, because the spec changed under the owner and the answered question resumes the ticket as a normal run (`previous_status` needs-input with `answers`), while dispatch skips it until then; an in-progress ticket left behind would be redispatched with no run to finish it. The guards need no change: the run edits nothing in a repository, and `before_dir` is outside every one (pinned by `OpsBeforeValuesTests`).

Failure policy, enforced by `harness-work attempt`: the first failure of a stage retries at the same tier and effort; the second re-runs one step up the ladder (sonnet goes to opus, opus goes to opus at effort xhigh), except that a second failure at opus xhigh or max, or on an explicitly set Fable, goes straight to `park`, since nothing is above it; the third answers `park` (#387): the stage's final failure parks the ticket (`status:blocked`, with the evidence) rather than asking the owner, and the loop moves on. No escalation goes to Fable. `fix` has its own rule, two rounds: the first failure retries at the same tier and the second answers `park`, with no escalation. `breaker` runs one round (#375): its failure answers `done` at any tier and however often it is recorded, and the loop goes on to the coder with the breaker's gaps as `Requirement:` lines and to the reviewer with them as check items; it never sends the tests back for a second round and never answers `park`. A park is `harness-board park N --reason "<stage>: <what still fails>" --evidence-file <tail>` (status:blocked, a Parked comment with the evidence, a proposed follow-up, a notification) and then `harness-work dispatch --after N`, which launches the next ready ticket, and the turn ends; the loop parks the same way at a land cap or a land refusal it does not handle, after filing a size-cap split as proposed tasks (`--follow-up` naming them), and on a tool failure no stage can fix (gh or git down). `harness-board needs-input` stays only for a question an agent asks that the ticket, the epic and the code cannot answer, about product behavior or direction, or about something hard to undo or touching security, credentials or personal data. A stage is `tests` (red cannot be reached), `breaker` (a constant or fixture-special-casing cheat passed), `code` (the ticket's own tests not green), `review` (the reviewer returned no usable findings; a findings array of any length, empty included, passes), `fix` (high or medium findings on the ticket's files still open after a fix round's re-check), `ci` (checks red). Each stage counts its own failures: a run of failures ends at that stage's next pass, and another stage's result neither adds to it nor resets it.

Every Agent call the work skill makes carries the description `#N <stage>`, which `harness-work cost` reads (`^#(\d+)\b` and the word after it): `tests` for the test-author (in a revise pass or a fix round too), `breaker`, `code` for the coder until the first review, `review` for the first review, and `fix` for every coder or reviewer run after the first review (its findings, CI failures, the owner's comments). A continued (SendMessage) agent's transcript is split at the coordinator's continuation entries into segments, each its own round, and a code or review segment starting after the end of the ticket's first review counts as `fix`, except segment 1 of an agent whose description names its stage. A revisit of a ticket with `status:needs-input` and a newer comment by the repository owner passes that comment to the agents as the answer. A revisit of a ticket in `status:in-review` with unresolved review threads from the owner runs the coder on those comments only, then checks, the head review (the coder's commits follow the latest harness review), ready and the land step again: the PR, at any risk, lands without waiting for the owner again, his addressed comments being his review, while the head review still covers the head for `harness-pr land`; a `manual-land` ticket's revise pass ends at ready instead.

## Hooks

`hooks.json` wires: Notification to `notify.py`; SessionStart (`startup|resume|clear|compact|fork`) to `session_brief.py`; PreToolUse `Bash` to `readonly_bash.py`, `branch_guard.py`, `tests_first.py`, `backup_gate.py` and, last, `readonly_allow.py`; PreToolUse `Edit|Write|NotebookEdit` to `branch_guard.py` and `tests_first.py`; PostToolUse `Edit|Write|NotebookEdit|Bash` to `after_edit.py`; Stop to `verify_on_stop.py`. Timeouts 10 s for the guards and readonly_allow, 30 s for backup_gate. Claude Code combines the hooks' answers by decision, not by order (`deny` > `defer` > `ask` > `allow`, docs/research/hook-permission-decisions.md), so backup_gate's `allow` after a backed-up `rm` and readonly_allow's `allow` of a read never pre-empt a deny from the guards. A hook killed at its timeout prints nothing, so the call goes through; tests_first therefore keeps one deadline, 8.5 s from its start (interpreter start and imports take the rest), and gives every git call the lesser of 3 s and what is left, and the red proof all that is left. Out of time, it denies wherever a denial was pending or the record could not be checked (the check-ignore of a Bash write, the proof, the file list of a wholesale rewrite, and on a guarded branch the main checkout's lookup, `main_checkout(..., raise_timeout=True)`: `Could not find this worktree's main checkout in time (git was too slow), so the tests-first rules were not checked; the edit is refused, not judged. Retry it.`); only the lookup that names the branch (its first git call) fails open, since without it the branch is unknown (#285).

**branch_guard.py** (PreToolUse `Edit|Write|NotebookEdit|Bash`). Fail open. Exempt when `HARNESS_ALLOW_MAIN` is `1` (environment or project settings).
- Edit, Write, NotebookEdit: take `file_path` or `notebook_path`; walk up to an existing directory; `git -C <dir> symbolic-ref --short HEAD`; if the branch is `main` or `master` and `git rev-parse --verify HEAD` succeeds (the repo has a commit), deny, except for a path under `docs/agent/` (the handoff note and specs, which the session brief reads) and for an untracked path that `git check-ignore` reports as ignored (local settings, `.env`, scratch files): `On main in <repo basename>. Work happens on a ticket branch: harness-work start <issue#> for a ticket, or git switch -c t/<n>-<slug> for untracked work.` Outside a repo, on a detached HEAD, or on an empty repo: allow.
- Bash: split the command on `;`, `&&`, `||`, `|`, `&` and newlines (and inside `(...)`, `$(...)`, `sh -c`, `eval`, a heredoc a shell reads and a `-c alias.x='!...'` git alias) and judge each part in the directory it runs in: `cwd`, moved by `cd`/`pushd` (an empty target, or one that is not a directory, leaves it unchanged unless `&&` follows, since a failed `cd` stops the chain; an unresolvable target such as `$VAR` makes it unknown and the repo rules allow), restored after a subshell, substitution or child shell; git's directory also follows `-C`, `--git-dir` and `--work-tree`, and `-c alias.<x>=` aliases are expanded. Deny when (a) a part plainly writes a path whose repo (that of the nearest existing directory; `.git/...` belongs to the repo around it) is a main working tree on `main` or `master` with a commit, from any cwd: a redirection or `tee` to it, `cp`, `mv`, `install`, `ln`, `rsync` or `dd of=` into it, `mv`, `rm`, `touch`, `truncate` or `chmod` of it, `sed`/`gsed -i`, `perl -i`, `awk -i inplace`, `ed` or `patch` on it (`xargs` with one of these counts as writing the current directory); a path under `<top>/.claude/worktrees/`, in a linked worktree or outside any repo is never refused, nor is `mkdir`. A written path is exempt, for every form (`rm`, `truncate` and both sides of `mv` included), when its word is one name (no unquoted glob or brace the shell expands), it is not under `.git`, it is under `docs/agent/` or one `git check-ignore` reports (so a directory holding a tracked file is not exempt), and, when it is a symlink, the file it resolves to is exempt in its own repo or lies outside every protected main working tree. A `cp`, `mv`, `ln`, `install` or `rsync` into an existing directory is judged by that directory, resolved (`cp x.py ~/h/` with `~/h -> <main checkout>/src` writes `src/`; `cp -R w/ .claude/` writes the main checkout's `.claude/`), and is exempt only when the directory is `docs/agent/` or under it, since the copy may put any name there (BSD `cp -R src/ dest` copies the contents of `src`), and then not when `dest/<basename of a source>` exists and is not exempt itself (`docs/agent/x.md -> ../../README.md`); a named destination (a file, a name that does not exist yet, and for `ln -n` or `-h` a symlink to a directory) is judged by its name like any written path. ### harness-red

Runs in a ticket worktree (cwd, or `--worktree PATH`). On a `t/<n>-` branch whose ticket cache (`tickets/<n>.json`) has `no-tests` in `flags`, `check` and `status` print `ticket N is no-tests: no red run needed` (with `--json`, one object `{"no_tests": true, "ticket": N, "message": "..."}`) and exit 0 with no run and no record (a missing or corrupt cache, absent flags or another branch name take the normal path); `harness-pr open` then writes `none: the ticket is no-tests` in the red block.

- `check [--base origin/main]`:
  1. `merge-base HEAD <base>`; changed paths = `git diff --name-only <merge-base>` plus `git status --porcelain` untracked and modified. Test files = those matching `HARNESS_TEST_PATTERNS`; none → `No test changes on this branch; write the tests first.` exit 1.
  2. Source files changed (not test, not exempt) → `Source already changed before the red run: <list>. Revert them or move them to the coder step.` exit 1.
  3. Run `HARNESS_TEST_CMD` with `{files}` = the test files, `cwd` = worktree, timeout `HARNESS_TEST_TIMEOUT`, `PYTHONDONTWRITEBYTECODE=1` (in another project's session the worktree's settings alone name the command, Settings above). A module that exists nowhere there (the code under test, not written yet; a new module of an existing package; a file of that name that is no python module), or only in a directory that holds no run file and is above none (`scripts/x_support.py`, `tests/b/x_support.py` for `tests/a/test_x.py`), stays the usual red `import`.
  5. Write the side file `red-files/<branch-slug>.json` (the test files' bytes as hashed, Red record above), then the record; print `red (<kind>): <n> test files, exit <code>` and the tail; exit 0 when red. On `green`: `Tests pass before the implementation; they do not test this change.` exit 1 (the record is still written so a refactor ticket can proceed).

It runs before a merge of main, not during one: mid-merge the merge base is still the old branch point and the test files main changed, staged by the merge, are taken as the branch's (Red record, above). A module the branch's own source adds is tracked (committed or staged), so main's lacking it is the usual red `import`; one only in an untracked file not yet added is refused like a dependency until it is added.
- `status`: the record for the current branch, and `current: yes|no` (test_hash against the files now, or the files being the red-time ones with main's merged changes: Red record, above).
- `files [--base origin/main] [--json]`: the branch's own test files, which the tests, code and fix stages run instead of the whole suite. Changed paths as `check` computes them; the candidates are the worktree's files (`git ls-files --cached --others --exclude-standard`) that exist, match `HARNESS_TEST_PATTERNS` and have a runnable basename (`test_*.py`, `*_test.py`, `*.test.js`, `*_test.js`, `*.test.ts`, `*_test.ts`, `*.test.mjs`, `*.spec.js`, `*.spec.ts`). The list is the changed test files that are candidates, plus, for every other changed path (source or exempt, existing or deleted), the candidates the name rule or `HARNESS_TEST_MAP` gives. Name rule: a candidate's subject is its basename without the test affix and extension; normalised (lower case, each run outside `[a-z0-9]` one `_`, outer `_` trimmed), it names a path when it equals a `_`-token suffix of the path's normalised form without its last extension (components joined by `_`), or the normalised name of one of its directories (`bin/harness-work` → `test_work.py`; `lib/harness_lib/cost.py` → `test_cost.py`, `test_harness_lib_cost.py`, `test_harness_lib.py`). Files under `plugins/harness/templates/` (the scaffold's smoke tests, copied into other projects) are never candidates, so they are neither listed nor mapped. Text: the files, one per line, sorted; nothing when there are none. `--json`: `{"base", "files", "changed_tests", "mapped": {path: [tests]}, "unmapped": [paths]}`; a changed test file that is deleted or not runnable is in none of the lists. No-tests tickets get the same answer as any branch.
- `run [--base origin/main]`: `HARNESS_TEST_CMD` (or the detected default) with `{files}` = the `files` list, `cwd` = worktree, timeout `HARNESS_TEST_TIMEOUT`, `PYTHONDONTWRITEBYTECODE=1`; prints `own tests: <n> files, exit <code>`, then `elapsed: <s>s` (the seconds the run took, from `time.monotonic`; the test-author keeps a module under 180 s alone by it) and the last 40 lines, exit 0 when the command passed, else 1; a timeout prints `own tests: <n> files, <cmd> timed out after <t>s and was stopped` and the `elapsed:` line, exit 1. No files: `no own test files for this branch's changes; nothing run`, exit 0. It writes no record and never reads the red record.
- After a merge of main the record stays current, so no new `check` is needed; one run anyway refuses with `Source already changed before the red run` (the coder's source is on the branch) and leaves the record as it was.
- `scratch create`: a detached worktree of `HEAD` at `~/.claude/harness/repos/<key>/scratch/<branch-slug>` (plus uncommitted test files copied in), prints the path; `scratch run`: `HARNESS_TEST_CMD` on the record's test files in the scratch, prints `cheat passed` (exit 0) or `cheat failed` (exit 1) and the tail; `scratch remove`.
### harness-pr

- `open N [--worktree PATH] [--verify-log F] [--review F] [--notes F]`: in the ticket's worktree: refuse with the list when the tree is dirty, and refuse a `--notes` file that is missing or has a `## ` heading outside a code fence (`###` is fine), both before the push; `git push -u origin <branch>`; body from `templates/pr_body.md` with the title, `Closes #N`, the notes (a `## Notes` section between Summary and Definition of done, only with `--notes`; the Resolution repeats it), the definition-of-done checkboxes copied from the ticket, the tests list, the red proof (kind, exit, 15 lines of tail), the verify tail (20 lines of `--verify-log`), the review summary (counts by severity and the high findings from `--review`), a risks line for `risk:high`; `gh pr create --draft --base main --head <branch> --title "<title> (#N)" --body-file`; if a PR for the branch exists (`gh pr list --head <branch> --state open --json number,url,body`), `gh pr edit --body-file` instead, and there an absent `--review` keeps the text of that body's `## Review` section and an absent `--notes` keeps its `## Notes` section (none when it has none; sections split as the Resolution splits them, headings in code fences not counting), while a given flag replaces its section (an empty `--notes` file drops it) and the rest is rebuilt; with no PR yet, `harness-board comment N` with the PR URL; prints `{"number", "url"}`.

The round `{"round", "at", "head", "base", "blocking", "low", "outside", "pr", "review_id"}` (`review_id` the id GitHub gave the review, null for a no-findings post or with no PR) is saved with `reviews.save_round` (`base`: the previous round's head, the merge-base in round 1; the same HEAD replaces the latest round and keeps its number). It writes `reviews/N/round-<k>-blocking.json` (blocking, for the coder), `round-<k>-review.json` (blocking plus low, for posting and `open --review`) and `notes.md`, rewritten on every call from all rounds and every `--rulings` file given so far: `### Low findings` (each low finding once, outside ones marked `(outside the files this ticket changed)`), `### Out of scope` (each high or medium outside finding, ``- `path:line` [severity] body (outside the files this ticket changed)``, followed by ` -> #<n>` once it is ticketed) and `### Rulings` (each `Ruling:` line once, in order), each left out when empty, bodies on one line so no `## ` heading appears. Low outside findings never become tickets, and with no PR none are made. Prints `#N review round k: B blocking, L low, O outside; record: harness-work stage N <stage> <result>` (`review pass` in round 1; later `fix pass` with nothing blocking, else `fix fail`), the post and the new tickets when there are any, and the three paths; `--json` prints `{ticket, round, head, base, review_base, blocking, low, outside, files: {blocking, review, notes}, record: {stage, result}, pr, review_id, tickets}`, `review_base` being this head and `tickets` the numbers this call created. `findings N --latest [--json]` prints the latest round as recorded, writes nothing and makes no gh call; with none, `no review round recorded for #N` and exit 1.

Then the land below runs unchanged on the loop's last view: a PR not behind needs no worktree and lands exactly as without the flag, and after a catch-up merge the review at the head passes through the clean merges. Prints three lines (the revert, the bug, the ticket), or with `--json` `{pr, sha, revert, ticket, bug}`. Its git calls in the main checkout run inside harness-pr, so branch_guard sees only `harness-pr revert`, as for `land`'s pull, and `revert_landed` sets `HARNESS_ALLOW_MAIN=1` in its own environment first, so the revert commit and the push of main pass the git hooks.

### The auto-land gate

`lib/harness_lib/autoland.py` decides whether a pull request may merge without Ryan; it merges nothing itself (`harness-pr gate` prints its verdict, and the work loop lands every PR but a `manual-land` one through `harness-pr land --catch-up --loop`). `evaluate(facts, settings)` takes the facts gathered about one pull request (`pr`, `state`, `draft`, `head_ref`, `head_sha`, `author`, `login`, `closing`, `pr_labels`, `incidents`, `deploy`, `ticket` with `number`, `state` and `labels`, `files` with a rename's old path included, `review` with `commit_id`, `at_head`, `unreadable` and the `high`, `medium` and `low` counts, `unresolved_threads`, `owner_comments`, `behind_by`, `mergeable`, `checks`, `failed_checks`, `pending_checks`, `nontest_files`, `nontest_lines`) and answers `{verdict, code, reason, rule}`. The rules run in order and the first failing one decides; inside a rule the first failing condition, in the order below, decides. N is the ticket's number.

| Rule | Fails when | Verdict/code |
|---|---|---|
| 1 | autoland is not on | manual/off |
| 2 | state is anything but `OPEN`; draft; the head is not `t/<N>-...`; the author is not the authenticated login; `closing` is not exactly `[N]` | manual/pr |
| 3 | any open incident (the reason names every one) | wait/incident |
| 3 | a deploy of main not `completed` (in flight), or `completed` with any conclusion but `success` (failed); no deploy workflow passes | wait/deploy |
| 4 | the ticket's state is anything but `OPEN` | manual/ticket |
| 4 | the ticket's risk labels are anything but exactly `risk:low` | manual/risk |
| 4 | no `size:` label, or any `size:` label outside the sizes | manual/size |
| 4 | `manual-land` on the PR or the ticket (the label refuses the loop's `harness-pr land --loop` too, exit 9: only the owner's `/harness:land` lands it, #451) | manual/label |
| 5 | a changed path matches a manual path | manual/path |
| 5 | more than 8 non-test files or more than 400 non-test changed lines (size labels are estimates; this is the backstop) | manual/too large |
| 6 | no harness review, or the latest one's first line is neither the counts line nor `Harness review: no findings.` (`unreadable harness review`) | manual/review |
| 6 | the latest harness review is not at the head (`review of <sha7>, head <sha7>`) | wait/re-check |
| 6 | a high or medium finding at the head (low findings land) | fix/findings |
| 7 | the conversation is longer than one page of any of its connections (`conversation too long to read: ...`) | manual/comment |
| 7 | an unresolved review thread or an owner comment | manual/comment |
| 8 | `mergeable` is `CONFLICTING` | fix/conflict |
| 8 | `mergeable` is anything else but `MERGEABLE` (`UNKNOWN`: GitHub has not computed it yet) | wait/mergeable |
| 8 | behind main | wait/behind |
| 9 | checks `pending` | wait/ci |
| 9 | checks `failure` (the reason names the failed checks) | fix/ci |
| 9 | checks anything else (`none` and any unknown value) | manual/checks |
| 10 | all passed | land/land (`gate passed at <sha7>`) |

`gather_facts(main, slug, pr)` gathers those facts with gh.py's sequential helpers and git, both in the main checkout `main` (origin already fetched): `gh api user --jq .login`; `gh pr view P --json number,state,isDraft,headRefName,headRefOid,author,closingIssuesReferences,labels,mergeable,statusCheckRollup` (the ticket N from the head `t/<N>-...`; checks through `check_entries` and `overall`, which harness-pr's checks and land use too); `gh issue list --label incident --state open --json number,title`; `gh run list --workflow deploy.yml --branch main --limit 1 --json status,conclusion,headSha` (none, or gh failing with the API's 404 for deploy.yml, `HTTP 404: workflow deploy.yml not found ...`, gives deploy null; any other failure, a 404 about another workflow included, is a failing call); `gh issue view N --json state,labels`; `gh api repos/O/R/pulls/P/files?per_page=100 --paginate --slurp` (`files` with a rename's old path; `nontest_files` and `nontest_lines`, each file once by its new path with additions plus deletions, outside the HARNESS_TEST_PATTERNS committed at origin/main, else settings.py's `DEFAULT_TEST_PATTERNS`); `gh api --paginate repos/O/R/pulls/P/reviews` (the latest harness review as in the review gate, counting only reviews whose `user.login` is the `gh api user` login, since anyone can type the marker; its counts from its first line, `Harness review (<model>): <n> finding(s), <h> high, <m> medium, <l> low.` or `Harness review: no findings.`, anything else `unreadable`); `gh api --paginate repos/O/R/pulls/P/commits`; the GraphQL `CONVERSATION` query (authors with `__typename`; one page per connection, each asking `totalCount` and `pageInfo { hasNextPage }`, and `conversation_truncated` names the review threads, reviews, PR comments or a thread's comments that a page left out, since the unread rest may hold an owner comment); `gh api repos/O/R/compare/main...<head sha> --jq .behind_by`. An owner comment is a PR comment or review whose body is not empty, holds neither `<!-- harness -->` nor `<!-- harness-review -->`, and whose author is not a bot (`__typename` `Bot` or a login ending in `[bot]`); an unresolved thread counts when it holds one. `at_head` is true when the review's `commit_id` is the head, or when, walking first parents back from the head through the PR's commits, every commit until the reviewed one (which must be among them) is a clean merge of main: two parents, the second an ancestor of `origin/main`, and its tree equal to `git merge-tree --write-tree <parent1> <parent2>` without conflicts (after `git fetch origin <headRefName>`; git 2.38 or newer). A failing call raises `GatherError` (`<call> failed: <first stderr line>`, the call named as gh.py's `describe` names it, or `git <words>`), carrying the facts gathered before it.

`gate_settings(main, ref="origin/main")` gives `{autoland, sizes, manual_paths, smoke_local}` read only from the `env` of `<ref>:.claude/settings.json` (settings.py's `committed_env`): the process environment, the working tree and `settings.local.json` never count, so turning auto-land on takes a reviewed commit on main. Values follow `setting`'s rule for a file value (a string or number, never a bool, stripped).

| Variable | Meaning | Default |
|---|---|---|
| `HARNESS_AUTOLAND` | `1` opts the project in | off |
| `HARNESS_AUTOLAND_SIZES` | comma-separated sizes that may land; a value holding anything but `S`, `M` or `L` is ignored | `S,M` |
| `HARNESS_MANUAL_PATHS` | comma-separated globs that always land by hand, added after the defaults (de-duplicated); nothing here removes a default | none |
| `HARNESS_SMOKE_LOCAL` | `1` runs the smoke check locally | off |

### harness-runner

Self-hosted CI on the Mac for the private registered projects (#420): GitHub bills hosted minutes on a private repository and lists self-hosted usage as free. One Linux container per repository in Docker Desktop, named `runner-<repo>` (the GitHub repository's name from the project's origin, so the containers set up by hand on 2026-11-20 keep their names), registered as `harness-mac-<repo>` with the label `harness-mac`; a private project's ci.yml runs on `[self-hosted, linux, harness-mac]` (harness-scaffold). PROJECT is a registered project's name or path (`find_project`); its origin must be on github.com. docker is `docker` on PATH, gh `HARNESS_GH` else `gh`. Failures are one line, exit 1.

- `add PROJECT [--memory 2g] [--cpus 2]`: refuses a public repository (`gh api repos/<slug>`: `private`, else `visibility`) with one line naming it public, before any token or container; refuses when `runner-<repo>` exists (upgrade re-creates it, remove deletes it). Builds the image when `harness-runner:<version>` is missing, then asks GitHub for a registration token (`gh api -X POST repos/<slug>/actions/runners/registration-token --jq .token`, read from gh's stdout), writes it with `RUNNER_URL` and `RUNNER_NAME` to a mode-600 env file in a mode-700 temporary folder, runs `docker run -d --name runner-<repo> --restart unless-stopped --memory M --cpus C --env-file F --mount type=volume,source=runner-<repo>,target=/home/runner/config harness-runner:<version>` and removes the file as soon as docker returns (the CLI reads it before then). The token is on no command line, in no environment of a process the tool starts, and in no output; inside the container it reaches `config.sh` once, and `docker inspect` shows it until it expires an hour later. Then it waits up to 60 s for `Listening for Jobs` in the container's log (a warning, exit 0, when it does not come).
- `list [--json]`: every registered project with a github.com origin that GitHub says is private, in registry order: `[{name, repo, container_name, container, github, busy}]`, `container` the docker state or `missing` (`unknown` when docker does not answer, with a warning), `github` GitHub's `online`/`offline` for `harness-mac-<repo>` or `missing`. The text form is a table whose offline rows say `PRs queue for up to 24 h`. A public project is never listed.
- `upgrade`: `docker build --pull` of the image again, then for each registered project's existing `runner-<repo>`: skipped when already on the new image id, when it has no volume at `/home/runner/config` (one set up by hand: remove and add move it) or when GitHub says it is `busy` (run upgrade again later); otherwise `docker rm -f` and the same `docker run` (or `docker create` for a stopped one) on the new image with its volume, memory, CPUs and restart policy, and no env file: no new token, no registration deleted.
- `remove PROJECT`: `docker rm -f runner-<repo>`, `docker volume rm` of its config volume (its registration names a runner about to be deleted) and `gh api -X DELETE repos/<slug>/actions/runners/<id>` for `harness-mac-<repo>`.

The image (`templates/runner/`): `Dockerfile` is `FROM ghcr.io/actions/actions-runner:<x.y.z>` (pinned; the tool tags the image `harness-runner:<x.y.z>` from that line) plus build-essential, git, jq, python3 and gh, and `/home/runner/config` made as the runner user's. `entrypoint.sh` configures once, then runs: `config.sh` writes the registration (`.runner`, `.credentials`, `.credentials_rsaparams`, `.env`, `.path`) into `/home/runner` beside the runner's binaries, so the volume cannot be mounted there (an empty named volume would be filled from the image once and then keep its old binaries through every upgrade); it is mounted at `/home/runner/config`, the first start copies the files into it and every later start, a re-created container's included, copies them back and skips `config.sh`, so re-creating a container keeps its registration. A named volume starts with the owner of the image's directory, hence the `install -d -o runner`.

Trust boundary: a workflow an agent writes runs on the Mac. Jobs run inside the container with no host mounts (only the named config volume) and no Docker socket, so a job cannot reach `~/.claude`, the keychain, a project's checkout or credentials, or another repository's runner; it holds the job's `GITHUB_TOKEN` and the repository's secrets, as on a hosted runner. Memory and CPU caps keep a job from starving the Mac. Public repositories never get a self-hosted runner, because a fork's pull request would run its code on the Mac: `add` refuses them and the scaffold gives them `ubuntu-latest`.

Standup and digest: `runner_checks(paths)` runs only when docker is on PATH and `docker ps -a` lists a `runner-*` container; then each project whose origin's repository has `runner-<repo>` gets one `gh api repos/<slug>/actions/runners` call (6 s), side by side. Without docker or without a runner container no gh call is made and nothing is added. A project whose runner GitHub reports `offline` or does not list (`missing`), or whose runner list cannot be read, gets one line, `- runner: runner-<repo> is offline on GitHub (container exited): its pull requests' CI queues, for up to 24 h, instead of failing; ...` (standup, under the project's heading; digest, a `### Runner` block under it), and the project's JSON a `runner` object (`container`, `state`, `github`, `error`); a project without a runner container has no `runner` key. When docker is on PATH but `docker ps` fails, both add a `## Runners` section with one line (start Docker Desktop) and set the top-level `runners_error`. A private project with no runner container is not flagged (finding it would cost a visibility call per project). `harness-work budget status` does not report runners.

### harness-standup, harness-projects, harness-worklog

`harness-standup` adds, per project and inside the existing time budget (gh calls run in threads, 6 s): `Board: r ready, p in progress, v in review, q needs input` (only for a project whose `origin` is on github.com); `PRs awaiting you:` lines; `Needs input:` lines (title, first line of the question); `Stale worktrees:` lines; for every project whose `origin` is on github.com, whether or not gh is found or answers (it reads only local state), `- learn: last run 9d ago; run /harness:learn` or `- learn: never run; run /harness:learn` when `last_run` in `repos/<repo-key>/learn.json` is older than 7 days or none is recorded (#424), and in `--json` that project's `"learn": {"last_run": ISO or null, "due": bool}` (null for any other project); and after the fleet section a `## Budgets` line when any budget is exhausted and a `## Runs` section for headless runs alive or failed in the last day. `harness-projects` is unchanged. `harness-worklog` reads the transcripts of the repo's own `~/.claude/projects/` folder and of every folder for a worktree under `<repo>/.claude/worktrees/` (removed worktrees included), counting each entry of a session id found in several files once; `--transcripts <folder>` still reads that one folder alone. Run from inside a linked worktree (by `--repo`, `CLAUDE_PROJECT_DIR` or the cwd), it works on the main checkout, so the log never lands on a ticket branch. `harness-worklog` counts as the user's own message any non-empty user text that does not start with a tag or whose leading tag, by exact name, is `pasted_content`, `bash-input` or `command-name` (or `command-message` with a `<command-name>` later in the text), so pastes, `!` commands and slash commands bill their block while task notifications, system reminders, local command output, `isMeta` and compaction summaries do not.

Hours per ticket (#59). Each transcript entry belongs to a ticket: its folder's when that is a worktree `<repo>/.claude/worktrees/t-N-<slug>`, else its `cwd`'s inside such a worktree, else its `gitBranch` `t/N-...`, else the ticket of the `/harness:work N` turn it is in (from that typed message to the session's next message the user typed, which ends it unless it is itself a `/harness:work N`); anything else (the main checkout on main, a worktree not named `t-N-*`) is unattributed. Within a counted block the stretch between two entries goes to the later entry's ticket, so a block across several tickets is split by message time. A day's logged hours are apportioned to its tickets and its unattributed time in proportion to their minutes, each to the quarter hour by largest remainder (ties to a ticket, then the lower number), so a day's ticket hours never exceed its logged hours and the parts add up to it exactly. After writing the log, `update` records every ticket with an entry on a day it recomputed (held days excluded), including one whose share of each such day rounds to 0, in the repository of the repo's `origin` on github.com (none, or another host: one line saying the tickets were not recorded, exit 0): `gh api user` for the login, then per ticket `gh api repos/O/R/issues/N/comments --paginate --slurp`, and the login's own comment containing `<!-- harness-hours -->` is edited in place (`PATCH repos/O/R/issues/comments/ID`), or created (`POST`) when the ticket has none and has hours. The comment is one markdown table, one row per day `| yyyy-mm-dd | H.HH |`, oldest first, and a Total row of those rows; the rows of the recomputed window (its dropped days included) are replaced by the recount, a day at 0 hours having no row, the rest kept; an unchanged body is not written, so a re-run changes nothing. A gh failure (the login, or one ticket) is a `harness-worklog: warning:` line on stderr and never the exit status: the log is the bill and is already written, and the next `update` within the window rewrites the comment from the recount.

`harness-worklog invoice --month yyyy-mm [--out-dir DIR]` (default `<repo>/worklog/invoices`) reads every issue of the origin's repository (`gh issue list --state all --limit 5000 --json number,title,parent,comments`) and keeps the login's hours comment on each, then writes `DIR/invoice-<month>.csv` with columns `date, epic, ticket, title, hours, resolution`: one row per ticket and day of the month (`ticket` the bare number, `epic` its parent's number or empty, `resolution` the first paragraph of its newest `**Resolution**` comment by the login, on one line), one row per day with `ticket` `unattributed` for the day's hours in `worklog/worklog.csv` (manual rows included) less its tickets' hours (the day's descriptions as its resolution), and one `Total` row; the rows add up to the month's hours in the log. A day whose tickets carry more than the log is a warning, its negative remainder kept so the total still reconciles. `DIR/invoice-<month>.md` has the same rows by epic (with the epic's title), by ticket and by day. Without a GitHub origin every hour is unattributed, with a warning; a gh failure exits 1 and writes nothing. The `/harness:invoice [--month yyyy-mm]` skill runs it (default the previous month) and reports the totals.

### The gh shim

`plugins/harness/shim/gh` (#448), an executable python3 script, logs the gh calls no harness tool makes: an agent's own `gh` in Bash, a poller. Claude Code puts a plugin's `bin/` on the Bash PATH after the user's own PATH, so a `gh` there would never be reached before Homebrew's; the shim lives in a folder of its own, `shim/`, which session_brief's SessionStart line in `CLAUDE_ENV_FILE` puts first on PATH (Hooks, session_brief.py). It runs the first executable `gh` on PATH whose folder's real path is not the shim's own folder's real path (so the shim's folder is skipped wherever and however often it is on PATH, through a symlink too), with its argv unchanged and stdin, stdout and stderr inherited (the same open files, never captured), waits and exits with that gh's exit code (128+N when a signal N killed it); with no other gh, one line on stderr and exit 127. It ignores SIGINT while it waits (the gh, in the same process group, gets the terminal's own) and passes SIGTERM and SIGHUP on. After the call it logs one line through `ghlimit.log_call(args, cwd=None, exit=<code>, ms=<ms>, tool="agent")` (repo and ticket from the cwd and `PWD`), unless `HARNESS_GH_LOGGED` is set and not empty (a harness runner's child: gh.py, which logs the call itself). It loads harness_lib from its real path's `../../lib` only after the call returns, so a call pays no import before it starts; a lib that cannot be loaded and a log that cannot be written (any exception) are skipped silently, so the shim never changes a call's output or exit.

## Canary

## Daily use

- **New project**: `/harness:new-project ~/Projects/<name>`.
- **Plan**: `/harness:plan <request>` interviews you and writes the epic and tasks on the board as `status:proposed`; `harness-board promote <epic#>` makes them ready.
- **Work**: `/harness:work` dispatches every ready ticket; `/harness:work 12` runs one here. Notifications tell you when a PR is ready or a ticket needs you.
- **Answer**: reply on the ticket; the next `/harness:work 12` reads it.
- **Land**: every ticket's PR lands at the end of its `/harness:work` run, at any risk; a ticket the loop cannot land is parked. `/harness:land` lists the PRs awaiting you; `/harness:land 7` lands a parked one you choose and cleans up. `harness-board status 12 ready` unparks ticket 12 for the loop.
- **Morning**: `/harness:standup`; the digest arrives at 08:30 on its own.
- **Lessons**: `/harness:learn` files proposed chore tickets. **Context**: `/harness:handoff` before `/clear`. **Hours**: `/harness:worklog`; the month by ticket for the invoice: `/harness:invoice`.
