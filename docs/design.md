# Harness design, v2

Ryan's personal Claude Code harness. One repository, one plugin, installed once at user scope, applied to every project. v2 written 2026-10-13 against Claude Code 2.1.296 (installed from the latest channel that day; the per-call Agent `effort` parameter arrived in 2.1.292), gh 2.99.0, git 2.39. v1 (2026-10-06) is in git history; what changed and why is in `docs/research/` and in the interview notes at the end of this file.

## Principles

1. **The board is the context.** Every unit of work is a GitHub issue: an epic with sub-issue tasks, each carrying the request, an outline, a definition of done and the tests that must pass. Agents read the ticket and its epic before working and write status back. The user's job is to answer questions on tickets and review pull requests.
2. **Tests before code, proven.** A test-author writes tests from the ticket; a tool proves they fail against the unchanged code; an adversary tries to pass them with a trivial implementation; only then does a coder touch source. A hook denies source edits until the proof exists.
3. **Never on main.** Each ticket gets its own branch and worktree. A hook denies edits, commits and pushes on main in every repository. GitHub Free does not protect branches on private repos, so the hook is the only block; landing goes through a pull request the user lands (`/harness:land`, or approving a session's `harness-pr land` prompt); `harness-pr autoland` for eligible ones is the epic #132 plan.
4. **Route by labels, escalate by failure.** Opus 5.5 at high effort is the default everywhere. The planner labels each task with size and risk; the labels pick the tier and effort (Sonnet, Opus, or Opus at xhigh for size:L or risk:high; never Fable) unless the project's `HARNESS_CODE_TIER` or `HARNESS_REVIEW_TIER` sets it for that stage, and `HARNESS_CODE_EFFORT` sets the coding stages' effort. A second failure re-runs one step up (Sonnet to Opus, Opus to Opus at xhigh); a third, or a second already at Opus xhigh, stops and asks on the ticket. Fable runs only when a setting names it or Ryan launches it.
5. **Spend the subscription first.** Interactive sessions and dispatched ticket work run on the Max subscription by default. The API key is spent only on request: `harness-work dispatch --api` (an alias for `--venue headless`) runs headless and bills it. While the `api` budget is exhausted, `--api` and `--venue headless` are refused. High-risk pull requests get ultrareview, which bills claude.ai usage credits. An exhausted budget is remembered for a day.
6. **Additive, never invasive.** Projects keep their own `CLAUDE.md`, hooks, rules and skills. The harness adds the board, the guards and the loop beside them, in every project including jotform-glow-sync.
7. **Deterministic where it must be, advisory where it can be.** Hooks and tools enforce; prompts advise.
8. **Fail open, except where a guard is sure.** A hook that hits its own error exits 0 and says so on stderr. The guards deny only when they have established the branch and the path.
9. **Standard library only.** `python3` 3.9 or newer, `git`, `gh`. Nothing to install.
10. **Hooks run outside the sandbox**, with the user's permissions and no prompt. The verify and test commands must be commands the user trusts.

Code shared between files lives in `plugins/harness/lib/harness_lib` (python3 standard library, `from __future__ import annotations`), loaded in place from the checkout with no install step. A file finds it relative to its own real path: a seven-line prologue at module top, after the standard-library imports, puts `os.path.realpath(__file__)`'s `../lib` first on `sys.path` (so a symlink still reaches the checkout, and neither a hooks/-local file nor a project file can shadow it; a file copied out of the checkout does not find it) and binds the names it uses in its own namespace (`from harness_lib.paths import canonical_path, ...`), never through `CLAUDE_PLUGIN_ROOT`.

Fail open: a hook that cannot load the lib (missing, a syntax error, an import that raises) writes `<hook>.py: cannot load harness_lib from <lib>: <error>` to stderr in one line and exits 0, so the call is allowed; notify.py also prints the bell (`{"terminalSequence": "\u0007"}`, as when `notify` answers False), because a Notification hook's stderr reaches no one; session_brief instead goes on without ticket state and puts one `Warning:` line naming harness_lib in the brief, because the guards are then off and a SessionStart hook's stderr reaches no one; in a project that declares its own SessionStart hook, where the brief is otherwise silent, that warning line is its whole output. The bin tools do not fail open: a bin tool that imports the lib (every one but harness-scaffold) prints `<tool>: cannot load harness_lib from <lib>: <error>` in one line and exits 1 before it parses an argument, because it must not guess a state key.

Every bin script is otherwise standalone (no imports between scripts): argparse, standard library, finds nothing through `CLAUDE_PLUGIN_ROOT` (that variable is not set for Bash). Scripts compose by calling each other on PATH and exchanging JSON (`--json`). A script that must call another finds it next to itself (`Path(__file__).resolve().parent`) when it is not on PATH. Each prints one line and exits 1 on a bad invocation or a failed precondition, never a traceback. `gh` is resolved as `os.environ.get("HARNESS_GH", "gh")` so tests can substitute a fake.

Install (once): `sh scripts/install.sh`. A marketplace added from a local path loads the plugin in place, so edits take effect at the next session start or `/reload-plugins`.

## Platform facts this design relies on

Verified 2026-10-13 from the Claude Code docs, the gh source at v2.99.0 and the GitHub docs; details in `docs/research/`.

- Plugin agents support `model` (alias, full id or `inherit`) and `effort`; they ignore `hooks` and `permissionMode`. The Agent tool takes `model` per call and, since 2.1.292, `effort`. An agent that omits `effort` runs at the session's level.
- `"model": "opus"` in settings resolves to Opus 5.5. `modelSettings` is keyed by canonical ids (`claude-opus-5-5`, `claude-fable-5-1`, `claude-sonnet-5-5`); a top-level `effortLevel` does not apply to Opus 5.5.
- PreToolUse receives `cwd`, `session_id`, `agent_type` (`harness:coder` for plugin agents), `tool_name`, `tool_input` (`file_path` absolute for Edit and Write, `notebook_path` for NotebookEdit, `command` for Bash). It denies with `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny", "permissionDecisionReason": "..."}}`; deny wins over every other hook. SessionStart carries no branch; its `cwd` is the worktree root when the session runs in one.
- `claude -w <name>` creates `.claude/worktrees/<name>` on branch `worktree-<name>` and cannot pick a branch name; `git worktree add` is the way to control the branch. `claude --bg -n <name> "<prompt>"` starts a background session in the cwd with the supervisor's stored login; trust is inherited from the main checkout; a session already in a linked worktree does not self-isolate. `claude rm` leaves a user-created worktree in place.
- Billing: `ANTHROPIC_API_KEY` and `apiKeyHelper` outrank the subscription login; in `-p` mode the key is used without a prompt. Background sessions cannot be billed separately. Cloud sessions and routines bill the subscription, need a TTY to start, and do not load plugins. `claude ultrareview <PR> --post --json` runs in the cloud, bills usage credits (about 5 to 25 dollars a run), and prints findings.
- Auto mode (verified 2026-10-24 on 2.1.310; `docs/research/auto-mode-classifier.md`): narrow Bash allow rules such as `Bash(harness-pr:*)` are resolved before the classifier, while a rule that ends in `:*` is read as a literal prefix, so `Bash(harness-*:*)` never matched a `harness-*` call; a compound call (pipe, redirect, `;` or `&&`) still reaches the classifier when one of its parts (`tail`, `head`, `python3`, `echo`, ...) matches no allow rule (116 of 116 on 2.1.310, 0 rule path), while one whose every part is covered (`cd`, `git`, `gh`, a `harness-<tool>`) usually takes the rule path (28 of 41 on 2.1.310; what sends the other 13 to the classifier is unknown). `autoMode` is read from `~/.claude/settings.json` only, not from the project file. A linked worktree and its main checkout therefore share one state directory, and so does every spelling of the path on a case-insensitive file system (macOS: `portfolio_projects/Harness` and `portfolio_projects/harness`). The helpers `canonical_path`, `same_entry`, `path_key`, `repo_key` and `adopt_old_state` are defined once, in `lib/harness_lib/paths.py`. The hooks session_brief and tests_first import all five and branch_guard imports `canonical_path` and `same_entry`, each binding the names in its own namespace; none keeps a copy, so without the lib a hook computes no key of its own (it fails open, above). The tools harness-board, harness-pr and harness-work import all five; harness-red imports `canonical_path`, `repo_key` and `adopt_old_state`; and harness-standup and harness-digest (which only key run files and never migrate a directory) import `canonical_path`, `same_entry`, `path_key` and `repo_key`. Migration from the spelling-based key: before the key was canonical it was the sha1 of the real path as spelled. Red record `red/<branch-slug>.json`:

```json
{"branch": "t/12-slug", "base_sha": "<merge base>", "test_files": ["tests/test_x.py", "tests/conftest.py", "tests/fixtures/a.json"],
 "run_files": ["tests/test_x.py"], "test_hash": "sha256 over path + newline + bytes of every test file, sorted",
 "cmd": "...", "exit": 1, "kind": "assertion|import|error|green", "tail": "last 40 lines", "at": "..."}
```

`test_files` is every changed path matching `HARNESS_TEST_PATTERNS` (fixtures and `conftest.py` included) and all of them are hashed; `run_files` is the subset passed to the test command, those whose basename matches `test_*.py`, `*_test.py`, `*.test.js`, `*_test.js`, `*.test.ts`, `*_test.ts`, `*.test.mjs`, `*.spec.js` or `*.spec.ts`. A change with no runnable file is refused.

A record is **current** (#231) when its test files hash to `test_hash` now, or when they are exactly the red-time files with main's changes since `base_sha` merged in: a merge of main (or a rebase) that brings in main's edits to the branch's test files keeps the proof, while a test change of the branch's own does not. harness_lib's `redproof.py` (`record_current(root, record, record_path, timeout)`) decides it for both harness-red `status` and tests_first, so the two agree on the rules; only their budgets differ: `status` gives it 30 s, tests_first what is left of its one deadline (tests_first, below), and it answers `current`, `stale` or `unknown` (`record_state`; the budget ran out first). `status` prints `unknown` as `current: no`; tests_first denies it with its own message. So on a slow git the hook can refuse an edit, asking for a retry, while `status` says `current: yes`; never the other way round. `check` keeps the red-time bytes of the test files in a side file, `red-files/<branch-slug>.json` beside `red/` (`{"test_hash", "files": {path: base64}}`, written just before the record); it counts only when it holds exactly the record's `test_files` and they hash to the record's `test_hash`, so an edited or stale side file proves nothing. A record without a valid side file (one written before it existed) has its red-time bytes recovered per candidate base by taking main's change back out of each file (`git merge-file -p --ours <now> <new base> <old base>`); the recovered set must hash to `test_hash` too, and goes through the same forward replay. When the hash differs, the new merge base is that of `refs/remotes/origin/main`, then `refs/heads/main` (the refs `check` defaults to, spelled in full so a tag or another ref named `main` cannot stand in; the record keeps no ref), each taken at the commit its newest reflog entry set and only when that entry is one the harness trusts (Trust boundary, below), with HEAD (`git merge-base <tip> HEAD`), with `MERGE_HEAD` added while a merge is in progress (`git merge-base <tip> HEAD MERGE_HEAD`, the base the merge commit will have, so a source conflict can be resolved mid-merge). A candidate counts only when it differs from `base_sha` and descends from it (`git merge-base --is-ancestor`): an older base (a stale local main, a record made with `--base` a stacked parent) would let the branch undo main's edits. Each test file must then be exactly its red-time bytes with main's change merged in (a file main left alone, or deleted, must be its red-time bytes): first `git merge-file -p --ours <red-time> <old base> <new base>` (Myers, no objects written); for the files where that differs, git's own merge (ort, histogram), as `git merge-tree --write-tree <synthetic> <new base>` (git 2.38+), where the synthetic commit is the old base's tree with the red-time blobs, its parent the old base, so the merge base is the old base. Its blobs, trees and commit go to a temporary object directory (`GIT_OBJECT_DIRECTORY`, reading the repository's through `GIT_ALTERNATE_OBJECT_DIRECTORIES`, with a temporary `GIT_INDEX_FILE` and a fixed identity and date), so the repository's object store and index are untouched; it costs eight git calls (rev-parse, hash-object, read-tree, update-index, write-tree, commit-tree, merge-tree, cat-file), about 0.3 s, only when merge-file has not matched every file; a conflicted ort merge counts for nothing (merge-file's `--ours` covers that case). Before it: one rev-parse for `MERGE_HEAD`, a merge-base and an is-ancestor per ref, one `cat-file --batch` per candidate and one merge-file per changed file (two without a side file: the recovery, then the replay). The inputs are fixed (bytes proven by `test_hash`, two commits of main), so a match pins every byte of the file now and nothing the branch does can satisfy it but the replay itself; a replay that differs from git's real merge can only give a false "not current", never a false "current". A known limit: the replay merges once, from `base_sha` to the newest merge base, while git merged each merge of main in turn, so after several merges a later edit of main's that lands next to an earlier merge's hunk can, rarely, merge differently; that reads as not current (a false deny, never a false allow); the recovery is below. The branch's own lines are thus compared by position against the new base, not by content: an edit, a move, a swap or a merge resolution that changes the branch's lines (main's side kept, a third value, the branch's line moved elsewhere) leaves the record stale. `--ours` settles a conflict the way git's `-X ours` would: a resolution that keeps the branch's own lines verbatim and drops main's conflicting edit of them keeps the record, as taking the branch's whole file (`git checkout --ours`) always did through the hash; any other resolution of a conflict does not. A `base_sha` that is not a commit id (40 hex digits, or 64 in a `--object-format=sha256` repository) or not a commit here (a hand-written `"0" * 40`) gets the whole-file comparison only. Any git failure counts as not current, a timeout as `unknown`.

Recovering from a false "not current" on a branch that has source: running `harness-red check` again does not help. It refuses with `Source already changed before the red run` and leaves the record as it was; `check --base HEAD` sees only uncommitted changes, so it needs a new, failing test change and records only those files, and with tests that pass at HEAD it writes a green record, which then refuses every source edit. The real recovery re-proves the branch's tests as they are now against main's code, by hand from a clean tree in the ticket worktree (the orchestrator or the user; the coder and the test-breaker are refused these git forms):

```sh
head=$(git rev-parse HEAD); base=$(git merge-base HEAD origin/main)
git diff --name-only "$base" "$head"     # pick out the test files (HARNESS_TEST_PATTERNS) the branch changed
git reset -q --hard "$base"               # main's code at the merge base
git checkout "$head" -- <those test files>
harness-red check                         # red: a new record at $base
git reset -q --hard "$head"               # the branch as it was; its test files hash to the new record
```

It proves whatever the tests are now, so first read `git diff <base_sha> HEAD -- <test files>` and run it only when that difference is main's.

Trust boundary. The red proof stops an agent's shortcuts, not an agent set on getting round it. The state directory `~/.claude/harness/repos/<key>/` lies outside every repository, so neither branch_guard nor tests_first judges a write to it: an agent can write a red record, a side file or a ticket cache with `no-tests` itself, which gives more than any forged ref. Within that boundary a merge of main adds no easier way round: a ref counts at the commit its newest reflog entry set, and only when that entry is a fetch or pull from `origin` (named or the default) whose refspecs name no destination or take `main` to one, a push or a clone, and, for `refs/heads/main` (the user's own checkout), a commit, merge, rebase, reset or branch creation. That stops `git update-ref <ref> <commit>` (no message), `git fetch . <commit>:<ref>`, a fetch of another remote or another branch into the ref, `git branch -f`, a tag named `main` or `origin/main`, and a write to the ref's file (no reflog entry). It does not stop `git update-ref -m "fetch: fast-forward"`, a hand-written reflog line, or `git remote set-url origin` to a repository of the agent's own followed by a fetch. A ref with no reflog (`core.logAllRefUpdates=false`, or an entry gc expired) names no base: a false "not current" until the next fetch. Neither the hook nor `status` asks the remote.

Tier rubric, implemented once in `harness_lib/routing.py` (`label_tier`) and reported by `harness-board tier`: `size:S` and `risk:low` and type not `bug` gives `sonnet`; everything else gives `opus`, and `size:L` or `risk:high` gives it effort `xhigh` (`label_effort`). The labels never give `fable`. Escalation (`next_route`) goes sonnet to opus, opus to opus at `xhigh`, and stops there: a second failure at opus `xhigh` or `max`, or on an explicitly set `fable`, is `needs-input`. The review stage has its own rule, `harness-board tier N --stage review`: `opus` for every ticket, at effort `xhigh` for `risk:high`. A project's routing settings (Settings, above) replace the rubric: `HARNESS_CODE_TIER` is the code tier whatever the labels say, so it is the tier `tier`, `show`, the ticket cache, `ready` and an epic's task rows carry and the one `harness-work attempt` escalates from, and it replaces the labels' effort too (`HARNESS_CODE_EFFORT`, when set, is the effort either way); `HARNESS_REVIEW_TIER` is the review tier whatever the labels say, their `xhigh` included.

### The work loop (one ticket, in-session)

```
harness-work start N            ticket context, branch t/N-slug, worktree, status in-progress, tier
harness-board tier N --json     tier and effort for the test-author, breaker and coder: HARNESS_CODE_TIER and
                                HARNESS_CODE_EFFORT when set, else the labels; effort passed when not null
test-author (tier)              tests only; must show them red
harness-red check               proof: tests fail, source untouched; record written
test-breaker (tier)             scratch copy; cheat attempt; pass means tests go back to the author (max 2 rounds)
coder (tier)                    source only; new tests and CLAUDE_VERIFY_CMD green; commits
reviewer (opus; xhigh if risk:high) findings JSON; split by the ticket's files: the rest become new tickets;
                                model and effort from harness-board tier N --stage review --json (HARNESS_REVIEW_TIER
                                when set, else the labels)
harness-pr open N [--notes F]   push, draft PR from the template (Closes #N, DoD, red proof, verify tail); --notes adds a `## Notes` section (second pass, out-of-scope file) that the Resolution repeats
harness-pr review P --findings  inline review comments from the findings on the ticket's files
coder (tier)                    fixes every posted finding, whatever its severity, in commits after the review;
                                push; the reviewer re-checks and its findings are posted again
harness-work attempt N fix      after each fix round: pass when the re-check found nothing on the ticket's files;
                                retry, then needs-input (max 2 rounds, no escalation)
harness-pr checks P --wait      CI; failures go back to the coder (max 2 rounds)
[harness-pr ultra P]            when risk:high: ultrareview, posted to the PR; with HARNESS_ULTRAREVIEW=off one line,
                                nothing run
harness-pr ready P              refused while the latest harness review has findings and no newer commit;
                                ready for review, status in-review, notification
```

Every review finding on the files the ticket touched is fixed before `harness-pr ready`, whatever its severity; only a finding outside the ticket's files becomes a new ticket, and the PR body names it and says why. The skill is one turn, every agent in the foreground: it ends at ready, a posted needs-input question, a `harness-work start` refusal, or the final failure `harness-work attempt` records; without a ticket number, once dispatch has launched the runs, shown its `--dry-run` plan or found no ready tickets.

A ticket whose `flags` (from `harness-board show N --json`) hold `no-tests` skips the test-author, `harness-red check` and the breaker: the coder implements against the definition of done, the verify command must still pass, and the review still runs.

Failure policy, enforced by `harness-work attempt`: the first failure of a stage retries at the same tier and effort; the second re-runs one step up the ladder (sonnet goes to opus, opus goes to opus at effort xhigh), except that a second failure at opus xhigh or max, or on an explicitly set Fable, goes straight to needs-input, since nothing is above it; the third calls `harness-board needs-input` with the evidence and stops. No escalation goes to Fable. `fix` and `breaker` have their own rule, two rounds each: the first failure retries at the same tier and the second calls `needs-input`, with no escalation. A stage is `tests` (red cannot be reached), `breaker` (the cheat still passes after the second round: needs-input), `code` (verify not green), `review` (the reviewer returned no usable findings; a findings array of any length, empty included, passes), `fix` (findings on the ticket's files still open after a fix round's re-check), `ci` (checks red), `verify` (the full verify before ready is red). Each stage counts its own failures: a run of failures ends at that stage's next pass, and another stage's result neither adds to it nor resets it.

Every Agent call the work skill makes carries the description `#N <stage>`, which `harness-work cost` reads (`^#(\d+)\b` and the word after it): `tests` for the test-author (in a revise pass too), `breaker`, `code` for the coder until the first review, `review` for the first review, and `fix` for every coder or reviewer run after the first review (its findings, CI failures, ultrareview findings, the owner's comments). A continued (SendMessage) agent's transcript is split at the coordinator's continuation entries into segments, each its own round, and a code or review segment starting after the end of the ticket's first review counts as `fix`, except segment 1 of an agent whose description names its stage. Any question the agents cannot answer from the ticket, the epic or the code also ends in `needs-input`. A revisit of a ticket with `status:needs-input` and a newer comment by the repository owner passes that comment to the agents as the answer. A revisit of a ticket in `status:in-review` with unresolved review threads from the owner runs the coder on those comments only, then checks and ready again.

Writes `repos/<repo-key>/cost/<N>.json`, replacing an earlier one: `{"ticket", "title", "repo", "computed_at", "type", "size", "risk", "tier", "pr", "rows", "totals", "by_model", "session_totals", "sessions", "rounds", "needs_input", "lines", "elapsed", "ci", "landed_at", "coverage"}`. `rows` to `sessions` are `ticket_usage`'s; `pr` is `--pr`, else the pull request found on the cache's branch, else null; title to tier and `rounds` are null without a ticket cache; `coverage` is the lower-bound note. The gh-backed parts (gh run in the main checkout): the PR is `gh pr view P --json number,url,createdAt,mergedAt,headRefName` with `--pr`, else `gh pr list --head <cache branch> --state all --json ... --limit 10`, its latest merged one first, else its newest (no branch: no PR). `lines` is `{"test", "source", "other": {"added", "removed"}}` summed over every file of `gh api repos/{owner}/{repo}/pulls/P/files?per_page=100 --paginate --slurp`: test when the path matches HARNESS_TEST_PATTERNS, else other when it matches HARNESS_SOURCE_EXEMPT, else source, each setting from the environment, else the main checkout's `.claude/settings.json` `env`, else settings.py's `DEFAULT_TEST_PATTERNS` and `DEFAULT_SOURCE_EXEMPT` (harness-red's strings). `ci` is `{"runs", "failed", "cancelled", "total_s", "median_s"}` over the completed runs of `gh run list --branch <the PR's headRefName> --json databaseId,status,conclusion,createdAt,startedAt,updatedAt --limit 100` (the cache's branch when `gh pr view` fails): failed is conclusion failure, timed_out or startup_failure, a run lasts updatedAt minus startedAt (createdAt without one), median_s is whole seconds (null without a run). `gh issue view N --json comments,labels` gives `needs_input` (comments starting `**Needs your input**`), the ready time and the type, size and risk the cache lacks. `elapsed` is `{"started_at", "pr_opened_at", "ready_at", "landed_at", "start_to_ready_s", "start_to_land_s"}`: the cache's started_at, else the earliest `Started on ` comment; the PR's createdAt; the earliest comment starting `PR #<P> ready for review`; mergedAt; a span null when an end is missing; the whole part null when nothing is known. `landed_at` repeats mergedAt. No PR: `lines`, `ci` and the PR times are null. A failed gh call leaves only its part null and prints one stderr line naming the call; the record is still written and the exit is 0. `rounds` replays the attempt store with `attempt`'s rule (`cost.attempt_action`, shared by both): `{"stages": {stage: {"runs", "fails", "retry", "escalate", "needs_input"}}, "breaker_rerounds", "fix_rounds"}`, each stage counted on its own in attempt order, a pass ending its run of failures; only stages with attempts are listed; breaker re-rounds are breaker fails and fix rounds fix attempts. - `dispatch [--max 10] [--venue headless|bg | --api] [--dry-run]`: `--api` is an alias for `--venue headless`, and `--api` with `--venue bg` is an argument error. First `runs --sweep` (below), then the budget check: when `api` is exhausted after the sweep (the sweep can be what marks it) and `--venue headless` or `--api` was given, refuse with a non-zero exit, `--dry-run` and an empty board included, naming the time it is exhausted until and `harness-work budget reset api`, and start and launch nothing; then `harness-board ready`; skip tickets that have a live run; for each remaining up to `--max` minus live runs: `start N`, then launch. A live run is an unended record whose headless process is alive, or whose `--bg` session `claude agents` lists in a live state (`running`, `working`, `blocked`, `idle`, `busy`, `waiting`, `starting`; any live state while the listing cannot be read). The sweep has already closed (and stopped) a `--bg` session whose ticket is finished, so such a session holds no slot, `--dry-run` included, and `--max N` plans N minus the truly live runs; a `blocked` session of a ticket that is not finished stays live and holds one:

An invalid value is ignored with one `harness-work: HARNESS_CODE_EFFORT=... is not one of ...; ignored` warning on stderr per command (a `--dry-run` and an empty board included; stdout stays clean under `--json`). - `runs [--sweep] [--all]`: lists run records with state (alive, exited N, done, `ended early (draft PR #N)`, `ended early (no PR)`). `--sweep` updates records whose process has exited: reads the log tail and sets `outcome` (`ok`, `early`, `billing`, `auth`, `error`), or for a `--bg` run maps its `claude agents` state (`done` → `ok`, `failed` → `error`, `stopped` → `stopped`). The ticket, not the state, says when a `--bg` turn is over, because the bg supervisor marks a finished session `blocked` (not `done`) when its summary of the final reply suggests a next step for the user (#123): a ticket is finished when its issue is CLOSED (whatever labels it kept, `status:in-progress` included) or OPEN with `status:in-review` or `status:needs-input`; in progress, ready, blocked or without a status label it is not. A session whose ticket is not finished is never stopped and a live state keeps its record open; when the repository or gh cannot read the ticket, one warning, and the session is neither stopped nor counted ended (an ended state still closes its record, `ok` without the early check). An `ok` run, headless or `--bg` (a `failed` or `stopped` one never), whose issue is OPEN and still `status:in-progress` with no ready pull request of its branch in any state (none, or only drafts: a draft counts as no ready pull request; a row without `isDraft` is not a draft) becomes `early` (the session ended its turn before the work did), whatever the log says, and the record keeps the newest open draft as `draft_pr`, shown as `ended early (draft PR #N)` (an `early` state is shown in place of `exited N`); when gh cannot tell, or the record names no repository, it stays `ok` with a warning, and one command asks gh once per ticket and branch (dispatch's sweep and its redispatch share the answer); `exit` is set only for `--bg` runs when the `claude agents` listing provides it, otherwise it stays null (a reparented headless child leaves no exit code). With a JSON result (`claude -p --output-format json`; its `subtype` says `success` even on an API error): `is_error` not true → `ok`; an API failure (`terminal_reason: "api_error"` or an `api_error_status`) → `auth` on 401 and 403, `billing` on 402, `error` on 429 and 5xx whatever the text, otherwise by the `result` text, which then holds claude's own message (`^(Credit balance is too low|Your credit balance|insufficient credits|billing)` → `billing`; `^(Invalid API key|Not logged in|authentication)`, a 4xx naming the key `^API Error: 4\d\d .*API key` (not 429), `apiKeyHelper script is failing` or `anthropic-workspace-id` anywhere → `auth`, a credential that can never work), else `error`; any other `is_error` → `error`, and the result text, the model's own words then, is never read. Without a JSON result (a crash before one), the tail's API-error lines decide: `credit balance|insufficient.*credit|billing_error|payment required|402` → `billing`, `invalid.*api.key|authentication_error|401` → `auth`. A `billing` or `auth` outcome on a headless run marks `api` exhausted for 24 h with the status and message (or the matching line) as reason, and until then `dispatch --api` and `--venue headless` are refused. A ticket whose run ended without a ready PR (`early`, or any other ended outcome) and is still `status:in-progress` is re-dispatched by the next `dispatch` (`again after <outcome>` in the plan, `again after <outcome>, draft PR #N` when an open draft exists), until 3 of its runs ended within 7 days; a run whose outcome is `billing` or `auth` does not count (the budget's failure, not the ticket's: after `budget reset api` or on `bg` the ticket goes again), every other ended run does, a null outcome, `stopped` and `unknown` included. When an open draft exists, the launch prompt (`/harness:work N` followed by a paragraph) and a start comment on the issue name the PR and say the worktree may hold uncommitted work from the previous run, so the run reads `git status` and the PR's review comments first; otherwise the prompt and the start comment are the plain ones. Past that cap, dispatch skips the ticket with `<runs> runs ended without a ready pull request in 7 days (last: <outcome> at <ended_at of the latest-started run>); run it in this session with /harness:work N, or wait for the window` (`--json`: `{"number", "why", "runs", "window_days": 7, "advice": "/harness:work N"}`; `<runs>` and `runs` are the counted runs, billing and auth left out), since a run in the session you are watching is the way forward. `runs` appends `capped` to the STATE of that latest-started record (`runs --json`: `"capped": true`, `state` unchanged) for exactly the tickets dispatch would skip by the cap in this repository: no live run, the latest run ended inside the window, the issue open and `status:in-progress` with no ready pull request of its branch (when gh cannot tell, no mark); `runs` asks gh only about tickets at the cap.

- `check [--base origin/main]`:
  1. `merge-base HEAD <base>`; changed paths = `git diff --name-only <merge-base>` plus `git status --porcelain` untracked and modified. Test files = those matching `HARNESS_TEST_PATTERNS`; none → `No test changes on this branch; write the tests first.` exit 1.
  2. Source files changed (not test, not exempt) → `Source already changed before the red run: <list>. Revert them or move them to the coder step.` exit 1.
  3. Run `HARNESS_TEST_CMD` with `{files}` = the test files, `cwd` = worktree, timeout `HARNESS_TEST_TIMEOUT`, `PYTHONDONTWRITEBYTECODE=1`.
  4. kind: `green` when exit 0; else `import` when the output matches `ModuleNotFoundError|ImportError|No module named|Cannot find module|ERR_MODULE_NOT_FOUND`; `assertion` when it matches `AssertionError|assert |FAILED|failed|✗|not ok`; else `error`. Before that, a run that proves nothing is refused with no record and exit 1 (`no red run recorded: no tests ran` / `...: tests failed to load`): exit 5 or `no tests ran|NO TESTS RAN` → no tests ran; a `SyntaxError`/`IndentationError` line → failed to load; a missing module (`ModuleNotFoundError|ImportError: cannot import name|No module named|Cannot find module|ERR_MODULE_NOT_FOUND`) stays red even inside a pytest collection error; otherwise `error during collection|ERROR collecting` → failed to load, `collected 0 items` → no tests ran.
  5. Write the side file `red-files/<branch-slug>.json` (the test files' bytes as hashed, Red record above), then the record; print `red (<kind>): <n> test files, exit <code>` and the tail; exit 0 when red. On `green`: `Tests pass before the implementation; they do not test this change.` exit 1 (the record is still written so a refactor ticket can proceed).
- `status`: the record for the current branch, and `current: yes|no` (test_hash against the files now, or the files being the red-time ones with main's merged changes: Red record, above).
- After a merge of main the record stays current, so no new `check` is needed; one run anyway refuses with `Source already changed before the red run` (the coder's source is on the branch) and leaves the record as it was.
- `scratch create`: a detached worktree of `HEAD` at `~/.claude/harness/repos/<key>/scratch/<branch-slug>` (plus uncommitted test files copied in), prints the path; `scratch run`: `HARNESS_TEST_CMD` on the record's test files in the scratch, prints `cheat passed` (exit 0) or `cheat failed` (exit 1) and the tail; `scratch remove`.

### harness-pr

- `open N [--worktree PATH] [--verify-log F] [--review F] [--notes F]`: in the ticket's worktree: refuse with the list when the tree is dirty, and refuse a `--notes` file that is missing or has a `## ` heading outside a code fence (`###` is fine), both before the push; `git push -u origin <branch>`; body from `templates/pr_body.md` with the title, `Closes #N`, the notes (a `## Notes` section between Summary and Definition of done, only with `--notes`; the Resolution repeats it), the definition-of-done checkboxes copied from the ticket, the tests list, the red proof (kind, exit, 15 lines of tail), the verify tail (20 lines of `--verify-log`), the review summary (counts by severity and the high findings from `--review`), a risks line for `risk:high`; `gh pr create --draft --base main --head <branch> --title "<title> (#N)" --body-file`; if a PR for the branch exists, `gh pr edit --body-file` instead; `harness-board comment N` with the PR URL; prints `{"number", "url"}`.
- `review P --findings F`: findings JSON list `[{"path", "line", "severity": "high|medium|low", "body"}]`; `gh pr diff P` is parsed to the set of (path, right-side line) in the diff; findings on those lines become inline comments (`path`, `line`, `side: RIGHT`), the rest are listed in the review body; `gh api repos/O/R/pulls/P/reviews --input` with `event: COMMENT` and body `Harness review (<model>): <n> findings, <h> high, <m> medium, <l> low.` followed by the off-diff list and the marker `<!-- harness-review -->`. Zero findings: `gh pr review P --comment -b "Harness review: no findings. Checked: <text from --checked>"` followed by the marker, so it counts as the latest harness review.
- `checks P [--wait] [--timeout 1200]`: poll `gh pr view P --json statusCheckRollup` every 20 s: no checks after 120 s → `no checks registered` exit 0 with a warning; any `PENDING|QUEUED|IN_PROGRESS` → keep waiting; any `FAILURE|CANCELLED|TIMED_OUT|ERROR|ACTION_REQUIRED|STARTUP_FAILURE` → exit 1 with the names and, for GitHub Actions runs (details URL `/actions/runs/<id>`), the last 60 lines of `gh run view <id> --log-failed`; all `SUCCESS|SKIPPED|NEUTRAL` → exit 0. Without `--wait` one poll.
- The review gate, in `ready` and `land`: the latest harness review is the review with the newest `submitted_at` whose body carries `<!-- harness-review -->` (`gh api --paginate repos/O/R/pulls/P/reviews`); its findings are its inline comments (`.../reviews/<id>/comments`) and the ``- `path:line` [severity] body`` lines of its body, none for `Harness review: no findings.`; a commit is newer when its committer (else author) date in `.../pulls/P/commits` is after `submitted_at`. Findings and no newer commit: refuse with exit 1, naming each finding. gh failing: refuse (fail closed). No harness review: proceed.
- `ready P`: the review gate (no override); `gh pr ready P`; ticket number from `closingIssuesReferences` (or `--ticket N`); `harness-board status N in-review --comment "PR #P ready for review: <url>"`; notification `<repo> PR #P ready for review: <title>`.
- `comments P [--since ISO] [--unresolved]`: review threads (GraphQL `reviewThreads` with `isResolved`, comments with author, path, line, body, createdAt), reviews and issue comments on the PR, excluding bodies containing `<!-- harness-review -->`; `--unresolved` keeps unresolved threads only. JSON or markdown.
- `awaiting [--all-projects]`: open, non-draft PRs by the authenticated user: number, title, ticket, age, checks state (one poll), unresolved thread count. `--all-projects` walks the registry.
- `ultra P [--post] [--force]`: when the project's `HARNESS_ULTRAREVIEW` is off (`load_routing` on the main checkout: the environment, else its `settings.json`, never `settings.local.json`), prints `ultrareview PR #P: off for this project (HARNESS_ULTRAREVIEW=off); nothing run` and exits 0, with no claude call, no `ultra/<P>.json`, no budget change and no gh call; `--force` runs it whatever the setting. Each problem `load_routing` reports is one `harness-pr: warning:` line on stderr (also with `--force`); an invalid `HARNESS_ULTRAREVIEW` is ignored, so it runs. Otherwise `claude ultrareview P --json --timeout 30` (`--post` only with `--post`); saves stdout to `ultra/<P>.json`; a non-zero exit whose output mentions credits, billing or balance marks `cloud` exhausted for 24 h; prints the finding count and the highest severities.
- `land P [--yes] [--discard] [--accept-findings]`: preconditions: not a draft, `mergeable` not `CONFLICTING` (retry twice on `UNKNOWN`), checks green by one poll (cancelled counts as red), the review gate (`--accept-findings`, the only override, turns its refusal into a warning; a PR that is already merged skips it), `closingIssuesReferences` non-empty (warn and continue when empty). Then `gh pr merge P -R O/R --squash --delete-branch`; locate the worktree for the head branch in `git worktree list --porcelain`; `git worktree remove` (`--force` only with `--discard`; a dirty worktree otherwise stops after the merge with instructions); `git branch -D <branch>`; in the main checkout `git fetch --prune` and, when it is on main, `git pull --ff-only` (before it, each dirty path the fast-forward changes whose working-tree bytes equal the landed content, read from main's upstream after the fetch, and whose index holds HEAD's or the landed version, is restored with `git checkout <target> -- <paths>` and reported as `cleaned <path> (identical to the landed content)`; when any path git would refuse to overwrite differs, or an untracked file is in the way, nothing is restored, main is not pulled and those paths are named as a problem; never a stash); confirm the ticket closed (else `gh issue close`), remove its `status:*` labels, comment the `**Resolution**` (format under The board; body and url from `gh pr view P --json body,files,url`, every changed file from `gh api repos/O/R/pulls/P/files?per_page=100 --paginate --slurp`, or the view's first 100 files with a warning when that call fails; a failed `gh pr view` posts neither comment and names the Resolution in the error; before posting it, `harness-work cost N --pr P --markdown --repo <main>` (the sibling tool, run as harness-board is: no stdin, the tool timeout, cwd the main checkout) and its stdout, stripped, appended after a blank line as that ticket's Cost block; empty stdout adds nothing, and a non-zero exit, a timeout or no harness-work is one `harness-pr: warning: no cost block for #N: <first stderr line, else exit K, else the reason>` line and the Resolution without the block, the land's exit unchanged) and then `Landed in <merge sha>`, both through `harness-board comment`. Idempotent on resume: no Resolution (and no cost run) when the ticket already has one, and neither comment when `Landed in` is already there (the Resolution goes first, so a land stopped between them still posts `Landed in`). The skip matches only this landing's own comments, `Landed in` this merge sha (when the sha is unknown, the `Squash commit:` of this PR's Resolution) or `Landed in PR #P` (each a whole token) and a Resolution whose `PR:` line is this PR's URL, so a reopened ticket's second landing gets its own Resolution and `Landed in`; `harness-board epic-check <parent>` when there is a parent. Prints a four-line summary.
- `gate P [--json]`: the auto-land verdict (The auto-land gate, below). In the main checkout `git fetch --quiet origin`, then `gate_settings`; autoland off prints `manual: autoland off` with no further gh call; else `gh repo view` for O/R, `gather_facts` and `evaluate`. Prints one line `<verdict>: <reason>`; `--json` prints `{pr, verdict, code, reason, rule, head, ticket}` (head and ticket null when unknown). A gh or git call that fails gives verdict `wait`, code `gh`, rule null and the reason `<call> failed: <first stderr line>` (fail closed). Exit 0 for every verdict; 1 for a bad invocation or no repository.

### The auto-land gate

`lib/harness_lib/autoland.py` decides whether a pull request may merge without Ryan; everything it does not land stays for `/harness:land`. `evaluate(facts, settings)` takes the facts gathered about one pull request (`pr`, `state`, `draft`, `head_ref`, `head_sha`, `author`, `login`, `closing`, `pr_labels`, `incidents`, `deploy`, `ticket` with `number`, `state` and `labels`, `files` with a rename's old path included, `review` with `commit_id`, `at_head`, `unreadable` and the `high`, `medium` and `low` counts, `unresolved_threads`, `owner_comments`, `behind_by`, `mergeable`, `checks`, `failed_checks`, `pending_checks`, `nontest_files`, `nontest_lines`) and answers `{verdict, code, reason, rule}`. The rules run in order and the first failing one decides; inside a rule the first failing condition, in the order below, decides. N is the ticket's number.

| Rule | Fails when | Verdict/code |
|---|---|---|
| 1 | autoland is not on | manual/off |
| 2 | state is anything but `OPEN`; draft; the head is not `t/<N>-...`; the author is not the authenticated login; `closing` is not exactly `[N]` | manual/pr |
| 3 | any open incident (the reason names every one) | wait/incident |
| 3 | a deploy of main not `completed` (in flight), or `completed` with any conclusion but `success` (failed); no deploy workflow passes | wait/deploy |
| 4 | the ticket's state is anything but `OPEN` | manual/ticket |
| 4 | the ticket's risk labels are anything but exactly `risk:low` | manual/risk |
| 4 | no `size:` label, or any `size:` label outside the sizes | manual/size |
| 4 | `manual-land` on the PR or the ticket | manual/label |
| 5 | a changed path matches a manual path | manual/path |
| 5 | more than 8 non-test files or more than 400 non-test changed lines (size labels are estimates; this is the backstop) | manual/too large |
| 6 | no harness review, or the latest one's first line is neither the counts line nor `Harness review: no findings.` (`unreadable harness review`) | manual/review |
| 6 | the latest harness review is not at the head (`review of <sha7>, head <sha7>`) | wait/re-check |
| 6 | a high or medium finding at the head (low findings land) | fix/findings |
| 7 | the conversation is longer than one page of any of its connections (`conversation too long to read: ...`) | manual/comment |
| 7 | an unresolved review thread or an owner comment | manual/comment |
| 8 | `mergeable` is `CONFLICTING` | fix/conflict |
| 8 | `mergeable` is anything else but `MERGEABLE` (`UNKNOWN`: GitHub has not computed it yet) | wait/mergeable |
| 8 | behind main | wait/behind |
| 9 | checks `pending` | wait/ci |
| 9 | checks `failure` (the reason names the failed checks) | fix/ci |
| 9 | checks anything else (`none` and any unknown value) | manual/checks |
| 10 | all passed | land/land (`gate passed at <sha7>`) |

`gather_facts(main, slug, pr)` gathers those facts with gh.py's sequential helpers and git, both in the main checkout `main` (origin already fetched): `gh api user --jq .login`; `gh pr view P --json number,state,isDraft,headRefName,headRefOid,author,closingIssuesReferences,labels,mergeable,statusCheckRollup` (the ticket N from the head `t/<N>-...`; checks through `check_entries` and `overall`, which harness-pr's checks and land use too); `gh issue list --label incident --state open --json number,title`; `gh run list --workflow deploy.yml --branch main --limit 1 --json status,conclusion,headSha` (none, or gh failing with the API's 404 for deploy.yml, `HTTP 404: workflow deploy.yml not found ...`, gives deploy null; any other failure, a 404 about another workflow included, is a failing call); `gh issue view N --json state,labels`; `gh api repos/O/R/pulls/P/files?per_page=100 --paginate --slurp` (`files` with a rename's old path; `nontest_files` and `nontest_lines`, each file once by its new path with additions plus deletions, outside the HARNESS_TEST_PATTERNS committed at origin/main, else settings.py's `DEFAULT_TEST_PATTERNS`); `gh api --paginate repos/O/R/pulls/P/reviews` (the latest harness review as in the review gate, counting only reviews whose `user.login` is the `gh api user` login, since anyone can type the marker; its counts from its first line, `Harness review (<model>): <n> finding(s), <h> high, <m> medium, <l> low.` or `Harness review: no findings.`, anything else `unreadable`); `gh api --paginate repos/O/R/pulls/P/commits`; the GraphQL `CONVERSATION` query (authors with `__typename`; one page per connection, each asking `totalCount` and `pageInfo { hasNextPage }`, and `conversation_truncated` names the review threads, reviews, PR comments or a thread's comments that a page left out, since the unread rest may hold an owner comment); `gh api repos/O/R/compare/main...<head sha> --jq .behind_by`. An owner comment is a PR comment or review whose body is not empty, holds neither `<!-- harness -->` nor `<!-- harness-review -->`, and whose author is not a bot (`__typename` `Bot` or a login ending in `[bot]`); an unresolved thread counts when it holds one. `at_head` is true when the review's `commit_id` is the head, or when, walking first parents back from the head through the PR's commits, every commit until the reviewed one (which must be among them) is a clean merge of main: two parents, the second an ancestor of `origin/main`, and its tree equal to `git merge-tree --write-tree <parent1> <parent2>` without conflicts (after `git fetch origin <headRefName>`; git 2.38 or newer). A failing call raises `GatherError` (`<call> failed: <first stderr line>`, the call named as gh.py's `describe` names it, or `git <words>`), carrying the facts gathered before it.

`gate_settings(main, ref="origin/main")` gives `{autoland, sizes, manual_paths, smoke_local}` read only from the `env` of `<ref>:.claude/settings.json` (settings.py's `committed_env`): the process environment, the working tree and `settings.local.json` never count, so turning auto-land on takes a reviewed commit on main. Values follow `setting`'s rule for a file value (a string or number, never a bool, stripped).

| Variable | Meaning | Default |
|---|---|---|
| `HARNESS_AUTOLAND` | `1` opts the project in | off |
| `HARNESS_AUTOLAND_SIZES` | comma-separated sizes that may land; a value holding anything but `S`, `M` or `L` is ignored | `S,M` |
| `HARNESS_MANUAL_PATHS` | comma-separated globs that always land by hand, added after the defaults (de-duplicated); nothing here removes a default | none |
| `HARNESS_SMOKE_LOCAL` | `1` runs the smoke check locally | off |

`DEFAULT_MANUAL_PATHS`: `.github/**`, `.claude/**`, `scripts/deploy.sh`, `scripts/smoke.sh`, `scripts/deploy_guard.py`, `scripts/verify.sh`, `**/credentials/**`, `**/.env*`, `**/*.pem`, and `pyproject.toml`, `package.json`, `**/conftest.py`, `pytest.ini`, which decide what CI runs. Paths match with settings.py's `glob_match`.

### harness-digest

Across the registry: PRs awaiting review (`harness-pr awaiting --all-projects`), `status:needs-input` tickets with the first line of the question, `status:in-progress` tickets older than 3 days without a PR, stale worktrees, runs with outcome `billing|auth|error|early` since the last digest (the newest digest file other than today's, which a second run the same day rewrites; 24 h without one), budgets. Writes `~/.claude/harness/digest/<date>.md`, prints it, and sends one notification `Harness digest: <p> PRs to review, <q> need input, <s> stale` (nothing when all zero). `--install-launchd` writes `~/Library/LaunchAgents/com.ryaneskuri.harness-digest.plist` (daily at 08:30, `python3 <absolute path of this script>`, `PATH` including `/opt/homebrew/bin` and `~/.local/bin`, stdout and stderr to `~/.claude/harness/digest/launchd.log`) and loads it with `launchctl bootstrap gui/<uid>`; `--uninstall-launchd` reverses it. Each project's calls get a 6 s budget; a project that cannot be read gets one line.

### harness-standup, harness-projects, harness-worklog

`harness-standup` adds, per project and inside the existing time budget (gh calls run in threads, 6 s): `Board: r ready, p in progress, v in review, q needs input` (only for a project whose `origin` is on github.com); `PRs awaiting you:` lines; `Needs input:` lines (title, first line of the question); `Stale worktrees:` lines; and after the fleet section a `## Budgets` line when any budget is exhausted and a `## Runs` section for headless runs alive or failed in the last day. `harness-projects` is unchanged. `harness-worklog` reads the transcripts of the repo's own `~/.claude/projects/` folder and of every folder for a worktree under `<repo>/.claude/worktrees/` (removed worktrees included), counting each entry of a session id found in several files once; `--transcripts <folder>` still reads that one folder alone. Run from inside a linked worktree (by `--repo`, `CLAUDE_PROJECT_DIR` or the cwd), it works on the main checkout, so the log never lands on a ticket branch. `harness-worklog` counts as the user's own message any non-empty user text that does not start with a tag or whose leading tag, by exact name, is `pasted_content`, `bash-input` or `command-name` (or `command-message` with a `<command-name>` later in the text), so pastes, `!` commands and slash commands bill their block while task notifications, system reminders, local command output, `isMeta` and compaction summaries do not.

## Templates

`templates/`: `ticket_task.md`, `ticket_epic.md`, `pr_body.md`, `CLAUDE.md`, `settings.json`, `verify.sh`, `ci.yml`, `deploy.yml`, `deploy_guard.py`, `pull_request_template.md`, `pre-commit`, `gitignore`, `worktreeinclude`, `pyproject.toml`, `package.json`, `test_smoke.py`, `smoke.test.js`.

`deploy.yml` (v2): on a push to main and on `workflow_dispatch` with a boolean input `force` (default false); concurrency group `deploy-main`, cancel-in-progress false; permissions `contents: write` (the revert's push), `issues: write`, `pull-requests: read` (the merge's pull request and the ticket it closes); one job, 90 minutes (deploy.sh and smoke.sh at their default bounds, both again after a revert, plus git and gh): `actions/checkout` with `fetch-depth: 0`, then one step with `GH_TOKEN` from `github.token`. `deploy_guard.py`, copied to a project's `scripts/`, standard library and gh only (`HARNESS_GH`, else `gh`; the repository is `GITHUB_REPOSITORY`, else `gh repo view`):
- `run --sha SHA [--force]`, in order: an open issue labelled `deploy-frozen` (`gh issue list --label deploy-frozen --state open`; closed ones never count) and no `--force` prints `deploys are frozen by #N` and exits 0, deploying nothing (a freeze that cannot be read exits 1); no `scripts/deploy.sh` prints `no deploy script`, exit 0; `scripts/deploy.sh` runs, bounded by `DEPLOY_GUARD_DEPLOY_TIMEOUT` seconds (default 1800), and a non-zero exit or the timeout exits 1 with no revert; no `scripts/smoke.sh`, exit 0; `scripts/smoke.sh` runs, bounded by `DEPLOY_GUARD_SMOKE_TIMEOUT` seconds (default 600), its stdout and stderr into a log: exit 0 exits 0, exit 2 is `degraded`, anything else or the timeout is `revert`, each with that log, and `run` exits with its exit.
- `degraded --sha SHA --smoke-log F`: a comment on the open issue labelled `degraded`, else `Degraded: <owner/repo>` opened with that label (made sure of first with `gh label create`, its failure ignored); the body names the commit and fences the log's last 60 lines. No git write; exit 0, 1 when GitHub could not be told.
- `revert --sha SHA [--smoke-log F]`: revert the merge on main as github-actions[bot], redeploy and smoke again under the same two bounds (a revert pushed with `GITHUB_TOKEN` does not trigger deploy.yml again), open the incident and ask on the ticket; a revert that cannot restore main freezes deploys (`deploy-frozen`) and exits 1, a successful one exits 0.

## Canary

Harness's live system is the main checkout every project loads, so its smoke check is local: `sh scripts/smoke.sh [--plugin DIR]` runs `scripts/canary.py` with python3 (DIR defaults to `plugins/harness`), one line per check on stdout, a passing one starting with `ok`. It compiles every `.py` under hooks/ and lib/ and every file in bin/ (a dotfile, such as a Finder `.DS_Store` or an AppleDouble `._` file, is skipped here and in the `--help` runs) with `/usr/bin/python3` when it exists (the 3.9 floor), else python3, through `compile()` so no bytecode is written; runs each hook as Claude Code does (`python3 <hook>`, the event on stdin, 10 s) in a temporary git repository on main with one commit and reads its answer as Claude Code does (stdout parsed as JSON, the decision at `hookSpecificOutput.permissionDecision`; text that is not JSON is no decision): branch_guard denies an Edit of a source file and `git commit -m x` and allows an Edit under `docs/agent/` and `git status`, readonly_bash denies `echo x > f` for `harness:reviewer`, tests_first allows on main, session_brief answers SessionStart with an `additionalContext`, notify with no notifier on PATH prints the bell, after_edit and verify_on_stop exit 0; and runs every bin tool's `--help`. A case fails on a timeout, a non-zero exit, a traceback, an error line on stderr or a wrong answer. Exit 1 on a big failure (a file that does not compile, any hook case, the `--help` of harness-pr, harness-board, harness-work or harness-red, a `--plugin` that is not there), 2 when only a reporting tool's `--help` failed, else 0; a big failure wins. Every process it starts gets a temporary HOME, TMPDIR and working directory and none of the caller's `HARNESS_*`, `CLAUDE_*`, `GIT_*` or `PYTHON*` variables or `XDG_CONFIG_HOME`, so `HARNESS_ALLOW_MAIN` cannot turn a deny into an allow; the temporary directory is removed at the end. Under 120 s (a few seconds on this Mac); `tests/test_canary.py` runs it on plugin copies with spelled breaks.

## Daily use

- **New project**: `/harness:new-project ~/Projects/<name>`.
- **Plan**: `/harness:plan <request>` interviews you and writes the epic and tasks on the board.
- **Work**: `/harness:work` dispatches every ready ticket; `/harness:work 12` runs one here. Notifications tell you when a PR is ready or a ticket needs you.
- **Answer**: reply on the ticket; the next `/harness:work 12` reads it.
- **Land**: `/harness:land` lists PRs waiting; `/harness:land 7` merges one and cleans up.
- **Morning**: `/harness:standup`; the digest arrives at 08:30 on its own.
- **Lessons**: `/harness:learn` files chore tickets. **Context**: `/harness:handoff` before `/clear`. **Hours**: `/harness:worklog`.
