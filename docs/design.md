# Harness design, v2

Ryan's personal Claude Code harness. One repository, one plugin, installed once at user scope, applied to every project. v2 written 2026-10-13 against Claude Code 2.1.296 (installed from the latest channel that day; the per-call Agent `effort` parameter arrived in 2.1.292), gh 2.99.0, git 2.39. v1 (2026-10-06) is in git history; what changed and why is in `docs/research/` and in the interview notes at the end of this file.

## Principles

1. **The board is the context.** Every unit of work is a GitHub issue: an epic with sub-issue tasks, each carrying the request, an outline, a definition of done and the tests that must pass. Agents read the ticket and its epic before working and write status back. The user's job is to answer questions on tickets and review pull requests.
2. **Tests before code, proven.** A test-author writes tests from the ticket; a tool proves they fail against the unchanged code; an adversary tries to pass them with a trivial implementation; only then does a coder touch source. A hook denies source edits until the proof exists.
3. **Never on main.** Each ticket gets its own branch and worktree. A hook denies edits, commits and pushes on main in every repository. GitHub Free does not protect branches on private repos, so the hook is the only block; landing goes through a pull request: eligible ones are merged by `harness-pr autoland`, the user lands the rest.
4. **Route by labels, escalate by failure.** Opus 5.5 at high effort is the default everywhere. The planner labels each task with size and risk; the labels pick the tier (Sonnet, Opus, Fable). A second failure re-runs one tier up; a third stops and asks on the ticket.
5. **Spend the subscription first.** Interactive sessions and dispatched ticket work run on the Max subscription by default. The API key is spent only on request: `harness-work dispatch --api` (an alias for `--venue headless`) runs headless and bills it. While the `api` budget is exhausted, `--api` and `--venue headless` are refused. High-risk pull requests get ultrareview, which bills claude.ai usage credits. An exhausted budget is remembered for a day.
6. **Additive, never invasive.** Projects keep their own `CLAUDE.md`, hooks, rules and skills. The harness adds the board, the guards and the loop beside them, in every project including jotform-glow-sync.
7. **Deterministic where it must be, advisory where it can be.** Hooks and tools enforce; prompts advise.
8. **Fail open, except where a guard is sure.** A hook that hits its own error exits 0 and says so on stderr. The guards deny only when they have established the branch and the path.
9. **Standard library only.** `python3` 3.9 or newer, `git`, `gh`. Nothing to install.
10. **Hooks run outside the sandbox**, with the user's permissions and no prompt. The verify and test commands must be commands the user trusts.

Code shared between files lives in `plugins/harness/lib/harness_lib` (python3 standard library, `from __future__ import annotations`), loaded in place from the checkout with no install step. A file finds it relative to its own real path: a seven-line prologue at module top, after the standard-library imports, puts `os.path.realpath(__file__)`'s `../lib` first on `sys.path` (so a symlink still reaches the checkout, and neither a hooks/-local file nor a project file can shadow it; a file copied out of the checkout does not find it) and binds the names it uses in its own namespace (`from harness_lib.paths import canonical_path, ...`), never through `CLAUDE_PLUGIN_ROOT`. `paths.py` holds the state-key helpers (repo-key, below); `shellwalk.py` holds the shell walker both Bash guards split commands with: `Part`, `closing`, `substitution`, `split_command`, `command_words`, `stdin_program`, the tables behind them (`SHELLS`, `WRAPPERS`, `KEYWORDS`, `GIT_VALUE_OPTIONS`, `ASSIGNMENT`, `NUMBER`, `PYTHON`, `SED_IN_PLACE`, `REDIRECT`, `REDIRECTS`) and the depth cap `MAX_DEPTH`, defined once there and never in a hook. The hooks branch_guard, tests_first and session_brief import `paths.py` today, and so do all six bin tools that use the state-key helpers (harness-board, harness-pr, harness-work, harness-red, harness-standup and harness-digest); none carries a copy. The hooks branch_guard, tests_first, readonly_bash, session_brief, verify_on_stop, after_edit and notify also import `hookio.py`. `lib/harness_lib/hookio.py` holds the hook I/O those seven share: `read_input()` (the event on stdin, `{}` for empty, invalid or non-object input), `hook_cwd(data)` (`cwd`, else `CLAUDE_PROJECT_DIR`, else the process's directory), `edited_path(data)` (`tool_input`'s `file_path`, else `notebook_path`), `deny(reason)` (the PreToolUse deny JSON), `emit(obj)` (`json.dumps` to stdout, no newline) and `run_fail_open(name, main)`, the `__main__` tail: `main()`'s status (0 for None), or on an exception one stderr line `<name>: <error>` and 0. `sessionstate.py` holds the per-session state after_edit and verify_on_stop share: `SessionState.for_repo(root, data)` (`.dir`, `$TMPDIR/claude-harness/<first 12 hex of the sha1 of the resolved root>`, made on the first write, never by naming a path; `.session`, the `session_id` with anything outside `[A-Za-z0-9._-]` turned into `_`, `nosession` when absent; `.dirty`, `.verify_file` and `.stamp(name)`, the files `dirty-<session>`, `verify-<session>.json` and `<name>-<session>` in it; `ensure_dir()`, `record(paths)`, `dirty_files()` and `clear_dirty()`), `porcelain_status(root, timeout)` (`git status --porcelain=v1 -z --untracked-files=all` without the index lock: `b""` for no root, None when git fails or times out) and `status_paths(root, out)` (the paths in that output, a rename's or copy's source skipped). Only session_brief keeps a fallback copy of the four it uses, inside the except branch of its lib import, so the brief still reaches the session without the lib. `settings.py` holds `settings_env(root, names=("settings.json", "settings.local.json"))` (the `env` object of each named `.claude` file, a later file winning key by key; a missing or broken file counts as none), `setting` (the environment first when not blank, then a string or number from that `env`), `patterns` (a comma-separated list, stripped, empties dropped) and `glob_match` (repo-relative, `**` takes zero or more segments, other segments `fnmatchcase`, a pattern without `/` matches the basename); branch_guard, tests_first, verify_on_stop, harness-red and harness-work import them and keep no copy. tests_first classifies with `settings_env(main, ("settings.json",))` only, the main checkout's tracked file. harness-scaffold keeps its own `TEST_FILE_PATTERNS`. hooks/notify.py, harness-board, harness-pr and harness-digest import `notify.py`, the one macOS notification (`notify(message, group, title="Harness", subtitle="") -> bool`: terminal-notifier with `-title`, `-subtitle` only when given, `-message`, `-group`, `-activate`, `-sound`, else osascript; it answers whether either showed it and never raises), with `env_setting`, `succeeded`, `applescript_string`, `DEFAULT_APP` and `DEFAULT_SOUND`; no other file keeps a copy. `cli.py` and `text.py` hold the bin tools' command-line scaffolding and their text, file and time helpers; harness-board, harness-pr, harness-standup and harness-digest import them and keep no copy, harness-worklog imports `Parser`, `run_main` and `session_folder`, and the hooks session_brief and tests_first import `read_json` (session_brief also `one_line`, with a fallback copy of both only in its lib import's except branch); harness-projects imports `Problem` but keeps its own `Parser`, and harness-work, harness-red and harness-scaffold still carry their own `Parser`, `Problem` and some of the helpers below, until they move over. `cli.py` holds `Problem` (a bad invocation, a failed precondition or a failed call: one line, exit 1), `Parser` (argparse whose `error` is `<prog>: error: <message>` on stderr and exit 1), `run_main(prog, main)` (the `__main__` tail: a `Problem` is `<prog>: <one line>`, any other exception `<prog>: <TypeName>: <one line>`, both exit 1 and never a traceback; Ctrl-C exits 130; a closed stdout (`| head`) exits 1 quietly; `SystemExit` passes through; otherwise 0), `warn(prog, message)` (`<prog>: warning: <one line>` on stderr), `emit(as_json, data, text)` (indented JSON with non-ASCII kept, else the text), `table(rows)` (left-aligned columns two spaces apart) and `issue_number` (an argparse `type=`: a positive number, `#` allowed). `text.py` holds `one_line` (whitespace runs collapsed), `first_line` and `last_line` (the first or last non-blank line, stripped, `""` for none), `as_list` (a gh list given as a JSON list or `{"nodes": [...]}`, its objects only), `read_text(path, what)` (`~` expanded, undecodable bytes replaced, a `Problem` naming `what` and the path when unreadable), `read_json` (None when unreadable or invalid), `write_json(path, data, *, prefix)` and `write_text(path, text, *, prefix)` (written to a `prefix`ed temporary file in the target's folder and renamed over the target, so a reader never sees half a file; the folder is made, the temporary file removed on failure), `home` and `harness_home` (`~/...` and `~/.claude/harness/...`), `same_path` (whether two paths name the same real path, `~` expanded), `session_folder` (Claude Code's folder name for a project: every non-alphanumeric turned into `-`), `now_iso` (the current UTC second, `2026-10-16T12:34:56Z`), `parse_iso` (an aware datetime, a `Z` or a naive time meaning UTC, else None), `parse_iso_seconds` (epoch seconds, a naive time meaning local time, else None) and `age_text(then, now)` (`just now`, `5m ago`, `3h ago`, `2d ago`, `4mo ago`, `2y ago`). `registry.py` is the one reader and writer of `~/.claude/harness/projects.json` for harness-projects, harness-board, harness-standup and harness-digest: `Project(path, name, billable=False, client="", notes="", extra={})` (`from_entry` fills in the schema's fields, the name defaulting to the folder's, and keeps unknown keys in `extra`; `to_entry()` writes them back), `registry_path()`, `load_registry(strict=False, path=None)` (`path` defaults to `registry_path()`; `[]` for a missing file; Problem with the one wording of `is not valid JSON ... fix it or remove it`, `cannot read <path>: <error>`, `expected {"version": 1, "projects": [...]}` and `is version ...; this tool reads version 1`; an entry without a path is skipped, or with `strict`, as harness-projects reads, `<path>: project N has no path`), `save_registry(projects)` (through text.py's `write_json`) and `find_project(projects, key)` (exact name, then any case, then path; Problem for none or several). No tool keeps a copy; harness-pr keeps its own reader, which turns a malformed registry into an empty table. `gh.py` holds the gh helpers: `gh_exe()` (`HARNESS_GH`, else `gh`), `gh_binary()` (that name as a path when it holds a separator and is executable, else looked up on PATH; None when not found), `GH_ENV` (`GH_PROMPT_DISABLED`, `GH_NO_UPDATE_NOTIFIER`, `NO_COLOR`, each `1`), `describe_list_call(args)`, `repo_slug(origin_url)` and `GhBatch(gh, calls, cwd, deadline, *, budget_seconds, describe=describe_list_call)`, the gh calls run side by side whose failures are cli.py's `Problem` and whose timeout names the `budget_seconds` it was given; harness-standup and harness-digest import them and pass their own `GH_BUDGET`, and session_brief imports `gh_binary` and `GH_ENV` (a fallback copy only in its lib import's except branch) and keeps its own `run_side_by_side`. Fail open: a hook that cannot load the lib (missing, a syntax error, an import that raises) writes `<hook>.py: cannot load harness_lib from <lib>: <error>` to stderr in one line and exits 0, so the call is allowed; notify.py also prints the bell (`{"terminalSequence": "\u0007"}`, as when `notify` answers False), because a Notification hook's stderr reaches no one; session_brief instead goes on without ticket state and puts one `Warning:` line naming harness_lib in the brief, because the guards are then off and a SessionStart hook's stderr reaches no one; in a project that declares its own SessionStart hook, where the brief is otherwise silent, that warning line is its whole output. The bin tools do not fail open: a bin tool that imports the lib (every one but harness-scaffold) prints `<tool>: cannot load harness_lib from <lib>: <error>` in one line and exits 1 before it parses an argument, because it must not guess a state key.

Every bin script is otherwise standalone (no imports between scripts): argparse, standard library, finds nothing through `CLAUDE_PLUGIN_ROOT` (that variable is not set for Bash). Scripts compose by calling each other on PATH and exchanging JSON (`--json`). A script that must call another finds it next to itself (`Path(__file__).resolve().parent`) when it is not on PATH. Each prints one line and exits 1 on a bad invocation or a failed precondition, never a traceback. `gh` is resolved as `os.environ.get("HARNESS_GH", "gh")` so tests can substitute a fake.

Install (once): `sh scripts/install.sh`. A marketplace added from a local path loads the plugin in place, so edits take effect at the next session start or `/reload-plugins`.

## Platform facts this design relies on

Verified 2026-10-13 from the Claude Code docs, the gh source at v2.99.0 and the GitHub docs; details in `docs/research/`.

- Plugin agents support `model` (alias, full id or `inherit`) and `effort`; they ignore `hooks` and `permissionMode`. The Agent tool takes `model` per call and, since 2.1.292, `effort`. An agent that omits `effort` runs at the session's level.
- `"model": "opus"` in settings resolves to Opus 5.5. `modelSettings` is keyed by canonical ids (`claude-opus-5-5`, `claude-fable-5-1`, `claude-sonnet-5-5`); a top-level `effortLevel` does not apply to Opus 5.5.
- PreToolUse receives `cwd`, `session_id`, `agent_type` (`harness:coder` for plugin agents), `tool_name`, `tool_input` (`file_path` absolute for Edit and Write, `notebook_path` for NotebookEdit, `command` for Bash). It denies with `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny", "permissionDecisionReason": "..."}}`; deny wins over every other hook. SessionStart carries no branch; its `cwd` is the worktree root when the session runs in one.
- `claude -w <name>` creates `.claude/worktrees/<name>` on branch `worktree-<name>` and cannot pick a branch name; `git worktree add` is the way to control the branch. `claude --bg -n <name> "<prompt>"` starts a background session in the cwd with the supervisor's stored login; trust is inherited from the main checkout; a session already in a linked worktree does not self-isolate. `claude rm` leaves a user-created worktree in place.
- Billing: `ANTHROPIC_API_KEY` and `apiKeyHelper` outrank the subscription login; in `-p` mode the key is used without a prompt. Background sessions cannot be billed separately. Cloud sessions and routines bill the subscription, need a TTY to start, and do not load plugins. `claude ultrareview <PR> --post --json` runs in the cloud, bills usage credits (about 5 to 25 dollars a run), and prints findings.
- gh: `gh issue create --parent` links a sub-issue (not idempotent on retry); `gh api repos/O/R/issues/N/sub_issues` lists sub-issues with labels; `--blocked-by`, `--add-blocked-by` and `--json blockedBy` are native; a parent never auto-closes. `gh label create --force` updates. `gh pr checks --watch` exits 0, 1 (failure) or 8 (pending) and counts cancelled runs as not failed. The PR author can post a `COMMENT` review with inline comments through `POST /repos/O/R/pulls/N/reviews`; `APPROVE` is refused. `gh pr merge -R O/R --squash --delete-branch` deletes only the remote branch; local cleanup is ours. Branch protection and rulesets return 403 on this account's private repos. Issue types are organization-only; labels it is.

Machine-wide, under `env` in `~/.claude/settings.json`: `HARNESS_API_KEY_CMD` (default `security find-generic-password -s harness-anthropic -w`), `HARNESS_NOTIFY_APP`, `HARNESS_NOTIFY_SOUND`, `HARNESS_SECRET_SCAN`, `HARNESS_PROJECT` (`owner/number` of the GitHub Projects board harness-board mirrors the labels to; unset means no mirroring; see The board), `CLAUDE_VERIFY_TIMEOUT` as before.

Globs match against the repo-relative path with `/` separators; `**` matches any number of segments including none; a pattern without `/` matches the basename. One matcher function, specified here so every script agrees: split the pattern on `/`, walk segments, `**` consumes zero or more, other segments use `fnmatch`.

## State

- `~/.claude/harness/projects.json`: the registry (unchanged, v1 schema).
- `~/.claude/harness/budgets.json`: `{"api": {"exhausted_until": ISO-8601 or null, "reason": ""}, "cloud": {...}}`.
- `~/.claude/harness/runs/<repo-key>-<issue>-<yyyymmddHHMMSS>.json`: one headless or background run (schema under harness-work).
- `~/.claude/harness/digest/<yyyy-mm-dd>.md`: the daily digest.
- `~/.claude/harness/repos/<repo-key>/`: durable per-repository state: `tickets/<issue>.json` (ticket cache), `red/<branch-slug>.json` (red proofs), `scratch/<branch-slug>/` (the adversary's working copy), `ultra/<pr>.json`.
- `$TMPDIR/claude-harness/<repo-key>/`: the v1 ephemeral state (dirty lists, fingerprints), unchanged.

`repo-key` is the first 12 hex digits of the sha1 of the canonical path of the **main** working tree, found as the parent of `git rev-parse --git-common-dir` resolved to an absolute path. The canonical path is the real path with each component spelled as its parent directory lists it (`os.listdir`, matched case- and normalisation-insensitively and confirmed with `samefile`); from the first component that cannot be found, the rest stays as the real path spells it. A linked worktree and its main checkout therefore share one state directory, and so does every spelling of the path on a case-insensitive file system (macOS: `portfolio_projects/Harness` and `portfolio_projects/harness`). The helpers `canonical_path`, `same_entry`, `path_key`, `repo_key` and `adopt_old_state` are defined once, in `lib/harness_lib/paths.py`. The hooks session_brief and tests_first import all five and branch_guard imports `canonical_path` and `same_entry`, each binding the names in its own namespace; none keeps a copy, so without the lib a hook computes no key of its own (it fails open, above). The tools harness-board, harness-pr and harness-work import all five; harness-red imports `canonical_path`, `repo_key` and `adopt_old_state`; and harness-standup and harness-digest (which only key run files and never migrate a directory) import `canonical_path`, `same_entry`, `path_key` and `repo_key`. No tool keeps a copy (without the lib they print one line and exit 1, above). branch_guard uses no key helpers: it judges a main checkout reached through another spelling of its path (`/users/.../harness` for `/Users/.../Harness`) exactly as the on-disk spelling, comparing git's on-disk paths with the given path canonically rather than by `realpath`. `branch-slug` is the branch name with `/` replaced by `-`.

Migration from the spelling-based key: before the key was canonical it was the sha1 of the real path as spelled. When `repos/<repo-key>/` does not exist and `repos/<old>/` does, where `<old>` is the sha1 of the spelling of the main tree that git reported or that the tool's start path (cwd, `--repo`, `CLAUDE_PROJECT_DIR`, the hook's cwd or edited path) uses, the old directory is renamed to the canonical key, once. Only that repository's directory is moved; when both exist, both stay and the canonical one is used. harness-standup and harness-digest attribute a run file to a registered project by the canonical key or by the old key of the registered spelling, and harness-work counts a run as the repository's when its `repo` field is any spelling of the main tree.

## The board

GitHub Issues in each project's private repository. An **epic** is an issue labeled `epic`; its **tasks** are sub-issues. Dependencies use GitHub's native blocked-by. Status, type, size, risk and flags are labels. Done is closed.

**Projects board (optional, a mirrored view).** One GitHub Projects board, a user-owned project spanning the registered repositories, shows the same tickets as columns by Status, with the epics as swim lanes (grouped by Parent issue). The labels stay authoritative: no ticket state is ever taken from the board, and only `harness-board project check` and `project sync` read it, to compare it with the labels. The mirror sets the item's Status (Ready, In progress, In review, Blocked or Needs input) and, for `task create --priority`, Priority High; a closed issue becomes Done through the project's built-in workflow, not through the harness. A card dragged to another column is not a status change: the labels are not touched, and for an open issue the board is put back from the labels the next time that issue's status changes or `harness-board project sync` runs (decision D3 in `docs/proposals/kanban-board.md`). That holds for open issues only: a closed issue's card dragged out of Done stays where it is until auto-archive removes it. A drag between epic lanes may also change the issue's parent. A failed mirror call is one warning and never fails a command, so the board can drift until the next sync; `project check` and `project sync` report their own failures with exit 1. Since no ticket state comes from the board, drift is cosmetic. It is off unless `HARNESS_PROJECT` is set, from the environment (an empty value is off) or `env` in `~/.claude/settings.json`, and it needs the `project` scope of `gh auth`. Ryan chose a new board, separate from the existing "Claude Kanban" project #1 (2026-10-14). Setup is manual and is in `docs/guide.md` (Projects board); the behavior is specified under harness-board below (the mirror, #64; `project check` and `project sync`, #65).

Labels (name, color, meaning), created idempotently by `harness-board labels ensure`:

Tier rubric, implemented once in `harness-board tier`: `size:S` and `risk:low` and type not `bug` gives `sonnet`; `size:L` or `risk:high` gives `fable`; everything else gives `opus`. Escalation order is sonnet, opus, fable. The review stage has its own rule, `harness-board tier N --stage review`: `fable` for `risk:high`, `opus` for everything else.

Task body template (`templates/ticket_task.md`; the planner fills it, the scaffold installs it as a GitHub issue template too):

```markdown
## Request
<what was asked, in the requester's words, one paragraph>

## Outline
1. <step>

## Definition of done
- [ ] <observable, testable statement>

## Tests that must pass
Broad behavior first, specific cases after. One line each: where, and what it proves.
- `tests/test_<area>.py::test_<behavior>`: <the contract it pins down>
The existing suite (`<verify command>`) stays green.

## Context
- `<path>`: <why it matters>
```

Epic body template (`templates/ticket_epic.md`): `## Goal`, `## Why`, `## Scope` and `## Out of scope`, `## Definition of done`, `## Verification` (the end-to-end commands), `## Decisions and open questions`. Tasks are the sub-issues; no task list in the body.

## Agents

| Agent | Model, effort | Tools | Job |
|---|---|---|---|
| `planner` | opus, xhigh | Read, Grep, Glob, Bash (read-only guard) | Turns an interviewed request into an epic and tasks in the templates, with sizes, risks, flags and blocked-by, under the size cap. Returns a proposal; creates nothing. |
| `test-author` | opus (tier override per call), effort inherited | all | Writes the tests the ticket names, broad behavior first, against the public interface, and runs them to show them red. The tests-first hook denies it any source edit. |
| `test-breaker` | opus (tier override), inherited | all | In the scratch copy, writes the cheapest implementation that could pass the new tests (constants, special-casing the fixtures) and runs them. If it passes, the tests are too narrow. Denied test edits by the hook. |
| `coder` | opus (tier override), inherited | all | Makes the tests and the verify command green with the smallest coherent change, commits on the ticket branch, reports evidence. Denied test edits by the hook; stops and reports when the change outgrows the size cap. |
| `reviewer` | opus (fable, xhigh, for risk:high) | Read, Grep, Glob, Bash (read-only guard) | Reviews the branch against the ticket's definition of done; returns findings as JSON lines for the PR. |
| `researcher` | opus, inherited | WebFetch, WebSearch, Read, Grep, Glob, Bash (read-only guard) | Primary-source fact checking, as in v1. |
| `quick` | sonnet, inherited | all | Trivial mechanical tasks outside the ticket loop, as in v1. |

The orchestrator passes `model` on the Agent call from `harness-board tier` (and `effort` too once the Agent tool offers it: `high` by default, `xhigh` when escalating to Fable). The reviewer's model comes from `harness-board tier N --stage review`: `opus`, and `fable` (with `xhigh`) when the ticket is `risk:high` or when `harness-work attempt` says `escalate fable` for the review stage. The review stage is recorded with `harness-work attempt N review pass|fail --tier <the output of harness-board tier N --stage review>`, so its second failure escalates from opus to fable; without `--tier` the attempt uses the ticket's own tier, and a sonnet-tier ticket would escalate to opus. The read-only guard (`readonly_bash.py`) now covers `planner`, `reviewer` and `researcher`.

### The work loop (one ticket, in-session)

```
harness-work start N            ticket context, branch t/N-slug, worktree, status in-progress, tier
test-author (tier)              tests only; must show them red
harness-red check               proof: tests fail, source untouched; record written
test-breaker (tier)             scratch copy; cheat attempt; pass means tests go back to the author (max 2 rounds)
coder (tier)                    source only; new tests and CLAUDE_VERIFY_CMD green; commits
reviewer (opus; fable if risk:high) findings JSON; split by the ticket's files: the rest become new tickets
harness-pr open N [--notes F]   push, draft PR from the template (Closes #N, DoD, red proof, verify tail); --notes adds a `## Notes` section (second pass, out-of-scope file) that the Resolution repeats
harness-pr review P --findings  inline review comments from the findings on the ticket's files
coder (tier)                    fixes every posted finding, whatever its severity, in commits after the review;
                                push; the reviewer re-checks and its findings are posted again
harness-work attempt N fix      after each fix round: pass when the re-check found nothing on the ticket's files;
                                retry, then needs-input (max 2 rounds, no escalation)
harness-pr checks P --wait      CI; failures go back to the coder (max 2 rounds)
[harness-pr ultra P]            when risk:high: ultrareview, posted to the PR
harness-pr ready P              refused while the latest harness review has findings and no newer commit;
                                ready for review, status in-review, notification
```

Every review finding on the files the ticket touched is fixed before `harness-pr ready`, whatever its severity; only a finding outside the ticket's files becomes a new ticket, and the PR body names it and says why. The skill is one turn, every agent in the foreground: it ends at ready, a posted needs-input question, a `harness-work start` refusal, or the final failure `harness-work attempt` records; without a ticket number, once dispatch has launched the runs, shown its `--dry-run` plan or found no ready tickets.

A ticket whose `flags` (from `harness-board show N --json`) hold `no-tests` skips the test-author, `harness-red check` and the breaker: the coder implements against the definition of done, the verify command must still pass, and the review still runs.

Failure policy, enforced by `harness-work attempt`: the first failure of a stage retries at the same tier; the second re-runs one tier up; the third calls `harness-board needs-input` with the evidence and stops. `fix` has its own rule, the loop's two fix rounds: its first failure retries at the same tier and its second calls `needs-input`, with no escalation. A stage is `tests` (red cannot be reached), `breaker` (tests still cheatable after two rounds: proceed, but say so in the PR), `code` (verify not green), `review` (the reviewer returned no usable findings; a findings array of any length, empty included, passes), `fix` (findings on the ticket's files still open after a fix round's re-check), `ci` (checks red). Each stage counts its own failures: a run of failures ends at that stage's next pass, and another stage's result neither adds to it nor resets it.

Every Agent call the work skill makes carries the description `#N <stage>`, which `harness-work cost` reads (`^#(\d+)\b` and the word after it): `tests` for the test-author (in a revise pass too), `breaker`, `code` for the coder until the first review, `review` for the first review, and `fix` for every coder or reviewer run after the first review (its findings, CI failures, ultrareview findings, the owner's comments). Any question the agents cannot answer from the ticket, the epic or the code also ends in `needs-input`. A revisit of a ticket with `status:needs-input` and a newer comment by the repository owner passes that comment to the agents as the answer. A revisit of a ticket in `status:in-review` with unresolved review threads from the owner runs the coder on those comments only, then checks and ready again.

**branch_guard.py** (PreToolUse `Edit|Write|NotebookEdit|Bash`). Fail open. Exempt when `HARNESS_ALLOW_MAIN` is `1` (environment or project settings).
- Edit, Write, NotebookEdit: take `file_path` or `notebook_path`; walk up to an existing directory; `git -C <dir> symbolic-ref --short HEAD`; if the branch is `main` or `master` and `git rev-parse --verify HEAD` succeeds (the repo has a commit), deny, except for a path under `docs/agent/` (the handoff note and specs, which the session brief reads) and for an untracked path that `git check-ignore` reports as ignored (local settings, `.env`, scratch files): `On main in <repo basename>. Work happens on a ticket branch: harness-work start <issue#> for a ticket, or git switch -c t/<n>-<slug> for untracked work.` Outside a repo, on a detached HEAD, or on an empty repo: allow.
- Bash: split the command on `;`, `&&`, `||`, `|`, `&` and newlines (and inside `(...)`, `$(...)`, `sh -c`, `eval`, a heredoc a shell reads and a `-c alias.x='!...'` git alias) and judge each part in the directory it runs in: `cwd`, moved by `cd`/`pushd` (an empty target, or one that is not a directory, leaves it unchanged unless `&&` follows, since a failed `cd` stops the chain; an unresolvable target such as `$VAR` makes it unknown and the repo rules allow), restored after a subshell, substitution or child shell; git's directory also follows `-C`, `--git-dir` and `--work-tree`, and `-c alias.<x>=` aliases are expanded. Deny when (a) a part writes a path whose repo (that of the nearest existing directory; `.git/...` belongs to the repo around it) is a main working tree on `main` or `master` with a commit, from any cwd: a redirection or `tee` to it, `cp`, `mv`, `install`, `ln`, `rsync` or `dd of=` into it, `mv`, `rm`, `touch`, `truncate` or `chmod` of it, `sed`/`gsed -i`, `perl -i`, `awk -i inplace`, `ed` or `patch` on it (`xargs` with one of these counts as writing the current directory); a path under `<top>/.claude/worktrees/`, in a linked worktree or outside any repo is never refused, nor is `mkdir`, nor a named path the Edit rule exempts (under `docs/agent/`, or one `git check-ignore` reports, so a directory holding a tracked file is not exempt), for every form above, `rm`, `truncate` and both sides of `mv` included. The exemption judges what the write reaches: a `cp`, `mv`, `ln`, `install` or `rsync` into a directory is judged by that directory, both for the repo it lands in (the holder rule runs on the destination directory, not on `dest/<basename of a source>`, so `cp -R /tmp/x/t-13-x/ .claude/worktrees/` lands in the main checkout's `.claude/worktrees/`, and `cp -R /tmp/x/link/ .` lands at the root although the tracked `link` points outside) and for the exemption, which holds only when that directory itself is exempt (`docs/agent` or under it, or ignored), whatever its sources, since BSD `cp -R src/ dest` copies the contents of `src` and the shell expands a glob or brace source, so no source word names what lands there (`cp -R /tmp/x/data/ .` is refused although `data/` is ignored; `cp /tmp/*.log cache/` into an ignored `cache/` is allowed); into an existing exempt directory, a recursive copy (`cp -R`, `-r`, `-a`, in any cluster; `rsync -r`, `-a`, `--recursive`, `--archive`) is refused unless the directory is `docs/agent` or under it, because an ignored directory can hold a symlink into tracked code (`node_modules/@scope/pkg -> ../../packages/pkg`) that the copy writes through, and any of these copies is refused when `dest/<basename of a source>` already exists and is not exempt itself (an ignored `cache/app.py` symlinked to the tracked `src/app.py`); a name that does not exist, a plain file or a link that stays inside the exemption keeps the directory rule; a named file destination, a recursive copy to a name that does not exist yet included, is judged by its name (`cp notes.md docs/agent/handoff.md`, `ln -sfn ../.venv .venv`, `cp -R /tmp/x/data cache/restored`); never a word with an unquoted glob (`*`, `?`, `[`) or brace expansion (`{a,b}`, `{a..b}`), never a path whose first repo-relative component is `.git`; never a spelling that differs in case from a tracked file it names on a case-insensitive file system (`git ls-files -- ':(icase,literal)<path>'` lists that file under another spelling and it is the same file); a symlink is exempt only when the file it resolves to is itself exempt or lies outside every protected main working tree; with several targets the reason names the first one not exempt; (b) git runs in such a repo and the part is `git commit`, `merge` (unless `--ff-only`), `rebase`, `cherry-pick`, `revert`, `am`, `apply` (except `--check`/`--stat`/`--numstat`/`--summary`), `reset`, `rm` (except `--cached` or `-n`), `mv`, `clean` (except `-n`), `restore` (except `--staged` alone), `stash pop|apply`, `checkout` of paths or `-B main`, `switch -C main`, `branch -f|-m|-C` onto main or `-D|-d main|master`, `update-ref` or `symbolic-ref` writing `HEAD` or main, or `git push` with no refspec, of `HEAD`, or with `--delete`/`:` of any branch; (c) the part runs in such a repo and is `python -c`, `node -e`, or a python or node program read from a heredoc, that opens a file for writing or writes, moves or deletes files, unless the program has at least one path literal and every one lies outside every protected main working tree (by the holder rule of (a), so a ticket worktree or a repo on another branch counts as outside): a path literal is a quoted string (`'`, `"` or backtick) that starts with `/`, `~/`, `./` or `../`, holds a `/`, or is a bare file name with an extension (`[A-Za-z0-9_.-]+[.][A-Za-z0-9]{1,8}`), resolved against the part's directory with `~/` expanded; a path given only on the command line is not a literal; a program with a path literal joined to a value known only at run time is refused: after `+` or `+=` with a non-literal before it, an argument of any `.join(` or `.concat(` call (`os.path.join`, `path.join`, `''.join([...])`, `x.concat(...)`) with a non-literal argument before it, or of a `.concat(` whose receiver is not a literal, or an f-string or template literal with an interpolation before a `/`; a join made only of literals (list brackets and commas aside) is fixed. The literal check is a heuristic: a path built at run time in a form it does not recognise (such as a target held only in a call or a variable, as in `shutil.copy('/tmp/a', os.getcwd())`) is not seen, and such a program counts as writing outside when its literals do; (d) on any branch, in any repo state, including linked worktrees and outside a repo: any `git push` with `--force`, `-f`, `--force-with-lease`, a `+refspec` or a short-flag cluster containing `f`, or whose destination names `main` or `master` (`main`, `HEAD:main`, `x:refs/heads/main`, `:main`, `--delete main`), or with `--mirror`, `--all`, a matching `:` or a wildcard reaching main (`HARNESS_ALLOW_MAIN=1` turns off the whole guard, this included). Reason text names the part. Allowed on main: everything that reads, `git fetch`, `git pull`, `git switch`, `git checkout <branch>`, `git worktree ...`, `gh ...`, `harness-* ...`, the verify command.
- Never deny inside a linked worktree (its branch is never main), never deny for a different repo than the one on main. A command that is exactly the project's `CLAUDE_VERIFY_CMD` is always allowed. `mv` is refused when either path is in a protected repo and not exempt; `cp`, `install`, `ln` and `rsync` only by destination.

## bin tools

### harness-board

`harness-board <sub> [--repo PATH] [--json]`. Repo: `--repo`, else `CLAUDE_PROJECT_DIR`, else the toplevel of the cwd. `OWNER/REPO` from `gh repo view --json nameWithOwner`; no remote or no `gh` login → one line, exit 1.

Projects board mirror (#64): `HARNESS_PROJECT=<owner>/<number>` from the environment (an empty value turns it off), else `env.HARNESS_PROJECT` of `~/.claude/settings.json` when that parses as a JSON object; unset or unreadable means no `gh project` call at all, and a value not matching `owner/number` (number from 1, no leading zero, nothing stripped) is one warning and no call. With it set, `epic create` and `task create` run `gh project item-add <n> --owner <o> --url <issue url>` once the issue exists, then `gh project item-edit <n> --owner <o> --url <url> --field Status --value Ready`, and for `task create --priority` `--field Priority --value High`. The labels stay the source of truth: the first failing project call stops the rest, prints one warning, and leaves the exit code unchanged. `harness-work` and `harness-pr` pass each `harness-board: warning:` stderr line of a harness-board call that exits 0 through to their own stderr, in order, and keep its other stderr hidden (#69).

- `labels ensure`: the label table above, `gh label create <name> --color <hex> --description <text> --force`. Prints how many were created or updated.
- `epic create --title T --body-file F [--size S] [--risk R]`: labels `epic`, `status:ready`, size and risk when given. Prints `#N <url>`.
- `task create --title T --body-file F [--parent N] [--type task|bug|chore|refactor] [--size S|M|L] [--risk low|high] [--blocked-by N[,N]] [--no-tests] [--needs-local] [--priority]`: checks the remote and login first (`gh repo view`), creates the issue without `--parent`, then links it with `gh api -X POST repos/O/R/issues/<parent>/sub_issues -F sub_issue_id=<numeric id from gh issue view --json id? no: REST .id>` (the numeric database id, from `gh api repos/O/R/issues/N --jq .id`); a failed link is retried once and then reported with the issue number so no duplicate is ever created. Then `gh issue edit N --add-blocked-by`. Labels: type (default `task`), `status:ready`, size, risk, flags.
- `show N [--markdown]`: `gh issue view N --json number,title,url,body,labels,state,parent,blockedBy,comments`; when the issue is an epic, `gh api repos/O/R/issues/N/sub_issues` for the tasks with labels and state; parses the body sections (headings `## Request`, `## Outline`, `## Definition of done` as checkbox lines, `## Tests that must pass`, `## Context`); writes the cache (preserving `branch`, `worktree`, `started_at`, `attempts` from an existing cache); prints JSON, or with `--markdown` the ticket context, at most 120 lines: title and labels, the sections, the epic's goal paragraph, blocked-by numbers with state, the last 10 comments (author, date, first 20 lines each). A closed ticket's `**Resolution**` comments are printed whole after the sections, one per landing, oldest first, under `## Resolution` (`## Resolution (landing K of M)` when a reopened ticket has several), and left out of the comments; an epic's closed tasks each get their newest Resolution under `### #N <title>: Resolution` below the task list (one `gh issue view N --json comments` per closed task, markdown only; a task without one, or whose comments cannot be read, adds nothing). Resolutions come before comments in the 120-line budget: each is printed whole or not at all, and those that do not fit are named on one `Not shown for lack of room` pointer line (each ticket once). A ticket's own Resolutions are fitted newest first, so the oldest landing is the one dropped.
- `ready`: open issues with `status:ready` and not `epic`, whose `blockedBy` are all closed, `priority:high` first, then lowest number first. Table or JSON (number, title, type, size, risk, tier, flags).
- `status N <ready|in-progress|in-review|blocked|needs-input> [--comment TEXT]`: removes every `status:*` label, adds the new one, then (with `HARNESS_PROJECT`, the issue's url fetched with its labels) one `gh project item-edit ... --field Status` with Ready, In progress, In review, Blocked or Needs input, then comments when asked. `needs-input`, `harness-work start` and `harness-pr ready` go through it.
- `comment N (--body TEXT | --body-file F)`.
- `needs-input N --question TEXT [--evidence-file F]`: `status needs-input`, a comment `**Needs your input**` with the question, the evidence (fenced, at most 60 lines) and the line `Reply in a comment; /harness:work N picks it up.`, then a macOS notification `<repo> #N needs input` (harness_lib's `notify`, as notify.py). Prints the URL.
- `answers N [--since ISO]`: comments by the authenticated user (`gh api user --jq .login`) newer than `--since` (default: the newest `**Needs your input**` comment, else the cache's `fetched_at`, else no bound), skipping the harness's own comments (posted under the same account): every comment harness-board posts (`comment`, `status --comment`, `needs-input`, `close --comment`, `epic-check`) ends with the line `<!-- harness -->`, and older ones are recognised by a body starting `**Needs your input**`, `Started on `, `PR #` or `Landed in `. JSON. `status`, `close` and `epic-check` also refresh an existing cache so the session brief never shows a stale status.
- `close N [--comment TEXT]`; `epic-check N`: when `subIssuesSummary.completed == total` and total > 0, comment `All tasks landed.` and close the epic.
- `board`: markdown by status, counts in the headings, `#N title (type, size, risk)` lines; `--json` the same structure.
- `tier N [--stage review]`: `sonnet`, `opus` or `fable` per the rubric; from the cache when present, else fetched. With `--stage review` (the only stage accepted) it prints `fable` for a `risk:high` ticket and `opus` otherwise, whatever the type and size.
- `project check` (#65): needs a valid `HARNESS_PROJECT` (unset, empty or not `owner/number` is one line naming it, exit 1, before any `gh project` call), then `gh project field-list <n> --owner <o> --format json --limit 100`. The Status field needs the options Ready, In progress, In review, Blocked, Needs input and Done, and Priority needs High and Normal, matched by name. Prints one line per missing field or option and exits 1 when any is missing, else one line and exit 0. A failed field-list is one line naming it, exit 1. It takes no `--repo` or `--json`.
- `project sync [--repo PATH | --all-projects] [--dry-run]` (#65): the repair path, with the same `HARNESS_PROJECT` rule as `check`. Reads the board once (`gh project item-list <n> --owner <o> --format json --limit 1000`; a failed read is one line naming item-list, exit 1, no writes), then the open issues of the repository (`--repo`, else as above) or of every project in `~/.claude/harness/projects.json` (the registry harness-standup and harness-digest read; a registered path that is missing, not a git repository or has no remote is one warning, skipped, exit 1 at the end), with `gh issue list --state open --json number,url,labels,state --limit 1000` run in each repository. Items match issues by issue URL. A missing open issue is added (`item-add`), then Status and Priority are written with `item-edit` only where the board disagrees: Status from the issue's own `status:*` label by the mirror's map (no status label: no Status write; an unknown label such as `status:done`, or two status labels: one warning naming the issue, no Status write), Priority High for `priority:high`, else Normal, where an unset board Priority counts as Normal: only High against Normal (either way) is drift, and an added issue gets a Priority write only for High (#74 review). Closed issues (the built-in workflow sets Done), pull requests, drafts and other repositories' items are never written. One stdout line per change (`<url>: add to the board`, `<url>: <Field> <old> -> <new>`) and a summary line; `--dry-run` prints the same lines and makes no write. A failed write is one stderr line naming the issue (a failed add skips that issue's edits); the rest still run, exit 1. When item-list's `totalCount` exceeds the items read, no issue is added (it may be on the unread part), drift on the items read is still fixed, and one warning gives the count, exit 1; an issue list that reaches its limit warns too, exit 1.

### harness-work

- `start N [--repo PATH]`: `harness-board show N` (cache); refuse an epic, a closed issue, a blocked ticket (open blockers listed) or `status:blocked`; `git fetch origin`; branch `t/N-<slug>` (slug: title lower-cased, non `[a-z0-9]` runs to `-`, trimmed, at most 30 chars); if `origin/t/N-*` exists reuse that branch, else `git worktree add <main>/.claude/worktrees/t-N-<slug> -b t/N-<slug> origin/main` (when the worktree already exists, reuse it); ensure `.git/info/exclude` lists `.claude/worktrees/`; run `HARNESS_WORKTREE_SETUP` or the detected setup in the worktree, then copy gitignored files matching `.worktreeinclude` from the main checkout; `harness-board status N in-progress --comment "Started on t/N-<slug> (<hostname>, <venue>)"` unless already in progress; record `branch`, `worktree`, `started_at` in the cache. Prints JSON `{"number", "branch", "worktree", "tier", "context": "<markdown>"}`; without `--json` prints the worktree path and then the markdown context.
- `attempt N <stage> <pass|fail> [--tier T]`: appends to the cache and prints the next action for that stage on failure: `retry` (one failure so far), `escalate <tier>` (two failures; the tier above the last used, Fable stays Fable), `needs-input` (three). Prints `done` on pass. Stages: `tests`, `breaker`, `code`, `review`, `fix`, `ci`; `fix` never escalates: `retry` after one failure, `needs-input` from the second. Failures count per stage, so `fix` and `review` count apart.
- `dispatch [--max 3] [--venue headless|bg | --api] [--dry-run]`: `--api` is an alias for `--venue headless`, and `--api` with `--venue bg` is an argument error. First `runs --sweep` (below), then the budget check: when `api` is exhausted after the sweep (the sweep can be what marks it) and `--venue headless` or `--api` was given, refuse with a non-zero exit, `--dry-run` and an empty board included, naming the time it is exhausted until and `harness-work budget reset api`, and start and launch nothing; then `harness-board ready`; skip tickets that have a live run; for each remaining up to `--max` minus live runs: `start N`, then launch. A live run is an unended record whose headless process is alive, or whose `--bg` session `claude agents` lists in a live state (`running`, `working`, `blocked`, `idle`, `busy`, `waiting`, `starting`; any live state while the listing cannot be read). The sweep has already closed (and stopped) a `--bg` session whose ticket is finished, so such a session holds no slot, `--dry-run` included, and `--max N` plans N minus the truly live runs; a `blocked` session of a ticket that is not finished stays live and holds one:
  - venue `headless` (only with `--api` or `--venue headless`; refused, as above, while `api` is exhausted): in the worktree, `claude -p "/harness:work N" --permission-mode auto --output-format json --settings <json>` where the settings JSON is `{"apiKeyHelper": "<HARNESS_API_KEY_CMD>"}` (the key itself never appears on a command line or in the environment), detached with `nohup`/`setsid`-equivalent (`subprocess.Popen(start_new_session=True)`), stdout and stderr to `~/.claude/harness/runs/<id>.log`;
  - venue `bg` (the default, whatever the budgets say; runs on the subscription): in the worktree, `claude --bg -n "<repo> #N <title>" --permission-mode auto "/harness:work N"` (the same unattended mode as headless, or the session stops at its first permission prompt); parse the id from `backgrounded · <id>`.
  - Write the run record `{"id", "ticket", "repo", "worktree", "branch", "venue", "pid" | "bg_id", "log", "started_at", "ended_at": null, "exit": null, "outcome": null}`.
  - `--dry-run` prints the plan and launches nothing.
- `runs [--sweep] [--all]`: lists run records with state (alive, exited N, done, `ended early (draft PR #N)`, `ended early (no PR)`). `--sweep` updates records whose process has exited: reads the log tail and sets `outcome` (`ok`, `early`, `billing`, `auth`, `error`), or for a `--bg` run maps its `claude agents` state (`done` → `ok`, `failed` → `error`, `stopped` → `stopped`). The ticket, not the state, says when a `--bg` turn is over, because the bg supervisor marks a finished session `blocked` (not `done`) when its summary of the final reply suggests a next step for the user (#123): a ticket is finished when its issue is CLOSED (whatever labels it kept, `status:in-progress` included) or OPEN with `status:in-review` or `status:needs-input`; in progress, ready, blocked or without a status label it is not. For each unended `--bg` record whose session the listing shows (in any state but `stopped`), the sweep reads the issue (once per command, shared with the early check and the redispatch); when the ticket is finished it runs `claude stop <bg_id>` (the conversation is kept), reports `stopped session <id>` (on stdout, on stderr under `--json`), and closes the record, `ok` for a live state and the mapped outcome for an ended one. A failed `claude stop` is one `harness-work: #N: cannot stop session <id>: ...` warning, the exit code unchanged and the record still closed; a closed record is never stopped again. A session whose ticket is not finished is never stopped and a live state keeps its record open; when the repository or gh cannot read the ticket, one warning, and the session is neither stopped nor counted ended (an ended state still closes its record, `ok` without the early check). An `ok` run, headless or `--bg` (a `failed` or `stopped` one never), whose issue is OPEN and still `status:in-progress` with no ready pull request of its branch in any state (none, or only drafts: a draft counts as no ready pull request; a row without `isDraft` is not a draft) becomes `early` (the session ended its turn before the work did), whatever the log says, and the record keeps the newest open draft as `draft_pr`, shown as `ended early (draft PR #N)` (an `early` state is shown in place of `exited N`); when gh cannot tell, or the record names no repository, it stays `ok` with a warning, and one command asks gh once per ticket and branch (dispatch's sweep and its redispatch share the answer); `exit` is set only for `--bg` runs when the `claude agents` listing provides it, otherwise it stays null (a reparented headless child leaves no exit code). With a JSON result (`claude -p --output-format json`; its `subtype` says `success` even on an API error): `is_error` not true → `ok`; an API failure (`terminal_reason: "api_error"` or an `api_error_status`) → `auth` on 401 and 403, `billing` on 402, `error` on 429 and 5xx whatever the text, otherwise by the `result` text, which then holds claude's own message (`^(Credit balance is too low|Your credit balance|insufficient credits|billing)` → `billing`; `^(Invalid API key|Not logged in|authentication)`, a 4xx naming the key `^API Error: 4\d\d .*API key` (not 429), `apiKeyHelper script is failing` or `anthropic-workspace-id` anywhere → `auth`, a credential that can never work), else `error`; any other `is_error` → `error`, and the result text, the model's own words then, is never read. Without a JSON result (a crash before one), the tail's API-error lines decide: `credit balance|insufficient.*credit|billing_error|payment required|402` → `billing`, `invalid.*api.key|authentication_error|401` → `auth`. A `billing` or `auth` outcome on a headless run marks `api` exhausted for 24 h with the status and message (or the matching line) as reason, and until then `dispatch --api` and `--venue headless` are refused. A ticket whose run ended without a ready PR (`early`, or any other ended outcome) and is still `status:in-progress` is re-dispatched by the next `dispatch` (`again after <outcome>` in the plan, `again after <outcome>, draft PR #N` when an open draft exists), until 3 of its runs ended within 7 days; a run whose outcome is `billing` or `auth` does not count (the budget's failure, not the ticket's: after `budget reset api` or on `bg` the ticket goes again), every other ended run does, a null outcome, `stopped` and `unknown` included. When an open draft exists, the launch prompt (`/harness:work N` followed by a paragraph) and a start comment on the issue name the PR and say the worktree may hold uncommitted work from the previous run, so the run reads `git status` and the PR's review comments first; otherwise the prompt and the start comment are the plain ones. Past that cap, dispatch skips the ticket with `<runs> runs ended without a ready pull request in 7 days (last: <outcome> at <ended_at of the latest-started run>); run it in this session with /harness:work N, or wait for the window` (`--json`: `{"number", "why", "runs", "window_days": 7, "advice": "/harness:work N"}`; `<runs>` and `runs` are the counted runs, billing and auth left out), since a run in the session you are watching is the way forward. `runs` appends `capped` to the STATE of that latest-started record (`runs --json`: `"capped": true`, `state` unchanged) for exactly the tickets dispatch would skip by the cap in this repository: no live run, the latest run ended inside the window, the issue open and `status:in-progress` with no ready pull request of its branch (when gh cannot tell, no mark); `runs` asks gh only about tickets at the cap.
- `budget [status | exhaust <api|cloud> --reason TEXT [--hours 24] | reset <api|cloud>]`.
- `worktrees [--stale DAYS]`: every `.claude/worktrees/*` of the repo with branch, last commit age, PR number and state (from `gh pr list --head`), flagged stale when older than `--stale` (default 7) and without an open PR. `worktree remove <branch> [--discard]`: `git worktree remove` (refuses a dirty tree unless `--discard`) then `git branch -D`.

Cloud dispatch is out of scope for v2: cloud sessions bill the subscription, need a TTY and do not load plugins. `needs-local` is kept on tickets so a future cloud venue can respect it.

### harness-red

Runs in a ticket worktree (cwd, or `--worktree PATH`). On a `t/<n>-` branch whose ticket cache (`tickets/<n>.json`) has `no-tests` in `flags`, `check` and `status` print `ticket N is no-tests: no red run needed` (with `--json`, one object `{"no_tests": true, "ticket": N, "message": "..."}`) and exit 0 with no run and no record (a missing or corrupt cache, absent flags or another branch name take the normal path); `harness-pr open` then writes `none: the ticket is no-tests` in the red block.

- `check [--base origin/main]`:
  1. `merge-base HEAD <base>`; changed paths = `git diff --name-only <merge-base>` plus `git status --porcelain` untracked and modified. Test files = those matching `HARNESS_TEST_PATTERNS`; none → `No test changes on this branch; write the tests first.` exit 1.
  2. Source files changed (not test, not exempt) → `Source already changed before the red run: <list>. Revert them or move them to the coder step.` exit 1.
  3. Run `HARNESS_TEST_CMD` with `{files}` = the test files, `cwd` = worktree, timeout `HARNESS_TEST_TIMEOUT`, `PYTHONDONTWRITEBYTECODE=1`.
  4. kind: `green` when exit 0; else `import` when the output matches `ModuleNotFoundError|ImportError|No module named|Cannot find module|ERR_MODULE_NOT_FOUND`; `assertion` when it matches `AssertionError|assert |FAILED|failed|✗|not ok`; else `error`. Before that, a run that proves nothing is refused with no record and exit 1 (`no red run recorded: no tests ran` / `...: tests failed to load`): exit 5 or `no tests ran|NO TESTS RAN` → no tests ran; a `SyntaxError`/`IndentationError` line → failed to load; a missing module (`ModuleNotFoundError|ImportError: cannot import name|No module named|Cannot find module|ERR_MODULE_NOT_FOUND`) stays red even inside a pytest collection error; otherwise `error during collection|ERROR collecting` → failed to load, `collected 0 items` → no tests ran.
  5. Write the record; print `red (<kind>): <n> test files, exit <code>` and the tail; exit 0 when red. On `green`: `Tests pass before the implementation; they do not test this change.` exit 1 (the record is still written so a refactor ticket can proceed).
- `status`: the record for the current branch, and `current: yes|no` (test_hash against the files now).
- `scratch create`: a detached worktree of `HEAD` at `~/.claude/harness/repos/<key>/scratch/<branch-slug>` (plus uncommitted test files copied in), prints the path; `scratch run`: `HARNESS_TEST_CMD` on the record's test files in the scratch, prints `cheat passed` (exit 0) or `cheat failed` (exit 1) and the tail; `scratch remove`.

### harness-pr

- `open N [--worktree PATH] [--verify-log F] [--review F] [--notes F]`: in the ticket's worktree: refuse with the list when the tree is dirty, and refuse a `--notes` file that is missing or has a `## ` heading outside a code fence (`###` is fine), both before the push; `git push -u origin <branch>`; body from `templates/pr_body.md` with the title, `Closes #N`, the notes (a `## Notes` section between Summary and Definition of done, only with `--notes`; the Resolution repeats it), the definition-of-done checkboxes copied from the ticket, the tests list, the red proof (kind, exit, 15 lines of tail), the verify tail (20 lines of `--verify-log`), the review summary (counts by severity and the high findings from `--review`), a risks line for `risk:high`; `gh pr create --draft --base main --head <branch> --title "<title> (#N)" --body-file`; if a PR for the branch exists, `gh pr edit --body-file` instead; `harness-board comment N` with the PR URL; prints `{"number", "url"}`.
- `review P --findings F`: findings JSON list `[{"path", "line", "severity": "high|medium|low", "body"}]`; `gh pr diff P` is parsed to the set of (path, right-side line) in the diff; findings on those lines become inline comments (`path`, `line`, `side: RIGHT`), the rest are listed in the review body; `gh api repos/O/R/pulls/P/reviews --input` with `event: COMMENT` and body `Harness review (<model>): <n> findings, <h> high, <m> medium, <l> low.` followed by the off-diff list and the marker `<!-- harness-review -->`. Zero findings: `gh pr review P --comment -b "Harness review: no findings. Checked: <text from --checked>"` followed by the marker, so it counts as the latest harness review.
- `checks P [--wait] [--timeout 1200]`: poll `gh pr view P --json statusCheckRollup` every 20 s: no checks after 120 s → `no checks registered` exit 0 with a warning; any `PENDING|QUEUED|IN_PROGRESS` → keep waiting; any `FAILURE|CANCELLED|TIMED_OUT|ERROR|ACTION_REQUIRED|STARTUP_FAILURE` → exit 1 with the names and, for GitHub Actions runs (details URL `/actions/runs/<id>`), the last 60 lines of `gh run view <id> --log-failed`; all `SUCCESS|SKIPPED|NEUTRAL` → exit 0. Without `--wait` one poll.
- The review gate, in `ready` and `land`: the latest harness review is the review with the newest `submitted_at` whose body carries `<!-- harness-review -->` (`gh api --paginate repos/O/R/pulls/P/reviews`); its findings are its inline comments (`.../reviews/<id>/comments`) and the ``- `path:line` [severity] body`` lines of its body, none for `Harness review: no findings.`; a commit is newer when its committer (else author) date in `.../pulls/P/commits` is after `submitted_at`. Findings and no newer commit: refuse with exit 1, naming each finding. gh failing: refuse (fail closed). No harness review: proceed.
- `ready P`: the review gate (no override); `gh pr ready P`; ticket number from `closingIssuesReferences` (or `--ticket N`); `harness-board status N in-review --comment "PR #P ready for review: <url>"`; notification `<repo> PR #P ready for review: <title>`.
- `comments P [--since ISO] [--unresolved]`: review threads (GraphQL `reviewThreads` with `isResolved`, comments with author, path, line, body, createdAt), reviews and issue comments on the PR, excluding bodies containing `<!-- harness-review -->`; `--unresolved` keeps unresolved threads only. JSON or markdown.
- `awaiting [--all-projects]`: open, non-draft PRs by the authenticated user: number, title, ticket, age, checks state (one poll), unresolved thread count. `--all-projects` walks the registry.
- `ultra P [--post]`: `claude ultrareview P --post --json --timeout 30` (post only with `--post`); saves stdout to `ultra/<P>.json`; a non-zero exit whose output mentions credits, billing or balance marks `cloud` exhausted for 24 h; prints the finding count and the highest severities.
- `land P [--yes] [--discard] [--accept-findings]`: preconditions: not a draft, `mergeable` not `CONFLICTING` (retry twice on `UNKNOWN`), checks green by one poll (cancelled counts as red), the review gate (`--accept-findings`, the only override, turns its refusal into a warning; a PR that is already merged skips it), `closingIssuesReferences` non-empty (warn and continue when empty). Then `gh pr merge P -R O/R --squash --delete-branch`; locate the worktree for the head branch in `git worktree list --porcelain`; `git worktree remove` (`--force` only with `--discard`; a dirty worktree otherwise stops after the merge with instructions); `git branch -D <branch>`; in the main checkout `git fetch --prune` and, when it is on main, `git pull --ff-only` (before it, each dirty path the fast-forward changes whose working-tree bytes equal the landed content, read from main's upstream after the fetch, and whose index holds HEAD's or the landed version, is restored with `git checkout <target> -- <paths>` and reported as `cleaned <path> (identical to the landed content)`; when any path git would refuse to overwrite differs, or an untracked file is in the way, nothing is restored, main is not pulled and those paths are named as a problem; never a stash); confirm the ticket closed (else `gh issue close`), remove its `status:*` labels, comment the `**Resolution**` (format under The board; body and url from `gh pr view P --json body,files,url`, every changed file from `gh api repos/O/R/pulls/P/files?per_page=100 --paginate --slurp`, or the view's first 100 files with a warning when that call fails; a failed `gh pr view` posts neither comment and names the Resolution in the error) and then `Landed in <merge sha>`, both through `harness-board comment`. Idempotent on resume: no Resolution when the ticket already has one, and neither comment when `Landed in` is already there (the Resolution goes first, so a land stopped between them still posts `Landed in`). The skip matches only this landing's own comments, `Landed in` this merge sha (when the sha is unknown, the `Squash commit:` of this PR's Resolution) or `Landed in PR #P` (each a whole token) and a Resolution whose `PR:` line is this PR's URL, so a reopened ticket's second landing gets its own Resolution and `Landed in`; `harness-board epic-check <parent>` when there is a parent. Prints a four-line summary.

  4. `--github`: `gh repo create <name> --private --source . --remote origin` (no push), `git push -u origin main`, `harness-board labels ensure`, `gh repo edit --delete-branch-on-merge`, then a ruleset attempt (`POST repos/O/R/rulesets`: target `main`, rules `pull_request`, `non_fast_forward`, `deletion`); a 403 prints `Branch protection is unavailable on this plan for a private repo; the local branch guard is the only block.` and continues.
  5. `--register`: `harness-projects add`.
- `labels`: `harness-board labels ensure` for an existing repo (alias).

### harness-digest

Across the registry: PRs awaiting review (`harness-pr awaiting --all-projects`), `status:needs-input` tickets with the first line of the question, `status:in-progress` tickets older than 3 days without a PR, stale worktrees, runs with outcome `billing|auth|error|early` since the last digest (the newest digest file other than today's, which a second run the same day rewrites; 24 h without one), budgets. Writes `~/.claude/harness/digest/<date>.md`, prints it, and sends one notification `Harness digest: <p> PRs to review, <q> need input, <s> stale` (nothing when all zero). `--install-launchd` writes `~/Library/LaunchAgents/com.ryaneskuri.harness-digest.plist` (daily at 08:30, `python3 <absolute path of this script>`, `PATH` including `/opt/homebrew/bin` and `~/.local/bin`, stdout and stderr to `~/.claude/harness/digest/launchd.log`) and loads it with `launchctl bootstrap gui/<uid>`; `--uninstall-launchd` reverses it. Each project's calls get a 6 s budget; a project that cannot be read gets one line.

### harness-standup, harness-projects, harness-worklog

`harness-standup` adds, per project and inside the existing time budget (gh calls run in threads, 6 s): `Board: r ready, p in progress, v in review, q needs input` (only for a project whose `origin` is on github.com); `PRs awaiting you:` lines; `Needs input:` lines (title, first line of the question); `Stale worktrees:` lines; and after the fleet section a `## Budgets` line when any budget is exhausted and a `## Runs` section for headless runs alive or failed in the last day. `harness-projects` is unchanged. `harness-worklog` reads the transcripts of the repo's own `~/.claude/projects/` folder and of every folder for a worktree under `<repo>/.claude/worktrees/` (removed worktrees included), counting each entry of a session id found in several files once; `--transcripts <folder>` still reads that one folder alone. Run from inside a linked worktree (by `--repo`, `CLAUDE_PROJECT_DIR` or the cwd), it works on the main checkout, so the log never lands on a ticket branch. `harness-worklog` counts as the user's own message any non-empty user text that does not start with a tag or whose leading tag, by exact name, is `pasted_content`, `bash-input` or `command-name` (or `command-message` with a `<command-name>` later in the text), so pastes, `!` commands and slash commands bill their block while task notifications, system reminders, local command output, `isMeta` and compaction summaries do not.
