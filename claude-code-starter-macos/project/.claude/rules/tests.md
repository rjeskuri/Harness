# Tests

- Tests check behavior through public functions, not implementation details, so refactors don't break them.
- A test verifies the solution; it doesn't define it. Never hard-code expected values into production code, and never delete, skip or loosen a failing test to make it pass. If a test looks wrong, say so and explain why.
- For a bug, first write a test that fails for the reported reason, then fix the code.
- Keep fixtures explicit and small, and put sample data in `tests/fixtures/`. Avoid deep fixture chains that hide where values come from.
- Files in `tests/golden/` are regenerated by a script, never edited by hand.
